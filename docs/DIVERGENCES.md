# DIVERGENCES.md — wire divergences & unconfirmed inferences

The single registry of (a) **deliberate divergences** from the Anthropic Claude
Managed Agents reference and (b) **inferences** about reference behavior made where
neither the SDK types nor the `ant` CLI can reveal it — each to be confirmed against a
real managed-agents recording. The verifier's wire-compat rung resolves intentional
mismatches against this file; an intentional mismatch missing here is a defect. New
divergences land here in the same PR that introduces them.

Format: **surface** — behavior. *Evidence.* Three sections: architecture/compatibility notes (not mismatches), CONFIRMED deliberate divergences, and INFERRED assumptions (each cross-linked to the issue tracking its confirmation).

## Architecture & compatibility notes (not divergences)

Facts that read like divergences but are not mismatches with the managed-agents wire —
recorded here so the allowlist stays honest.

- **Session resource (all session endpoints) — end-user binding** — Sessions carry no user_id field at all. Scoping keys are org/workspace/project (reserved, single-tenant defaults in v1); end-user-to-session ownership is an application-layer concern via session metadata and the audit-only created_by. This is a deliberate architectural divergence (explicitly from adk-go's AppName+UserID pattern; the platform stays user-agnostic). *Evidence: CLAUDE.md 'Non-negotiable design principles' #5; docs/history/2026-07.md § "`internal/store` — Postgres schema + migrations" (sessions schema: 'audit-only created_by, no user_id'); CLAUDE.md standing product decisions*
- **BYOC worker (POST …/work/{work_id}/heartbeat) — a stalled run stops beating** — A worker whose run reports no progress for `WORKER_STALL_TIMEOUT` (default 30m) cancels the run and stops heartbeating, so the lease lapses server-side and the control plane re-offers the item; it never force-stops such an item, since another worker may hold it by then (#383). No request or response shape changes — the worker simply stops calling a lane the protocol already handles the absence of, which is exactly what a dead worker's lease expiry is for — so this is client-side behavior, not a wire mismatch. The reference worker has no analogue: the pinned SDK's poller bounds only its Stop call (`stopTimeout`, 10s) and has no stall, deadline or max-runtime bound on the run itself, and the `ant` CLI's only worker-lifetime flag (`--max-idle`) stops the *worker* once its session goes idle on `end_turn`, which says nothing about a run that never returns — so nothing here contradicts observed reference behavior; the platform executor carries the same guard through `queue.KeepLease`, which is entirely internal. *Evidence: anthropic-sdk-go lib/environments/poller.go (stopTimeout is its only run-side bound); internal/worker/lease.go (progress, hbExitStalled), internal/queue/keeper.go (stall budget, ErrWorkStalled); docs/plan/33_bounding-a-wedged-work-item.md*
- **GET /v1/sessions/{id}/events/stream — SSE preview delta frames** — Streaming preview deltas use type 'content_delta', never the Messages API's 'content_block_delta'. event_start/event_delta frames are stream-only, never persisted, and reconcile under the buffered event's pre-allocated id. *Evidence: CLAUDE.md 'Wire-compatibility rules'; docs/history/2026-07.md § "`internal/events` + events API — append-only log, send/list, SSE stream (slice 3)" (events/preview.go: 'delta type is literally content_delta, NOT the Messages API's content_block_delta')*

## Deliberate divergences (CONFIRMED)

- **Session ID prefix parsing (all endpoints accepting a session id)** — Canonical prefix is sesn_; the alternate session_ form is accepted on input, mirroring the reference's dual form. *Evidence: CLAUDE.md 'Wire-compatibility rules'; docs/history/2026-07.md § "`internal/domain` — Anthropic-native core types" (domain/id.go 'accepts the alternate session_ form on input'); docs/history/2026-07.md § "`internal/api` + `cmd/controlplane` — wire-compatible control-plane CRUD"*
- **All endpoints — anthropic-version / anthropic-beta headers and ?beta=true** — anthropic-version and anthropic-beta request headers are accepted and ignored; ?beta=true is accepted where the reference honors it. No version negotiation is performed. *Evidence: CLAUDE.md 'Wire-compatibility rules'; docs/history/2026-07.md § "`internal/api` + `cmd/controlplane` — wire-compatible control-plane CRUD" (api/server.go: '?beta=true and anthropic-* headers accepted and ignored')*
- **Model backend (brain -> provider) — pluggable, config-driven providers** — The model backend is constructed purely from config (protocol anthropic|openai, model, base_url, api_key, optional headers) and routed via a model_providers registry. base_url is required for both adapters — there is no silent api.anthropic.com fallback — and an OpenAI-compatible gateway is a first-class backend. The reference has a fixed Anthropic backend; this whole seam is a deliberate self-hosting divergence. *Evidence: CLAUDE.md principle #4; docs/history/2026-07.md § "`internal/provider` — config-driven model access (slice 4)" (provider/provider.go, provider/anthropic: 'base_url is required (no silent api.anthropic.com fallback)'); docs/history/2026-07.md § "OpenAI-compatible adapter (`internal/provider/openai`)"*
- **Model turn timeout (brain -> provider) — bounded by the endpoint's silence, per route** — A turn is abandoned once the endpoint has sent nothing at all for that route's `stall_timeout` (default 10 minutes; any byte received, keepalives included, buys the budget back), and surfaces through the session.error(model_request_failed_error) shape a failed model request already uses — no new wire surface — settling exactly as one does: idle with retries_exhausted, or a chained turn with retry_status retrying when input arrived mid-turn (see the session.error retry-semantics inference below). The reference's own timeout policy is unobservable: the SDK types carry none and no recording shows one. This is therefore a platform-side operational bound rather than a claim about the reference — the hosted reference bounds its own fixed backend however it likes, while a self-hosted deployment points at arbitrary endpoints and must not let one wedged proxy hold a brain replica out of service (#121). *Evidence: docs/plan/17_model-endpoint-stall-bound.md; internal/provider/stall.go (StallGuard); docs/HISTORY.md § "Model endpoint stall bound (plan 17)"; see also the session.error retry-semantics inference below (#78)*
- **Observability — OTel alongside span.* events; traceparent across processes** — OTel spans and Anthropic span.* wire events are emitted from the same instrumentation point; W3C traceparent/tracestate propagates through every cross-process call including through work items to BYOC workers. Additive platform surface (deliberate divergence goal: OTel built in). *Evidence: CLAUDE.md principle #3; docs/history/2026-07.md § "`internal/events` + events API — append-only log, send/list, SSE stream (slice 3)" (events/span.go), docs/history/2026-07.md § "BYOC worker — `traceparent` propagation across the process boundary (slice 8, PR C2b-2)" (PR C2b-2, one OTel trace across the process boundary)*

- **Anthropic prebuilt skills — operator-imported, date-versioned** — The reference hosts its prebuilt skill catalog itself (short-name ids `docx`/`pdf`/`pptx`/`xlsx`, date-based versions); a self-hosted platform has no Anthropic-run catalog to reach, so the controlplane's run-once `-import-anthropic-skills` mode provisions them instead: the operator points it at a local checkout of github.com/anthropics/skills, each directory is validated exactly like an upload, and rows land as `source='anthropic'` with the SKILL.md name as the id and the checkout's last commit date (`YYYYMMDD`, `-import-version` overrides) as the version — this platform mints those versions; the reference's own version values for the same skills will differ. `display_title` is likewise set to the short-name id (`xlsx`, not a marketing name) — the reference's actual `display_title` for these skills is unrecorded and may be human-readable. - **Skills materialization — sentinel idempotence instead of the reference's re-extract-every-item** — The reference re-downloads and re-extracts every skill each work item, clearing each destination and removing `{workdir}/skills` at the end, its workdir being host-shared; our per-session sandboxes instead keep a `.materialized` marker — the resolved `{skill_id: version}` set (never the landing directory) plus an integrity generation (`skills.SentinelVersion`, now 2 = every recorded archive was digest-verified where a digest existed) — and skip rewriting only when the marker is of the current generation, is an exact bijection with the freshly resolved set, and every skill's directory still holds its SKILL.md; a marker of a weaker generation never satisfies a stronger pass (one re-materialization per live sandbox at upgrade). The agent-writable workdir means the marker is never trusted for anything load-bearing, and three tampering residuals are accepted rather than closed by abandoning the skip as the reference's every-item re-extract does, which clobbers such edits every item: an in-place content edit; a partial deletion leaving the root SKILL.md the probe checks as a proxy for the tree; and — the landing directory being the skill *name*, shared across versions — a forged marker version over an older version's files, suppressing that one in-session upgrade. All three are one irreducible class rather than three unfixed bugs — an agent that controls the sandbox filesystem can always present chosen bytes under `skills/<name>/` — each persists only until the resolved set changes, and none reaches past the agent's own single-tenant session. We also rewrite in place without first clearing the directory (the sandbox seam has no delete primitive), so a file dropped between versions can linger as an orphan beside the new version's complete set — accepted, our workdir never being shared. The read verifies the archive against the sha256 recorded at upload — a further divergence from a reference that records and checks none — refusing a bit-rotted, truncated or substituted object; the mismatch is skipped per-skill under its own `corrupt` outcome (beyond plan 06's ok/not_found/failed) and a version predating the digest column is read unverified. Extraction takes zip only (the reference's tar fallbacks are dead code here) and, like the reference since v1.63.0, materializes only regular files and directories — a Unix-host symlink, FIFO or device entry is skipped, never written out as a file holding its link target (skillarchive.go zipEntryIsPlain; TestExtractSkipsNonPlainEntries); three further deltas are defensive, unreachable for archives we validated: duplicate references dedupe first-wins (the reference, re-extracting each, is last-wins); an unusable version name falls back to the skill id (the reference tries `filepath.Base` first); traversal/backslash/relative segments are refused outright, where the reference absorbs them at the extraction root. Shared with the reference, not a divergence: both name the directory after the version's name, so two skills whose names collide overwrite each other under `{workdir}/skills/{name}/`. *Evidence: anthropic-sdk-go tools/agenttoolset/skills.go (RemoveAll+extract, Cleanup, filepath.Base), skillarchive.go (tar); internal/executor/skills.go, internal/worker/skills.go; the derivations cut from here are comments in internal/skills/extract.go (SentinelVersion, ParseSentinel, SentinelMatches, Resolved, MaxArchiveBytes), pinned by TestSentinel, TestSentinelMatches, TestReadArchiveVerifiesDigest, TestExtractRefusals, TestTargetDir, TestMaterializePreVerificationSentinelIsNotTrusted* *Tracked: #54.*

- **Sandbox disk cap — Kubernetes only, because Docker cannot enforce one honestly** — `sandbox.Hardening.EphemeralStorageBytes` (default 0, off) is applied by the Kubernetes backend as an `ephemeral-storage` limit *and* an equal request, and **ignored** by the Docker backend, which warns once per provider that the cap is unenforceable. Mirror of the pids row above, different cause: the Engine API *does* define `HostConfig.StorageOpt`, so this is not an absent field but one whose enforcement is conditional on the daemon's storage driver — some enforce it, some refuse the option outright, and Docker Desktop's `overlayfs` accepts it and enforces nothing at all (only the last is measured here; the rest are documented) — so the platform reports no cap it cannot vouch for. Failing `Provision` when it is set was rejected, the pids entry's reason inverted: this knob is off by default, so an operator who set it should be told it did nothing, not lose their executor. It is opt-in on Kubernetes for a sharper version of the memory cap's reason: a CPU or memory bound throttles or kills the process, this gets the whole **pod evicted** by the kubelet, taking the session's sandbox with it mid-call. - **Vault placeholders — `vltph_` opaque tokens, ours to mint (plan 12 D4)** — The sandbox-visible stand-in for an environment-variable vault secret is an "opaque placeholder" the reference defines no format for; we use `vltph_`-prefixed tokens (the prefix plus 128 bits of hex). The resource's actor fields diverge for a harder reason: the reference renders `created_by` and `principal` as `{"id": "user_…", "type": "user"}`, and this platform has no `user_` id to give, because sessions and credentials here are deliberately not bound to an end user (design principle 5). `created_by` therefore renders `{"id": "principal_…", "type": "principal"}` for a human who issued the key over SSO, `{"id": "apikey_…", "type": "api_key"}` for a machine credential that did, and `null` for the key seeded from `CONTROLPLANE_API_KEY` — which nobody issued. `workspace_id` and `principal` are emitted `null`, which is mirroring rather than reserving-by-guess: both came back null on the reference's own single-tenant account, so [#56](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/56) can populate them without a shape change. *Evidence: the created-resource capture in [#378](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/378); `internal/api/consoleapikeys.go`.*
- **A key seeded from `CONTROLPLANE_API_KEY` is listed but not console-mutable (plan 32 slice 2)** — The console lists every management key, including the one the environment variable seeds — hiding the credential the caller is authenticating with would misdescribe what can reach this API — but `POST …/api_keys/{id}` refuses to change its status or its name, naming the variable in the 400. The reference has no analog to diverge from: it has no env-var-managed credential class. The rule is ours and it is structural. That row's lifecycle already has an owner, rotation-by-restart, so a console disable would be silently undone by the next boot; and renaming it would break that rotation outright, since `EnsureAPIKey` archives the incumbent **by name** — a bootstrap row renamed out from under it would survive the next rotation and leave two live credentials under one name, which is precisely the race `api_keys_one_live_unissued` exists to prevent. *Evidence: `internal/api/consoleapikeys.go`'s `updateAPIKey`; `TestAPIKeyUpdateGuardsTheEnumAndTheEnvManagedRow`, whose negative control observes the control plane's own key 401 once the guard is removed.*

- **The lifecycle refusals say the same thing in different words (plan 32 slice 2, measured by [#389](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/389))** — The two state guards on `POST …/api_keys/{id}` now match the reference's *behaviour* exactly, and deliberately not its *wording*. Where the reference answers `"Archived API keys cannot be updated."` and `"Expired API keys can only be deleted, not renamed or reactivated."`, this platform answers `"api key <id> is archived, and an archived key cannot be updated"` and `"api key <id> has expired; an expired key can only be archived, not renamed or re-activated"`. - **MCP credential matching — what the normalization sentence does not reach (plan 29 slice 5)** — The documented rule is implemented verbatim: "scheme and host lowercased, default ports and trailing slashes stripped … a different path, subdomain, or non-default port does [prevent a match]". Everything the sentence does not name — path case, query, fragment, userinfo — is compared as given. Three readings it leaves open are ours, all settled toward *not* matching, since a false match sends a token to a server the credential was not registered for while a false miss dials unauthenticated and surfaces as an error: exactly one trailing slash is stripped; an IPv6 zone identifier is not folded, and host case is folded as ASCII only, because Unicode folding maps `İ` onto `i` while Go resolves the two to different DNS names; and a tie between two spellings inside one vault is broken by credential id. Two normalizations the sentence does not name are ours and go the other way, because net/http applies them to the request itself so the two spellings reach one origin: an empty port (`host:`) is dropped, and a default port is compared as a number, so `:0443` is `:443`. Also ours: a vault that matched but whose credential cannot be used does not fall through to a later vault — the documented rule is about which vault *matches*. And the "no match dials unauthenticated" wording has one exception this platform does not close: an `mcp_servers` URL written with userinfo authenticates with the Basic header net/http derives from it, matched credential or not; a matched credential replaces that header rather than joining it, so the configured, rotatable one wins. *Evidence: platform.claude.com/docs/en/managed-agents/mcp-connector ("Provide authentication at session creation") and /vaults ("Runtime behavior"), fetched 2026-08-14; internal/vaultresolve/mcpurl.go, internal/vaultresolve/mcp.go and their tests.* *Tracked: #45.*

- **Which failures are authentication failures (plan 29 slice 5)** — The two error types and their causes are documented; the **test** is not. This platform reads an authentication failure as 401 or 403 on the operation's most recent exchange, and nothing else — 407 is a proxy's status, not the server's. Two rules make "most recent" precise, both ours: the streamable transport's teardown `DELETE` is excluded, since it is sent after the operation has already failed and its success would erase the refusal that caused it; and an exchange that produced no response at all clears the flag, since a transport failure after a refused probe is a connection that failed. Both matter because the go-sdk opens every connection with a `server/discover` it recovers from on any error. That covers the reference's first two causes together, since a server answers alike whether a token was sent or not. It is observed in this platform's own transport chain because the go-sdk carries the status only as prose (v1.7.0 `mcp/streamable.go`, `checkResponse`), which a version bump may reword. A fourth cause is ours with no wire counterpart: a credential that matched and could not be resolved is an authentication failure and the dial is not made — an anonymous dial the operator believes was authenticated would hide the misconfiguration. `retry_status` is `retrying` for both types, per the connection-failure entry above. *Evidence: platform.claude.com/docs/en/managed-agents/mcp-connector ("Handle connection and authentication failures", fetched 2026-08-14); internal/mcp/authstatus.go, internal/executor/mcpcred.go, internal/executor/mcpexec.go (mcpFailure) and their tests.* *Tracked: #45.*

- **OAuth refresh — when it runs and what a failed one means (plan 29 slice 5b)** — That refresh is platform-performed, and its grammar (RFC 6749, the three `token_endpoint_auth` arms, RFC 8707 `resource`), are documented; when it runs and what happens when it fails are not. Ours: at the dial, and only there — a credential is refreshed when its `expires_at` is past or within a minute of it, never in reaction to the server's 401, so one expiry costs one exchange rather than a refused call and a retry. The minute absorbs both the skew that makes `expires_at` approximate and the flight time of the dial it is about to authorize. An expired credential that *cannot* refresh — no refresh block, no refresh token — still sends the token it has, since `expires_at` is the issuer's estimate and not its decision; that is the reference's `no_refresh_token` shape carried onto the dial path. A refusal from the token endpoint is `mcp_authentication_failed_error`, and so is every other way a 2xx fails to yield a grant — an error document, a body that never finished, one past this platform's 1 MiB cap — and an endpoint at an address the dial guard will not dial. None of those is a retry away from working, and a retryable verdict on them has nowhere to surface: the work item faults, is reclaimed, writes no catalog row, and repeats with the operator told nothing. What does retry is the issuer having a moment: unreachable, 5xx, or one of the three 4xx that are about timing rather than the grant (408, 425, 429). The shape is the `invalid`/`unknown` split the `mcp_oauth_validate` probe makes, with two deliberate departures: those three named 4xx, because a probe's verdict is advice an operator reads while this one settles a tool call for good, and the guard refusal, which the probe reports as a plain connection failure on purpose so it cannot become an internal-host oracle. Rotation is stored under a compare-and-set on the ciphertext the resolution read, best-effort: the dial uses the token it was issued whether or not the write lands, and a refusal that follows another resolution's rotation — the row's sealed bytes having changed under this dial — reads that rotation back instead of reporting a failure, which is what keeps an issuer's single-use refresh tokens from turning a concurrent dial into a permanent error. **One dead end is accepted**: a grant that names no lifetime — or one so long this platform will not believe it — stores a null expiry rather than keeping one already in the past, which would refresh on every later dial; that credential then gets no further proactive refresh, and recovering after the server refuses its token needs the operator, because nothing here refreshes in reaction to a 401. *Evidence: platform.claude.com/docs/en/managed-agents/vaults ("Runtime behavior", fetched 2026-08-14); internal/oauthrefresh, internal/vaultresolve/mcprefresh.go and their tests.* *Tracked: #45.*

- **Resolved toolset-config echo — what `configs[]` holds, and when it resolves (plan 29 slice 1)** — That the echo *is* resolved is documented, not inferred: the SDK marks `configs`/`default_config` and every `enabled`/`permission_policy` under them required on both toolset kinds' response types (three it calls "Resolved"), and the MCP-connector guide gives the two kinds one shape. - **MCP client transport — Streamable HTTP only, no HTTP+SSE fallback (plan 29 slice 2)** — `internal/mcp` speaks Streamable HTTP and nothing else. What is documented: the 2026-07-28 spec classifies the separate HTTP+SSE transport of 2024-11-05 as **Deprecated** — "New implementations SHOULD NOT adopt it … It is eligible for removal in a future revision" — while also giving clients that want to reach older servers an exact detection procedure ("If it fails with HTTP status code `400 Bad Request`, `404 Not Found`, or `405 Method Not Allowed` **and** the response body is not a recognized modern JSON-RPC error … Issue a GET request to the server URL, expecting … an `endpoint` event as the first event"). Both halves are quoted here because they pull in opposite directions and the choice between them is ours: the fallback is split out of the client rather than shipped with it, so until it lands, a server that hosts *only* the deprecated endpoints is unreachable and surfaces as an ordinary connection failure. Nothing is silently degraded — the SDK negotiates every protocol version from 2024-11-05 up **over Streamable HTTP**, so an old server that hosts the modern endpoint is reached today, and only the transport-level fallback is outstanding. Two smaller readings ride along. The standalone SSE stream is **disabled** (`DisableStandaloneSSE`): 2026-07-28 removed the GET endpoint it used, and a per-work-item connection asks one question and closes, so it has no use for a server-initiated stream in any revision. Against a *modern* server the setting is a no-op — go-sdk v1.7.0 returns before opening the GET whenever the negotiated version is 2026-07-28 or later — so what it actually governs is an older negotiation, where the spec makes the GET optional and a `tools/list` answer arrives on the POST regardless — which is what the contract suite exercises rather than a case it cannot reach, since go-sdk serves 2026-07-28 only from a stateless handler and every fixture therefore negotiates 2025-11-25; a test counts the standalone GETs. Whether the reference's client opens one is unobserved. And the client identifies itself to servers as `managed-agent-platform` with no version; the reference's client name is unobserved, and an operator reading their server logs sees ours. *Evidence: modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http § "Backward Compatibility" and § "HTTP+SSE Transport (2024-11-05)" (fetched 2026-08-08); internal/mcp/mcp.go (Connect); internal/mcp/mcp_test.go* *Tracked: #45; the fallback itself is #348 — it is named by plan 29's architecture but by no slice, so #45 closing at slice 4 would otherwise leave it untracked.*
- **The dial-address floor — what a customer-URL connection may reach (plan 29 slice 2)** — Three production paths resolve a host a customer named, and all three go through `internal/dialguard`: the vault-credential validate probe, the MCP client's `DefaultClient` (which the executor's discovery driver selects by supplying no client of its own), and the executor's dial-time token-endpoint refresh, which redials long after the probe last vetted the address. The guard refuses loopback, link-local (cloud metadata), the unspecified address and multicast on the **resolved** IP of every dial, and re-checks the embedded IPv4 target inside six specification-fixed IPv6 transition forms; an address it cannot read at all is refused rather than admitted, so the natural `IPAllowed(net.ParseIP(host))` call shape cannot fail open. **None of this is reference behavior**: the reference documents reachability but no per-address policy, and a refusal on its side would be indistinguishable from an ordinary `mcp_connection_failed_error` — so both the list and its consequence are ours. **RFC 1918 is deliberately allowed**, the reading most likely to look like an omission: this platform is self-hosted by premise, so an MCP server on the operator's own private network is the normal case, and this guard is the floor beneath an agent's egress policy rather than the policy itself. Two neighbouring dials are deliberately *not* behind it, and reading the guard as universal misplaces both — the `github_repository` clone is pinned to the literal `github.com` by a create-time grammar rather than an address check, and the per-session egress gate is governed by the environment's network policy. The decoding is hardening on the one prefix an attacker can count on being routed, not a general answer to NAT64: a Network-Specific Prefix carries nothing that marks it as one, so a deployment translating through its own space gets no decoding, and the over-refusal this costs is real, ranges from 0% to total depending on the deployment's prefix bytes rather than only its length, and is fail-closed by choice. *Evidence: internal/dialguard/dialguard.go, whose comments carry the whole derivation this entry used to duplicate — which six forms are decoded and why, the RFC 6052 six-candidate read and the padding skip that makes it usable, the RFC 8215 §5 sentence that argues against the decoding and why a guard deciding a refusal is not a node forwarding a packet, the measured over-refusal figures, and the RFC 2529 6over4 omission taken by decision rather than oversight; internal/dialguard/dialguard_test.go pins each class and form; internal/api/vaultvalidate.go (the overridable probe seam), internal/mcp/mcp.go (DefaultClient), internal/executor/mcpwork.go (the driver that selects it).* *Tracked: #45.*
- **MCP tool listing — what a malformed entry becomes, and the ceilings the protocol does not set (plan 29 slice 2)** — The reference makes its MCP connection server-side, so the exchange is invisible from the wire and only its outcomes are (`agent.mcp_tool_use`/`agent.mcp_tool_result`, and typed `mcp_connection_failed_error`/`mcp_authentication_failed_error`). Every reading here is therefore ours. An entry the platform cannot faithfully hand a model is **skipped**, never fatal to the listing — one bad entry must not deny an agent the rest of a catalog: an unusable name (empty, over 128 bytes, or outside `[A-Za-z0-9_.-]`, the SDK's own `validateToolName` charset rather than a guessed Anthropic rule), an `inputSchema` that is absent, null, not an object, or whose root `type` is not `"object"`, and a duplicate name (first wins — a malformed first entry leaves the name free, because the name is recorded after the schema check). A repeated pagination cursor **fails** the listing rather than looping; every cursor seen is remembered, not just the previous one. Five ceilings are platform policy and not protocol, which sets none: 100 pages, two minutes per listing, 30 seconds on any request the SDK detaches from the caller's context, 64 KiB on a single response's header block — the one a *legitimate* server can hit — and 8 MiB **accounted** across a connection, which is not the same as delivered: bodies count in full but header blocks only as far as they survive parsing to be counted, so the bytes actually on the wire can far exceed it (measured once at 91.8 MB against 3,900 bytes charged). Two readings are forced by the SDK's typed surface rather than chosen: a successful result carrying no `tools` field is recorded as "this server has no tools" rather than as malformed, and an empty-string cursor ends the listing — a real divergence from the pagination spec, which says an empty cursor is valid and MUST NOT be treated as the end, for a case no known server exercises. `"tools": [null]` panics go-sdk v1.7.0 and is recovered at the call site, because the executor is shared by every session on the host. *Evidence: internal/mcp/mcp.go — ListTools, listPage, usableName, inputSchema, limitedTransport, headerBytes, and the constants ListTimeout, maxToolPages and maxHeaderBytesPerResponse, each carrying its own rationale, its measured boundary, and the record of the ceilings this entry published and had falsified (mcp.go:744-769, including the rule that came out of it: do not multiply by a quantity nothing bounds); internal/xcontext/xcontext.go + mcp/streamable.go (the detached-context close the 30-second bound covers); internal/mcp/mcp_test.go drives every boundary from both sides; MCP 2026-07-28 server/utilities/pagination; go-sdk v1.7.0 mcp/tool.go, mcp/server.go, mcp/protocol.go.* *Tracked: #45.*
- **MCP-client egress and the tool catalog — what the reference leaves unobserved (plan 29 slice 2)** — The reference pins four things (that `limited.allow_mcp_servers`, default false, additively admits "MCP server endpoints configured on the agent"; that networking exists on **cloud** environments only; that session creation validates no MCP connectivity; and that a failed connection is "retried on the next `session.status_idle` to `session.status_running` transition") and leaves the rest unobservable, since its MCP exchange is server-side. **Where the policy is enforced is ours**: the platform dials from the executor's own process, structurally outside the per-session gate, so `limited` binds at that dial or nowhere — and before it, never after, since a refusal that still opened the connection would already have told the server the session exists. Reading a documented *sandbox-egress* field as also governing the platform's own dial is our reading, and the one that gives it something to admit. **The policy's type decides, not the environment kind**: a `self_hosted` config carrying a networking block is one the REST surface cannot have written, so it came from an import or a hand-written UPDATE and is a policy somebody meant; an unrecognized type **refuses**, matching `gate.newPolicy`'s fail-closed direction, because the schema constrains `config->>'type'` but leaves `config->'networking'` alone and a config-preserving update carries a stored value forward unvalidated. A block naming no type reads as no policy — the one corner this cannot distinguish, since `domain.Networking` is a value struct — and it adds no reach a hand-written `unrestricted` would not. **The catalog** is a per-session snapshot keyed `(session_id, server_name)` — `(session_id, thread_id, server_name)` since plan 35 slice 3, each thread discovering its own agent's servers — rather than a URL-keyed cache, because two sessions may reach one server with different credentials and see different tools. Its row is the retry state, and the three states are ours: absent means never reached, `failed` is re-attempted next work cycle, `ready` is offered and not re-fetched. **Nothing disables a server for the rest of a session** — no source documents such a state. A `ready` row is matched on url as well as name, and rows an agent patch no longer declares are deleted in the patch's own transaction; the url comparison and a settle-time re-read under the session's row lock are deliberate redundancy against a missed or overtaken delete. **A server that cannot be reached is a row, not a fault** — an unreachable endpoint, a non-http(s) url, a policy refusal, and a server the pass's time budget did not reach all land as `failed` and the turn chains anyway, since faulting would reclaim-loop against a server that is simply down. Failures surface as `mcp_connection_failed_error`, or `mcp_authentication_failed_error` where a credential was refused (the connection worked well enough to be refused), **once per work cycle** rather than once per turn — a cadence that falls out of the row rather than being imposed. Two failed rows say nothing: one the pass timed out on, and one whose url is not http(s), since nothing was dialled. **What a row may hold is bounded by this platform, not the protocol**: a reason at 2,000 bytes, a listing at a quarter-megabyte with tools past it dropped whole. Slice 6b made the dials concurrent — declaration order never was a fact about a server, and serially one slow server kept those behind it out of the catalog for the session's life — while credential resolution stays serial, because an OAuth refresh run twice on one token can make an issuer revoke the family. - **Answering an MCP call — the execution locus, the result's blocks, and a failure's two halves (plan 29 slice 4)** — The reference's MCP exchange is server-side, so only the event pair is observable and everything between the two events is ours. **Locus**: the platform's own executor answers every MCP call on **every** environment kind, `self_hosted` included, because a BYOC worker's contract has no MCP surface — which makes MCP's precedence over the built-ins a correctness rule rather than a preference, applied at all six settlement sites. **A tool that ran and failed is a result, not a fault**: MCP asks servers to report it as an ordinary `is_error` result so the model can self-correct, and making it a work-item failure would reclaim-loop against a tool that fails identically every time. **A server that refuses is not a connection that failed** — an unknown tool, an `input_required` answer, unusable blocks, or a value that will not re-marshal all arrive over a working connection; the client marks server-answered errors (`ErrServerAnswered`) as a boundary rule rather than a list of cases. **A call that never reached its server produces both events**: an `is_error` result so the turn continues and replay stays valid, plus a `session.error` naming the server so an operator sees a connection to heal. Its `retry_status` is **always `retrying`** — plan 29 specified `terminal` for an egress block and that is corrected here, because the union describes the *session* and this session neither terminates nor flushes; an operator can also widen `allowed_hosts` mid-session and heal the refusal. Messages are cut to `scheme://host`, since an `mcp_servers` entry may carry a credential. **Content blocks**: MCP's five types and the event's four do not correspond, so text and image translate, an embedded resource becomes a `document` titled with its URI, a resource link becomes text (never a url source, which would have the model's side dial an address this platform never vetted), audio is described rather than dropped, anything else is dropped, and an answer rendering to nothing gets one text block saying so. What a block may declare is the **intersection** of the event schema and the Messages schema the brain replays into — a block this platform can store but never send again fails every later turn on a log that cannot take it back. **Budgets are ours**, neither MCP nor the reference setting either: 100 KiB (`toolset.MaxOutputBytes`) charged per marshalled block, kept or dropped whole, with a trailing block naming what went and one exemption for a block whose text was already capped; and two minutes (`toolset.DefaultTimeout`) bounding the whole call, not one request. The execution pass is bounded as a whole too, by `EXECUTOR_MCP_PASS_TIMEOUT` (five minutes, operator-settable through Helm and compose) — checked *between* calls and never cancelling one, so its first call is always made; the reference documents no such limit either. No at-most-once guarantee is offered, because MCP has no idempotency key and the reference documents none. *Evidence: internal/executor/mcpexec.go and internal/mcp/calltool.go carry the reasoning beside the code; the claims above are each pinned by a named test in internal/executor/mcpexec_test.go, mcpwork_test.go, internal/mcp/calltool_test.go and internal/api/confirmation_test.go — the test names state the rules (TestMCPToolFailureIsTheModelsToRead, TestMCPProtocolFailureIsNotReportedAsAConnectionFailure, TestMCPBlobResourceRidesOnlyABlockTheWireCanCarry, TestMCPExemptionFollowsTheCappedBlockNotThePosition, TestToolResultResumeSchedulesAnOutstandingMCPCall, and the rest); anthropic-sdk-go v1.63.1 betasessionevent.go and betamessage.go for both schemas; modelcontextprotocol.io § tools for is_error's rationale.* *Tracked: #45.*

- **Offering an MCP tool to the model — the name it is given, the ways it can be lost, and the turn that waits (plan 29 slice 4b)** — The reference gives the model a **bare** tool name with the server in a field of its own (`agent.mcp_tool_use` has `name` and `mcp_server_name`), and no prefix convention is documented anywhere — `mcp__` appears in neither the SDK nor the `ant` CLI. This brain assembles one flat `tools[]` for an ordinary Messages endpoint, which carries a name and nothing else, so `mcp__{server}__{tool}` is **ours and forced by architecture**: without it two servers offering `search` would be one name and a call would be unattributable. It is confined to the provider request — the committed event carries the bare name and `mcp_server_name` as the SDK types them, and replay reassembles the pair so every later turn re-sends a name that turn actually offered. The composed name must fit `^[a-zA-Z0-9_-]{1,64}$` while the mcp-connector page documents a server name of 1–255 characters and an `mcp_toolset` `configs[]` name of 1–128 — both Anthropic's bounds, `configs[]` having no existence in the MCP protocol at all, so a pair legal on both wires can compose into one the endpoint rejects — and it would reject the whole request, every turn, forever. Bytes outside the class are **mangled to `_` one-for-one** rather than dropped, so the length checked before composition is the length produced. **Five ways a declared tool goes unoffered, each costing only its own tool and each a log line**: a name too long to compose; a name already taken (the agent's own `tools[]` wins over a third party's, and flattening is not injective, so two servers or two mangled names can collide — declaration order settles all three, and the reference publishes no separator to escape); a server whose listing failed or has not happened; a `configs[]` entry naming a tool the server does not report (the only one the docs settle — it warns without erroring); and a definition past the 256 KiB of MCP definitions one request carries. Two further drops are **silent by design** — a nameless tool and a repeated name are already refused where a listing is read, so warning about them would be noise about a state that cannot arise. The reports are log lines, not events, bounded at sixteen per turn; plan 29 proposed a `system.message` and that is corrected here, since the event is client-sent and replays into the system prompt, which one per turn would grow without bound. **A turn waits for a listing it has never had** (no model call; the item is handed back and the discovery driver chains the turn), while a *failed* row is an answer rather than an absence — the turn runs without that server. Failed rows are deleted on an idle→running transition, matching the reference's documented "retried on the next transition" cadence. An outstanding call is dialled only where its listing was read and only while the agent still declares the server there, since `mcp_servers` is mid-session-mutable and dialling a new address would ask a different party a question it never advertised. A name the model was not offered is treated as **client-executed** rather than run. `session.error` messages are bounded, since every string one is built from is capped nowhere it is stored. The agent's own tools are laid down before the MCP ones, which makes the collision rule decidable in one pass; ordering within `tools[]` is unobservable on the reference. An MCP call gates as an ordinary ask tool (`DefaultMCPToolsetPolicy` is `always_ask`), and one work item is enqueued per suspended turn at the highest kind its calls demand — `mcp_exec` over `web_exec` over `tool_exec`. *Evidence: internal/brain/mcptools.go, internal/brain/replay.go and internal/toolset/mcp.go carry the reasoning beside the code; roughly thirty named tests pin the rules individually across internal/brain/mcptools_test.go, mcpturn_test.go, internal/api/mcptoolset_test.go, internal/executor/mcpexec_test.go and internal/toolset/mcp_test.go — the names state the claims (TestTwoToolNamesThatSanitizeAlikeContestOneName, TestAFailedListingRunsTheTurnWithoutThatServer, TestWakingASessionRetriesItsFailedMCPListings, TestMCPCallForARepointedServerIsNotDialledElsewhere, and the rest); platform.claude.com tool-use "Define tools" for the name regex, the mcp-connector guides for the bare-name shape and the two bounds; anthropic-sdk-go v1.63.1 betasessionevent.go and betamessage.go.* *Tracked: #45.*
