# DIVERGENCES.md — wire divergences & unconfirmed inferences

The single registry of (a) **deliberate divergences** from the Anthropic Claude
Managed Agents reference and (b) **inferences** about reference behavior made where
neither the SDK types nor the `ant` CLI can reveal it — each to be confirmed against a
real managed-agents recording. The verifier's wire-compat rung resolves intentional
mismatches against this file; an intentional mismatch missing here is a defect. New
divergences land here in the same PR that introduces them.

Format: **surface** — behavior. *Evidence.* Three sections: architecture/compatibility notes (not mismatches), CONFIRMED deliberate divergences, and INFERRED assumptions (each cross-linked to the issue tracking its confirmation).

## Architecture & compatibility notes (not divergences)

Facts that read like divergences but are not mismatches with the managed-agents wire —
recorded here so the allowlist stays honest.

- **Session resource (all session endpoints) — end-user binding** — Sessions carry no user_id field at all. Scoping keys are org/workspace/project (reserved, single-tenant defaults in v1); end-user-to-session ownership is an application-layer concern via session metadata and the audit-only created_by. This is a deliberate architectural divergence (explicitly from adk-go's AppName+UserID pattern; the platform stays user-agnostic). *Evidence: CLAUDE.md 'Non-negotiable design principles' #5; docs/history/2026-07.md § "`internal/store` — Postgres schema + migrations" (sessions schema: 'audit-only created_by, no user_id'); CLAUDE.md standing product decisions*
- **GET /v1/sessions/{id}/events/stream — SSE preview delta frames** — Streaming preview deltas use type 'content_delta', never the Messages API's 'content_block_delta'. event_start/event_delta frames are stream-only, never persisted, and reconcile under the buffered event's pre-allocated id. *Evidence: CLAUDE.md 'Wire-compatibility rules'; docs/history/2026-07.md § "`internal/events` + events API — append-only log, send/list, SSE stream (slice 3)" (events/preview.go: 'delta type is literally content_delta, NOT the Messages API's content_block_delta')*

The reference's own timeout policy is unobservable: the SDK types carry none and no recording shows one. This is therefore a platform-side operational bound rather than a claim about the reference — the hosted reference bounds its own fixed backend however it likes, while a self-hosted deployment points at arbitrary endpoints and must not let one wedged proxy hold a brain replica out of service (#121). *Evidence: docs/plan/17_model-endpoint-stall-bound.md; internal/provider/stall.go (StallGuard); docs/HISTORY.md § "Model endpoint stall bound (plan 17)"; see also the session.error retry-semantics inference below (#78)*

- **Skills materialization — sentinel idempotence instead of the reference's re-extract-every-item** — The reference worker re-downloads and re-extracts every skill on every work item and removes `{workdir}/skills` when the item finishes, because its workdir is host-shared across sessions; this platform's sandboxes are per-session, so both halves instead write a `.materialized` sentinel recording the resolved `{skill_id: version}` set (only — the landing directory is deliberately **not** stored) plus an **integrity generation** (`skills.SentinelVersion`), and skip rewriting only when the marker is of the current generation **and** its set is an exact bijection with the freshly resolved set **and** every skill's directory still carries its SKILL.md. The generation states what a recorded materialization was actually guaranteed to have done — generation 2 means every archive was verified against the digest the registry holds for it, where one was recorded (a version predating the digest column has none, and is read unverified) — so a marker written under a weaker guarantee (the unversioned array form, written before digests existed) can never satisfy a stronger pass: without it, a sandbox populated by a pre-verification binary would keep matching and suppress digest verification for the rest of that session, which on a long-horizon session is a long time. It costs exactly one re-materialization per live sandbox at upgrade and nothing at steady state; recording the digests in the marker instead is not viable, because the BYOC worker learns a digest only from the download response — after the skip decision — and would have to spend a wire round trip per skill per pass to answer what the generation answers for free. A marker from a *newer* generation is likewise refused, so a downgraded binary re-materializes rather than trust a claim it cannot evaluate. Because the workdir is agent-writable the marker bytes are never trusted for anything load-bearing: the probe directory is recomputed each pass from trusted metadata (the executor's DB row / the worker's version GET), never from the marker, so a tool call that rewrites the marker cannot redirect the presence probe at a decoy directory, and — via the exact marker↔resolved-set bijection (equal length, each id once with its version) — cannot use a forged, duplicated, or zero-value entry to mask a skill that is absent from its directory; a removed SKILL.md is healed on the next pass. What the skip does **not** defend against is content-level tampering behind a present SKILL.md, since the probe tests presence, not content — three residuals persist until the resolved set changes: an in-place content edit of any materialized file; a partial deletion that removes a non-SKILL.md member but leaves SKILL.md (the presence probe checks the root SKILL.md as a tractable proxy for the tree, not every member); and — because the landing directory is the skill *name*, shared across a skill's versions — an agent that forges the marker's version to the newly-resolved one while leaving an older version's files in place, suppressing that one in-session upgrade. All three are the same tampering class (an agent that controls the sandbox filesystem can always present chosen bytes under `skills/<name>/`), none grants reach beyond the agent's own single-tenant session, and closing them would mean abandoning the skip to re-extract every pass as the reference does; all are accepted. The reference's re-extract clobbers such edits every item. A rewrite overwrites in place without clearing the skill's directory first (the sandbox seam has no delete primitive), so a file dropped between versions can linger as an orphan beside the new version's complete set — accepted; the reference clears because its host workdir is shared across sessions, which ours never is. The archive is read from object storage / the download stream under a compressed-size byte cap (`skills.ReadArchive`, set above the 30 MB upload limit but far below the gigabyte decompressed ceiling) into a buffer whose capacity is hard-clamped at that cap, so a corrupt or oversized stored object is refused before it can OOM either half and never provokes a gigabyte-scale allocation; extraction's own decompressed guard then bounds what a valid archive expands to. The same read then verifies the bytes against the sha256 the registry recorded at upload — a further divergence from the reference, which records and checks no digest at all — refusing an archive that bit-rotted, truncated, or was substituted in object storage; the mismatch is skipped like any other per-skill miss (under its own `corrupt` outcome) rather than faulting the run, and a version predating the digest column records none and is read unverified. Extraction accepts zip only: the reference's tar fallbacks are dead code against a platform that stores and serves canonical zips. Three further harness-behavior deltas, all defensive and unreachable for archives this platform itself validated: duplicate skill references dedupe first-wins (the reference re-extracts every entry, effectively last-wins); a version name unusable as a path segment falls straight back to the skill id (the reference tries `filepath.Base` first); and extraction refuses traversal/backslash/relative segments outright where the reference absorbs them at the extraction root. One limitation is shared with the reference, not a divergence: because both name the landing directory after the version's name, two distinct skills whose names resolve to the same directory would overwrite each other under `{workdir}/skills/{name}/` — accepted as reference-inherited. *Evidence: anthropic-sdk-go tools/agenttoolset/skills.go (unconditional RemoveAll+extract, Cleanup), skillarchive.go (tar paths); internal/skills/extract.go, internal/executor/skills.go, internal/worker/skills.go* *Tracked: #54.*

- **Oversized tool output — sandbox tools spill to a file (path and preview ours); web answers still truncate** — The reference's tools doc: "When a tool output exceeds 100,000 characters (about 25,000 tokens), it is automatically written to a file in the sandbox. The model receives a truncated preview with the file path and can read the full content from there." The sandbox tools now do the same (#226, docs/plan/18_spill-oversized-output.md): output past the per-call log budget (`toolset.MaxOutputBytes`, 100KiB) lands whole — NUL-sanitized — in the sandbox at `/tmp/tool_outputs/<tool_use_id>.txt`, and the preview keeps the head with a marker naming the file (`[output truncated; full output written to …]`); bash's failure arms spill before the exit-code/timeout trailer caps the body, so the tail exists when the trailer survives. Two shapes are ours, INFERRED — the reference documents the spill but neither its path convention nor its preview text (cross-linked from the INFERRED section below) — and one bound is honest: "whole" means everything `Sandbox.Exec` retained and returned to the toolset — its pre-existing per-stream memory guard (`sandbox.MaxOutputBytes`, 1MiB, unchanged) drains and discards the excess. A failed spill write falls back to the plain `[output truncated]` trailer, costing the call nothing. **`read` alone never spills**: its full content already sits at the very path the model just named, and a spilled copy would chain — every spill file exceeds the cap by construction, so reading one back would mint another copy under a fresh id with no fixed point; an oversized read truncates plainly, its tail reachable via `view_range` or bash slicing (a spill file holding one giant line has no breaks for `view_range` to cut and is reachable only by bash — accepted, still strictly better than the pre-change outright loss). The **web tools deliberately keep the old behavior**: `web_fetch` truncates with the plain trailer and `web_search`'s structured answer is pruned against the same budget with no marker (a snippet admitted whole or omitted, a hit whose title+URL alone exceed the remaining budget dropped) — their driver runs in the executor with **no sandbox provisioned** (plan 15's design), provisioning one solely to store a spilled answer would couple the web pass back into sandbox lifecycle, and web content, unlike a command's output, is re-fetchable. - **Sandbox process limit — Docker only, because Kubernetes has no per-pod one** — `sandbox.Hardening.PidsLimit` (default 512) is applied by the Docker backend as `HostConfig.PidsLimit` and **ignored** by the Kubernetes backend: the Pod API defines no pids resource — a per-pod process cap is the kubelet's `podPidsLimit` node setting, not a pod-spec field (k8s.io/api v0.36.2 `core/v1` has no such `ResourceName`; a pod under a 500m CPU limit on kind reads `/sys/fs/cgroup/pids.max` as the node default, measured). - **Sandbox disk cap — Kubernetes only, because Docker cannot enforce one honestly** — `sandbox.Hardening.EphemeralStorageBytes` (default 0, off) is applied by the Kubernetes backend as an `ephemeral-storage` limit *and* an equal request, and **ignored** by the Docker backend, which warns once per provider that the cap is unenforceable. This is the mirror image of the pids asymmetry above, but it does **not** have the same cause, and the difference is the point: the Engine API does define `HostConfig.StorageOpt`, so unlike a pids resource on a pod this is not an absent field — it is a field whose enforcement is conditional on the daemon's storage driver — and the daemons do not answer that condition the same way. btrfs, zfs and overlay2 over XFS with `pquota` can enforce it; classic overlay2 without `pquota` refuses the option outright; and Docker Desktop's `overlayfs` driver accepts it and enforces nothing at all. Only the last is measured here, on 29.6.2: `docker run --rm --storage-opt size=1G alpine:3 df -h /` exits 0 and the container's rootfs still reports the full 910.7 GB host filesystem, identical to the same run without the flag. So passing the cap through blindly fails two different ways depending on the daemon underneath — a refused provision on one, a security control that reports success and enforces nothing on another — and honouring it properly means reading the daemon's storage driver and branching on it, real work for a control this plan scopes to Kubernetes. Refusing to provision whenever the cap is set was rejected for the reason the pids entry gives, inverted — the knob is off by default, so an operator who sets it has asked for something specific and deserves to be told it did not happen, not to have their executor stop working. On the Kubernetes side the knob is opt-in, as the memory cap already is and for a sharper version of the same reason — memory is opt-in because an OOM kill mid-task beats the throttling a CPU quota causes, and this is opt-in because its enforcement is harsher still: exceeding a CPU or memory bound throttles or kills the process, while exceeding this gets the whole **pod evicted** by the kubelet, taking the session's sandbox with it — a platform-chosen default would silently convert a disk-hungry-but-honest tool call into a lost sandbox. The Kubernetes half is not unconditional either, and the caveat belongs with the cap rather than in a footnote: the kubelet measures local ephemeral storage only on the node layouts it supports (a single filesystem; a separate runtime filesystem; a split image filesystem), and on any other layout it "does not apply resource limits for ephemeral local storage" — the pod accepts the fields and exceeds them unevicted. What still fires there is node-pressure eviction, which is the arbitrary-victim outcome this cap exists to make targeted: a node short on local storage stops accepting new pods and the kubelet starts terminating running ones to reclaim space, chosen by usage against their requests and by priority — never by which pod filled the disk. Request is set equal to limit deliberately: the kubelet picks eviction victims by comparing usage against the *request*, so a limit the scheduler never reserved is a cap whose enforcement lands on whichever pod happens to be over its own request. The test asymmetry is structural rather than hidden, as with pids, but takes a different shape: there is no shared contract row at all, because no assertion made from inside a sandbox could observe this cap — there is no cgroup file to read and the enforcement action is the pod dying — so it is asserted at the provider level, exactly as the memory cap is (plan 19 decision 6). - **Vault credential create, update and `mcp_oauth_validate` (deployment-configured) — a `gcpkms` deployment bounds secret material at the key's ceiling: 64 KiB, or 8 KiB on an HSM key** — With `SECRETS_BACKEND=gcpkms`, credential secret material whose sealed JSON exceeds that bound is refused with a **400 naming the limit**, where the identical request on the identical build succeeds under the `local` or `openbao` cipher. - **Resolved toolset-config echo — what `configs[]` holds, and when it resolves (plan 29 slice 1)** — That the echo *is* resolved is not the inference: the pinned SDK marks `configs` and `default_config` required on the response types of **both** toolset kinds (`BetaManagedAgentsAgentToolset20260401`, `BetaManagedAgentsMCPToolset`), and required again on their members' `enabled` and `permission_policy` (`BetaManagedAgentsAgentToolsetDefaultConfig`, `BetaManagedAgentsAgentToolConfig`, and the MCP twins, whose doc comments read "Resolved …"), while the MCP-connector guide states the two kinds share one shape. An MCP server's tool names are unknowable when an agent is written (the guide makes an unknown name a warning, not an error), so enumerating them is impossible for that kind, and the built-in kind — whose eight names *are* enumerable, and whose per-tool `name` is an enum in the SDK — is held to the same rule rather than given a second one; whether the reference instead lists every built-in on an `agent_toolset_20260401` echo is unobserved. - **Turn classification — the tool blocks, not the stop_reason label** — A model response carrying tool blocks is a tool turn: the brain suspends on them whatever stop reason arrived with it (max_tokens, stop_sequence, model_context_window_exceeded, a non-compliant end_turn), and the tool intents it commits are enqueued and answered exactly as a tool_use stop's would be. **refusal is the one carve-out**: its blocks are dropped and the turn settles on its text alone. - **Request bodies, path IDs, and query parameters — U+0000 (and any unstorable byte) rejected before it binds** — U+0000 is a well-formed JSON escape — and, percent-decoded from `%00`, a real byte in a path or query value — that Postgres can store in neither a jsonb value nor a text column, so the only alternative to rejecting it is the 500 (`SQLSTATE 22021`/`22P05`) it becomes at bind time; it is rejected in the shape an absent or unknown value already carries, on three surfaces. (1) **Request bodies and inbound event payloads → 400:** a U+0000 anywhere in a JSON object body, key or value, is rejected by `decodeObject` on every endpoint that parses one — not only the metadata-accepting ones (agent / environment / session create and update, and the work-item metadata patch) the guard originally covered — as `internal/events` already rejects it in an inbound payload; this also covers *delete* keys, turning a previously-200 silent no-op (the Go-side merges for agents/environments/sessions dropped an unstorable key harmlessly while the identical patch 500'd against the work endpoint's SQL-side merge) into a 400, the one genuinely wire-observable choice, taken because preserving an asymmetry is not preserving a contract. (2) **Path IDs → 404, id-shaped query filters → 400:** a server-minted id is a known prefix plus a Crockford-base32 token, so anything else — a wrong prefix/alphabet or an unstorable byte — cannot name a stored row, and `domain.ID.Valid` rejects it on shape before the bind, as the 404 an unknown id gets on a path (agents / environments / sessions / events, the work `{work_id}`, and the worker session-read auth lane) and as a 400 on an id-shaped query filter (`agent_id`, the `page` cursor's decoded id). (3) **Free-form `types[]` → 400 on the unstorable byte only:** an unknown-but-storable event type filters to empty (the established behaviour), so only U+0000 / invalid UTF-8 is rejected there. The reference's own behaviour is undecidable from the typed schema — IDs are documented opaque server-generated strings, metadata a plain string map and every other field a plain string, and no `ant` CLI recording covers an unstorable byte — so whether it 400s, 404s, 500s, or strips is unknown; stricter-than-schema by storage necessity, flagged to confirm against a recording. - **The dial-address floor — what a customer-URL connection may reach (plan 29 slice 2)** — Two code paths resolve a host a customer named through `internal/dialguard`: the vault-credential validate probe (`auth.refresh.token_endpoint`, `auth.mcp_server_url`) and the MCP client's `DefaultClient` — so the MCP half is guarded for a caller that supplies no client of its own, which is what production does and what the field's own doc requires of a non-test caller. The vault-credential probe runs on a live API route; the executor's MCP discovery driver does dial through `mcp.Connect` with no client of its own — which is what selects `DefaultClient` and with it the guard — but nothing in production enqueues the `mcp_exec` item that runs it, so that arm is enforced in its tests and waits for the slice (plan 29 slice 4) that schedules discovery. The guard refuses loopback, link-local (cloud metadata), the unspecified address and multicast on the **resolved** IP of each dial, and re-checks the IPv4 target inside **six** IPv6 transition forms: NAT64 `64:ff9b::/32`, 6to4, Teredo, the RFC 4291-deprecated IPv4-compatible `::/96`, RFC 2765's IPv4-translated `::ffff:0:0:0/96`, and RFC 5214 ISATAP (the `00-00-5E-FE` interface identifier, which unlike the others rides *any* prefix and so is decoded in addition to them rather than as one of them — and of whose first octet only the `u` bit varies, since the group bit is not set on a unicast identifier; treating both as free, the natural reading of "u/g bits", refuses ordinary global-unicast addresses whose identifier happens to read `0100:5efe` or `0300:5efe`). An address the guard cannot read at all — nil, or the wrong length, which is exactly what `net.ParseIP` hands back for a host that is not an address — is refused rather than admitted, since every class predicate answers false for one and the natural call shape `IPAllowed(net.ParseIP(host))` would otherwise fail open. Six is not "every", and the omissions are of two kinds. 6rd embeds an IPv4 address at a position set by provider-assigned parameters an address does not carry, and the same blindness covers a NAT64 deployment on its own Network-Specific Prefix (below); both would need the guard told its deployment's parameters, which nothing does today. RFC 2529 6over4 is the other kind — left out by decision, so "every specification-fixed form is decoded" would be false. Its identifier is fixed (32 zero bits, then the IPv4 address), but that pattern is indistinguishable from the ordinary operator habit of writing a host part as `prefix::a.b.c.d`, and decoding it would refuse a measured **6.6%** of the addresses that habit produces — the same order as the NAT64 `/56` cost below, paid on a far more common address shape, for a mechanism that needs an IPv4-multicast-capable link and is effectively extinct. RFC 2529 §5 also lets the actual link-layer IPv4 address, learned through Neighbor Discovery, differ from the one in the identifier, so the decode would not be authoritative about where a packet goes even when it fired. Two neighbouring dials are deliberately *not* behind it, and reading the guard as universal would misplace both: the `github_repository` clone dials a URL from a session-resource row, but its host is pinned to the literal `github.com` by the create-time grammar (`parseGitHubRepoURL`) rather than by an address check, and the executor does not re-validate the stored URL before dialing; and the per-session egress gate opens sockets to hosts the agent itself names, filtered by the environment's network policy — the policy this guard is explicitly the floor beneath, not a part of. A NAT64 address yields **six** candidate targets, one per RFC 6052 §2.2 prefix length, because the address alone does not say which layout its deployment uses and reading only the low 32 bits is wrong in *both* directions. Admitting: under a `/48` prefix, `64:ff9b:1:a9fe:a9:fe00:808:808` carries `169.254.169.254` in bytes 6,7,9,10 while its low 32 read as `8.8.8.8`. Refusing: RFC 6052 puts the SHOULD-zero suffix in those same low 32 bits for every prefix length from `/32` to `/56`, so a low-32 reader saw `0.0.0.0` — the unspecified address, refused — instead of a target. For the layouts a deployment can actually use inside `64:ff9b::/32` that means `/48` and `/56`, whose suffix covers all four of those bytes, and the old guard refused **every** conformant mapping under both — `64:ff9b:1:808:8:800::` (a `/48` mapping of 8.8.8.8) included. (The `/32` and `/40` rows are arithmetic rather than deployments: RFC 6052 fixes the well-known prefix at `/96`, and the shortest prefix inside `64:ff9b::/32` an operator may use is RFC 8215's local-use `64:ff9b:1::/48` — from which a `/48`, `/56`, `/64` or `/96` translation prefix may be carved — so nothing maps legitimately at `/32` or `/40` here. The decoder tries them because an address cannot prove that.) Both directions are the same misreading and both are fixed here, which is why a candidate decoding to `0.0.0.0` is skipped as padding rather than refused: the change is additive against a *correct* one-layout reader, but not against the guard it replaced. What the skip admits back is a rule rather than a list: any address every one of whose non-padding readings is benign — `64:ff9b::` and `64:ff9b:1::`, prefix base addresses with no target and nothing listening, and equally `64:ff9b:1::808:808`, whose `/48` reading is padding and whose `/96` reading is `8.8.8.8`. It is not confined to NAT64 either, since the skip is not: a 6to4 wrapper under `2002::/32`, a Teredo address whose low 32 bits are all-ones, and an ISATAP identifier carrying `0.0.0.0` are admitted the same way and are wrappers around no target in the same way. Refusing those is not separable from refusing the two layouts above; it is one rule. The price is a measured over-refusal that the deployment's prefix **length does not determine** — the prefix bytes decide it too, and can decide it entirely. The well-known `64:ff9b::/96` pays **nothing**, always, measured exhaustively over the whole IPv4 target space: bytes 4–11 are zero by definition, so the `/32` through `/56` layouts read padding and are skipped, while the one remaining speculative layout, `/64`, reads bytes 9–12 and so decodes to `0.0.0.x` — the target's own first octet behind three zero bytes, which no blocked class matches for any of its 256 values. (Saying *every* speculative layout is skipped is the neat version and is wrong; the figure is right either way.) RFC 6052 fixes that prefix at `/96`, so there is no ambiguity there to pay for. On the RFC 8215 local-use `64:ff9b:1::/48` it ranges from nothing to everything: with the remaining prefix bytes zero, a legitimate public target is refused for **12.8%** of addresses under a `/48` mapping, **6.6%** under `/56` and `/64` and **0%** under `/96`; but an NSP whose own fixed bytes read as a blocked class under a shorter layout refuses **every** address it can express — `64:ff9b:1:7f00::/96` is legal and its `/48` reading is `127.0.0.0`. RFC 8215 §5 should be quoted against this decoding as well as for it, since it reserves the very prefix the cost is paid on: nodes "must not make any assumptions regarding the syntax or properties of those addresses (e.g., the existence and location of embedded IPv4 addresses)" — lowercase, in Deployment Considerations, so not RFC 2119, but it is the sentence most directly against what the decoder does. The answer is not that it does not apply: it is that a guard deciding whether to *refuse* a dial is not a node forwarding a packet, and assuming an embedded address that is not there costs a refusal while declining to assume one that is there costs the metadata endpoint. Fail-closed, sometimes total, and unavoidable for a guard handed an address rather than the layout that produced it; the escape hatch for a deployment that hits it is to configure the NAT64 prefix and collapse the six candidates to one, which nothing needs today and this design does not foreclose. That same absent knob bounds the decoding itself: only `64:ff9b::/32` is recognized, while RFC 6052 equally allows translating through a Network-Specific Prefix from the operator's own space, which nothing in an address marks as one — a deployment doing that gets no NAT64 decoding at all and its wrapped metadata address is admitted. The decoding is hardening on the one prefix an attacker can count on being routed, not a general answer to NAT64. None of this is reference behavior. The reference documents *reachability* — remote MCP servers over an HTTP endpoint, private-network servers only through MCP tunnels — but no per-address policy: nothing about loopback, link-local, the unspecified address, multicast or RFC 1918, and a refusal on its side would be indistinguishable from an ordinary `mcp_connection_failed_error`, which covers any network error. So both the list and its consequence are ours: an agent whose `mcp_servers` entry resolves to one of those classes gets a connection failure, where the reference might not. **RFC 1918 is deliberately allowed**, which is the reading that matters most and the one most likely to look like an omission: this platform is self-hosted by premise (CLAUDE.md), so an MCP server on the operator's own private network is the normal case rather than an attack, and the guard is the floor beneath an agent's egress policy rather than the policy itself. The rule predates this slice as the vault-credential validate probe's own guard, shipped with the plan 12 slice 2 probe that D8 specified — D8 itself specifies the probe's mechanics, not the address classes, which were an implementation choice riding along with it. Slice 2 extracted it so the probe and the MCP client enforce one implementation instead of two copies. The extraction is deliberately not behavior-preserving on the probe, and it moves in both directions. Tightening: the guard it inherited decoded three transition forms (NAT64, 6to4, Teredo) but admitted three more — IPv4-compatible `::/96`, IPv4-translated `::ffff:0:0:0/96` and RFC 5214 ISATAP — so `::127.0.0.1`, `::ffff:0:169.254.169.254` and `2001:db8:1234:5678:0:5efe:7f00:1` passed where `::ffff:127.0.0.1` and `::ffff:169.254.169.254` were refused, and it also gains the NAT64 six-layout read. Loosening: through the unspecified-candidate skip that makes those six layouts usable, the probe now admits `64:ff9b:1:808:8:800::`, `64:ff9b::` and `64:ff9b:1::`, which its old low-32 guard refused. Measured rather than assumed, the admitted forms were latent rather than a live bypass — a connect to `[::127.0.0.1]` never reaches a listener on `127.0.0.1` on either platform, because both kernels treat it as an ordinary global IPv6 destination rather than as an IPv4 address: with no IPv6 route Linux fails at once with `ENETUNREACH`, and on a host that has IPv6 connectivity the SYN is routed out the default IPv6 interface and the connect times out. The mechanism that would have delivered it to the embedded address is RFC 2893 §5 automatic tunneling, which RFC 4213 §8 removed; its §3.6 points the same way but with less force than it is tempting to claim — a decapsulator MUST silently discard a packet whose *inner* IPv6 source is invalid, and `::/96`'s membership of that list is a SHOULD. So closing it is defense in depth rather than a patched hole — a guard that holds only because the kernel also says no is not a guard. - **What a malformed MCP tool listing becomes (plan 29 slice 2)** — MCP requires a tool to carry a name and an object `inputSchema`; a customer-named server is free to break either, and the Go SDK decodes a response rather than validating it. Pagination it does **not** require to terminate — the 2026-07-28 pagination spec has no rule that a listing must end, only "servers SHOULD provide stable cursors" and "clients SHOULD treat a missing `nextCursor` as the end of results" — so a server that never stops issuing cursors is unbounded rather than non-conformant, and the ceilings below are this platform's policy rather than the protocol's. The reference never has to say what it does with any of it: it makes the MCP connection server-side, so the MCP exchange itself is invisible from the wire and only its outcomes are visible (as `agent.mcp_tool_use`/`agent.mcp_tool_result` events, and as typed `mcp_connection_failed_error`/`mcp_authentication_failed_error` session errors naming the server). So these readings are ours. An entry the platform cannot faithfully hand to a model is **skipped** rather than failing the listing: one malformed entry must not deny an agent the rest of a server's catalog. The nearest documented posture is adjacent rather than identical — Anthropic's *Messages API* MCP connector states that a `configs` entry naming a tool the server does not offer logs a backend warning and returns no error, because tool availability may be dynamic; the managed-agents pages say nothing about either an empty listing or a malformed entry, so the skip is consistent with that by analogy and is not the reference stating it. Four readings make up "cannot": a name that is empty, longer than 128 bytes, or outside `[A-Za-z0-9_.-]` — deliberately the MCP SDK's own `validateToolName` rather than a guessed-at Anthropic rule; if the reference is stricter, the place to enforce that is where the model request is assembled and the constraint can be checked against the reference. Note that the SDK does not itself enforce that rule anywhere: `AddTool` *logs* a violating name and registers the tool regardless, and no client-side path checks it at all, so a name breaking it reaches a client as an ordinary listing entry. This is the first place it can be caught, not a redundant second one. (Anthropic's own custom-tool docs describe a stricter set — letters, digits, underscores and hyphens, no `.` — which is part of why the stricter check belongs at request assembly); an `inputSchema` that is present and is not a JSON object; one whose root `type` is anything but `"object"`, **absent included**; and — a change of reading, not a carry-over — an **absent or null** `inputSchema`. MCP makes `inputSchema` required, so an entry without one is malformed rather than "a tool that takes no arguments", and synthesizing `{"type":"object"}` for it would present the model a contract the server never published; the earlier reading did synthesize it, on the argument that Anthropic's `input_schema` rejects `null`, which explains why the field cannot be *forwarded* but not why it should be *invented*. Requiring the root `type` rather than checking it only when present closes the same fabrication reached from the other side: an earlier shape let `{}` through as an "unconstrained" contract. Both MCP's schema (SEP-2106) and the pinned SDK's own server require it — `AddTool` panics unless the decoded schema's type is `"object"`, reading an absent type as not-`"object"` rather than as a default — and Anthropic's `input_schema` requires it too, so a schema without it could not be offered to a model anyway. A server that hands back a cursor it has already used, or never stops issuing new ones, **fails** the listing rather than looping: pagination is server-driven and the listing runs inside a work item holding a queue lease, so an unbounded loop there is a server-controlled one. Every cursor seen is remembered, not just the one immediately before — a server alternating between two cursors never repeats one in consecutive answers, and it can make those repeats free: under a 2026-07-28 negotiation a page sent with a positive `ttlMs` is answered from the SDK's own per-cursor cache with no request on the wire, so it draws nothing from the byte bound below either. A second entry claiming a name already taken is dropped for the same reason a malformed one is: a name is how a `configs[]` entry and a model's `tool_use` address a tool, so duplicates are an ambiguity rather than two tools, and they would reach a model as two definitions sharing a name in one request. First wins, and what makes a malformed first entry leave the name free is where the name is **recorded** rather than where it is checked: the duplicate check runs *before* the schema check and the recording *after* it, so an entry rejected for its schema never reaches the line that claims its name. (Saying the check itself runs after the schema check is the tempting shorthand and is wrong — it was carried in this entry for two rounds after the code comment was corrected.) The page bound is 100, and it is a compatibility limit and not only a safety valve — a spec-compliant server that genuinely paginates past it fails the listing outright rather than being truncated, which is the right failure (a silently short catalog is worse) but is a real ceiling an operator can hit. Three more bounds sit under it, all ours and none in the protocol: a connection reads at most 8 MiB **in total across every response**, bodies in full and header blocks as far as parsing leaves them countable (below), a whole listing runs at most 2 minutes, and any request the SDK detaches from the caller's context gets a 30-second deadline of its own. The byte bound is cumulative because a per-response cap does not bound a listing — 100 pages of 8 MiB is 800 MiB, and both ends retain it. Under a 2026-07-28 negotiation the SDK puts each `tools/list` result into a per-cursor cache unconditionally (gated only on that negotiation) and keeps it until that same cursor is asked for again, or until the server sends `notifications/tools/list_changed`, which clears the cache outright. Whether a *read* of that cache avoids the wire is a separate question with a different answer: the SDK treats an entry as a miss unless the server sent a positive, unexpired `ttlMs` hint, which nothing defaults — so a modern server that omits the field is cached but never served from cache. Retention does not depend on the hint; serving does. Headers are inside the bound, but only as far as they can be counted, which makes it two bounds rather than one and is worth stating precisely because the first version of this entry overstated it. net/http bounds a *single* response's header block and nothing bounds their sum, so a body-only budget let a paginating server move a hundred megabytes past a bound that said eight. Charging the block reconstructed from `resp.Header` closes that for header bytes the client can see. It cannot close it for anything that misses that map, and there are three such routes in falling order of what they can move. A **1xx informational block** — 103 Early Hints, say — never enters `resp.Header` at all, and a server may send many before its final response: a one-off probe under net/http's 10 MiB default, not a fixture the suite retains, measured 91.8 MB on the wire across 100 pages for 3,900 bytes charged — the gap this package then closes rather than one that survives its cap. **Padding whitespace or folded continuations** are the second, since textproto trims and joins before the map exists — measured against a raw listener whose only other header is Content-Length, a response of 200,048 wire header bytes whose `X-Pad` value was one character followed by 200,000 spaces reconstructs to 49, a factor of 4,083 that no arithmetic on the parsed map corrects; both halves move with whatever else the response carries, so the fixture is named rather than just the pair. **Trailers** are the third: they arrive after the body, so they are absent when the charge runs. Calling them the smallest, as this entry did, is true only over HTTP/1.1, where net/http rejects a long trailer against its own read buffer (measured: 3 KiB accepted, 8 KiB refused as "suspiciously long trailer after chunked body"). Over HTTP/2 a trailer block takes the same per-block cap as any other, and is in fact the *largest* of the three positions in practice — the acceptance boundary bisects to 65,856 bytes accepted and 65,857 refused, where the raw cap says 65,536. All three are bounded instead by the raw `MaxResponseHeaderBytes` the client this package builds sets in place of net/http's 10 MiB default, and it bounds a header **block** rather than a response, which is the correction this entry needed most. Over HTTP/1.1 the difference barely shows: net/http resets the limit per informational block only when the request carries an `httptrace` with `Got1xxResponse` set, the Go SDK installs none, so 1xx blocks and the final block draw on one limit. Over HTTP/2 — which this client explicitly enables, so it is the ordinary path and not an exotic one — the limit becomes the connection's `maxHeaderListSize` and applies to each decoded block on its own. Measured with a one-off probe rather than a retained fixture, though each figure follows from the constants: an 80 KiB final block is refused, while two 30 KiB Early Hints plus a 60 KiB final block (~120 KiB) is accepted, and with a 60 KiB trailer on top (~180 KiB) it is still accepted. What the suite retains is the boundary itself, driven either side of it. So a response cycle carries three separately-capped blocks. The cap is not the raw constant either: net/http converts `MaxResponseHeaderBytes` into an HTTP/2 `SETTINGS_MAX_HEADER_LIST_SIZE` through `adjustHTTP1MaxHeaderSize`, which pads it by an assumed ten fields at h2's 32-byte per-field accounting, so the framer admits **64 KiB + 320** per block and a single field can carry nearly all of it. **That cap bounds a peak, and no cumulative header ceiling follows from it** — which is a correction this entry has needed repeatedly. Several revisions published a ceiling and every one was falsified — by whitespace padding, by mistaking a block for a response, by claiming a socket total that no header arithmetic can produce, and by multiplying a per-block cap by a response count. That last is the one that matters, because it is what all of them needed: a bound on how many responses one connection answers, and go-sdk v1.7.0 does not have one. The handshake, `maxToolPages` pages and the session-ending `DELETE` come to 104, and two paths walk past it. A server that answers the first `server/discover` with `CodeUnsupportedProtocolVersion` and a supported-version list is probed a second time (`mcp/client.go`, `for range 2`). And any response delivered as `text/event-stream` may end carrying a priming `id:` with no call response — legal under SEP-1699 and explicitly supported by the SDK — which sends `handleSSE` round its reconnect loop again: the no-progress retry cap it grew for exactly this (#679) resets on every id that advances, the server picks the delay through the SSE `retry:` field, and the SDK's own TODO beside `connectSSE` records that a limit on total attempts for one logical request is still missing. A fixture in the suite drives it — **around two thousand responses to a single listing in three seconds**, in three of the 120 seconds `ListTimeout` allows, against the 104 the arithmetic multiplied by — and it is written to go *red* if that upstream limit ever lands, which is how this entry would learn it may publish a ceiling again. It counts responses and says nothing about their bytes, deliberately: an earlier revision reported `responses × 50000` as bytes delivered, false by more than two orders of magnitude, because `net/http` trims a padded header value in `writeSubset` *before* it reaches the wire — client-side trimming is what `headerBytes` cannot see, and the fixture that demonstrates *that* is a raw listener, not this one. One thing here is bounded and worth stating: `headerBytes` charges every response at least the twenty-odd bytes of its status line and terminator, so the byte budget caps the response count too, at a few hundred thousand. Its product with a maximal block is left unstated on purpose, under the rule this entry kept failing: do not multiply by a quantity nothing bounds. Deriving a figure is fine where both terms are enforced somewhere — the 800 MiB above is `maxToolPages` times `MaxResponseBytes`, and the few hundred thousand just above is that budget over a floor `headerBytes` guarantees — and the withdrawn product was not that: it multiplied an enforced per-block cap by a response count with no bound at all. Which is why every attempt to publish it has been wrong, including one that named the rule and broke it in the same sentence. What is bounded usefully is the peak and not the sum: one header block at a time, plus the 8 MiB cumulative figure for everything that can be accounted. The unaccounted blocks are parsed and dropped per response rather than retained, so they cost bandwidth rather than memory, and the loop ends on whichever of the byte budget or `ListTimeout` arrives first. Nothing here bounds socket traffic either, and nothing can: a server may put one byte in each DATA frame, or flood PING and WINDOW_UPDATE, none of which any count in this package sees. What bounds a hostile connection in that direction is the two-minute listing budget; these byte bounds are about memory, which is what an `io.ReadAll` of a multi-gigabyte response actually threatens. A caller who supplies its own `*http.Client` gets the accounted half only, since the raw per-block limit lives on the transport this package builds. The constant itself is pinned by fixtures with absolute margins rather than by arithmetic — a 16 KiB block accepted and three 30,000-byte informational blocks refused — which between them kill a mutant in either direction, including the 1 KiB tightening that would break essentially every real server and that stayed green under an inequality. Anything above 64 KiB — strictly, 64 KiB + 320 over HTTP/2 — in one *legitimate* header block from an MCP server fails the connection, and that is a real ceiling. It is set generously on purpose, since the cost of setting it too low is a working server this client cannot talk to: real blocks run a few hundred bytes to a few kilobytes, and the heavy realistic cases — SSO `Set-Cookie` chains, dense tracing and rate-limit headers — reach the low tens of kilobytes. The referent worth naming is nginx's `proxy_buffer_size`, its cap on an *upstream's* response header block, which defaults to one memory page — 4k or 8k depending on the platform, so 64 KiB is eight to sixteen times it — and a server behind a default reverse proxy is already held below this limit by the proxy. (An earlier version of this sentence compared it to what nginx *emits* of its own accord, a few hundred bytes, which makes the ratio ~200× and is the wrong comparison; it also invoked the absence of a cookie jar, which governs outbound request headers and cannot affect what a server sends.) This package holds its own copy alongside: names and descriptions are shared string backings rather than second copies, but every accepted schema exists twice, once as the SDK's decoded map and once as the bytes re-marshaled here. The detached-request deadline exists because `http.Client.Timeout` is the caller's to set and a supplied client may leave it zero, while the SDK builds a connection's lifecycle context as `context.WithCancel(xcontext.Detach(ctx))` — no deadline, and cut off from the caller's cancellation, so the only thing that ends it is the connection's own `Close` and only after the DELETE has returned — and sends the session-ending DELETE on it: a server that accepts that DELETE and never answers would otherwise hang `Close`, and the work item's queue lease with it, past anything left to interrupt it. And `"tools": [null]` is contained rather than propagated: `github.com/modelcontextprotocol/go-sdk` v1.7.0 dereferences every decoded element without a nil check (`filterValidTools` → `validateParamHeaderAnnotations`), so that response panics the client — recovered at the single SDK call, because the caller is an executor shared by every session on the host and a Go panic is not confined to its goroutine. One reading we do **not** make, and decline rather than cannot: a successful result carrying no `tools` field at all (`{"result":{}}`, or `"tools": null`) is recorded as "this server has no tools" rather than as a malformed, retryable response. The protocol does distinguish them, but the SDK does not — `ClientSession.ListTools` passes the decoded slice through `filterValidTools` before returning, and `filterValidTools` builds its result with `make([]*Tool, 0, len(tools))` — so both arrive as a non-nil empty slice and the typed call cannot separate them. A second reading is forced by the same typed surface and is a real divergence from the pagination spec rather than a choice: MCP states that an empty string is a valid cursor and **MUST NOT** be treated as the end of results, while go-sdk types `NextCursor` as a plain `string`, so an absent `nextCursor` and an empty one decode identically and the listing stops on both. A server that genuinely uses `""` as a cursor would be truncated after its first page. Recovering the difference means the same JSON-RPC-envelope reimplementation the paragraph above declines, for a case no server is known to exercise. It is recoverable a layer down and we decline to go there: the client already wraps the HTTP transport (for the byte cap), and that wrapper sees the raw body, so an absent `tools` key is readable. Doing it means parsing the JSON-RPC envelope ourselves — over Streamable HTTP that body may be an SSE frame rather than plain JSON, so it means reimplementing the SDK's framing to re-derive one bit, and correlating it back to a typed result the SDK has already flattened. The bit distinguishes two protocol violations whose only sensible handling differs by "record no tools" versus "fail the listing", and the cheaper answer to a server that violates the protocol here is the former. - **MCP-client egress and the tool catalog — what the reference leaves unobserved (plan 29 slice 2)** — The reference makes the MCP connection server-side, so the exchange itself is invisible from the wire and only its outcomes are; what it *does* pin is that networking's `limited.allow_mcp_servers` (default false) additively admits "MCP server endpoints configured on the agent", that networking exists on **cloud** environments only (a `self_hosted` config is exactly `{"type":"self_hosted"}`), that session creation validates no MCP connectivity, and that a failed connection "is retried on the next `session.status_idle` to `session.status_running` transition". Everything below fills what those leave open. **Where the policy is enforced**: the platform dials MCP servers from the executor's own process, structurally outside the per-session gate, so `limited` is enforced at that dial or nowhere — before it, never after, since a refusal that still opened the connection would already have told the server the session exists. The reference documents `allow_mcp_servers` as a sandbox-egress field; reading it as also governing the platform's own dial is ours, and is the reading that gives the field something to admit. **`self_hosted` is unconstrained**: with no networking block there is no policy to apply, and inventing one would fence off a deployment the reference never fences — but the kind is not what decides — the policy's **type** is. A `self_hosted` config carrying a networking block is one the REST surface cannot have written (it rejects every field but `type`), so the block came from an import, a restore or a hand-written UPDATE and is a policy somebody meant; the type it names is applied, and an unrecognized one refuses. A block naming no type at all reads as no policy, which is deliberate only in the sense that the decoded value cannot tell it from an absent block: `domain.Networking` is a value struct, so both arrive with an empty type. That corner adds no reach — a hand-written row can equally say `unrestricted` — and it is the one thing this rung does not distinguish. Deciding on the kind instead would leave the refusal below reachable on cloud rows alone. **An unrecognized policy refuses**, rather than reading the missing discriminator as the wire default: `gate.newPolicy` already fails closed on one, and the two enforcement points must not disagree about one policy. It is reachable, which is why it is decided rather than assumed — the schema constrains `config->>'type'` against the environment kind and leaves `config->'networking'` alone, and a config-preserving update (packages, description) carries a stored value forward without revalidating it, so reading it as unrestricted would make exactly that malformed row the one admitted everywhere. A cloud environment created through the REST surface always names a policy, since the config normalizer defaults it. **The catalog**: `mcp_catalogs` is a per-session snapshot keyed `(session_id, server_name)`, not a URL-keyed cache shared between sessions, because two sessions may reach one server with different credentials and be shown different tools. Its row is the retry state, and the three states are ours: no row means never reached, `failed` is re-attempted on the next turn (which is what makes the documented retry-on-resume possible without new state), `ready` is a listing the brain may offer and is not re-fetched. **Nothing disables a server for the rest of a session** — no source documents such a state, so a transient failure heals by itself and the per-server attempt count, if a threshold is ever wanted, is derivable from the log. **A `ready` row is matched on its url as well as its name**, and rows an agent patch no longer declares at their url are deleted in the patch's own transaction: `mcp_servers` is mid-session-mutable and replaced whole, and a listing attributed to the wrong endpoint would reach the model as tools that are not there. The pass also settles under the session's own row lock and re-reads the declared array from inside it, so a patch that lands while the dials are in flight cannot have a row written behind it for a server it just removed. The three together are deliberately redundant — the delete is the mechanism, and the url comparison and the settle-time re-read are what keep a missed or overtaken delete from being a correctness bug. **A server that cannot be reached is a row, not a fault**: an unreachable endpoint, a url that is not http(s), a policy refusal, and a server the pass's own time budget did not reach all land as `failed` rows and the turn is chained anyway, because faulting the work item would reclaim-loop it against a server that is simply down — the opposite of the documented "the session continues without that server's tools". (Chained on the same `HasUnansweredToolUse` condition every other settlement uses, so a discovery pass that settles while a tool call is still outstanding leaves the wakeup to whichever settles last.) That the pass is time-bounded at all is ours: the reference documents no such limit, and the platform needs one because it dials serially from a process that runs one work item at a time. The typed `mcp_connection_failed_error` session events that name the server on the wire are a later slice; today the failure is recorded in the row alone — and a reason that says the pass ran out of time before reaching a server never displaces one an earlier pass earned, since that text describes this platform's scheduling rather than the server. **What a row may hold is bounded by this platform, not by the protocol**: a failure reason is cut to 2,000 bytes and a listing to a quarter of a megabyte of the names, descriptions and schemas a server chose, tools past it dropped whole rather than truncated. MCP bounds neither, and the reference documents no limit of its own, so both figures are ours — chosen far above any catalog meant to be offered to a model and there for the one that is not. **Two scheduling properties are deliberately left standing**, named here so the budget above is not read as solving them: servers are dialled in declaration order, so a persistently slow one is re-attempted ahead of the servers behind it on every turn and can keep them out of the catalog indefinitely; and the budget is spent on the executor's single work goroutine, so a server that accepts a connection and never answers holds every other session's work on that host for as long as the budget allows. Both are the retry-and-fairness semantics plan 29's slice 6 is for; what this slice owes them is a bound an operator can lower (`EXECUTOR_MCP_DISCOVERY_TIMEOUT`, wired through Helm and compose), not a scheduler.

- **The console-API dialect's edges — rejections, paging bounds and the reserved org segment (plan 30 slice 2)** — The 2026-08-10 capture of the reference console showed the happy paths only: a create, a list, a revoke, and their bodies. Every edge our implementation answers is therefore a local choice, recorded here rather than presented as mirrored. **Rejections:** issuing on a `cloud` environment is a 400 (its work is consumed by this platform's own in-process executor, which holds no environment key, so the credential would authorize a worker that does not exist — and the reference offers no key UI for its cloud environments either, which is suggestive but not a captured response); issuing on an archived environment is a 400; an unknown or malformed environment id is a 404 in the same shape, so the namespace is no better an enumeration oracle than `/v1`; an unknown, malformed or *foreign* `token_id` all take one 404 branch, so revocation can neither reach across environments nor confirm that an id exists elsewhere. **The `name` bound** is 1–128 characters after trimming, and a whitespace-only name is rejected; the dialect's own bound is unobserved, and 128 is a local pick sized to a hostname-or-phrase label. **Paging** is offset / `total` / `has_more`, matching the observed listing envelope rather than this platform's wire-side keyset `next_page` cursor — the observed listing reported `limit: 100`, so 100 is both our default and our cap, and a `limit` or `offset` outside its range is a 400 whose message is ours. Whether the reference validates that segment at all, and what it says when it does not match, is unobserved.
