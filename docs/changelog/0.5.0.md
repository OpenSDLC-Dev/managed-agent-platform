## [0.5.0] - 2026-10-04

### Added

- **`grep` takes the reference's twelve search options and its description, and runs ripgrep in the sandbox** ([#827](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/827)) — The built-in `grep` tool's schema and description are the ones a 2026-09-02 recording showed the reference handing the model: `output_mode` (`files_with_matches`, `content`, `count`), `-i`, `-n`, `-A`, `-B`, `-C`/`context`, `type`, `glob`, `head_limit`, `offset` and `multiline`, each passed to ripgrep as the flag its description names. The executor and the BYOC worker carry a static ripgrep 15.2.0 for Linux x86_64 and aarch64 and install it in a sandbox's `/tmp` the first time it greps there, so `grep` behaves the same on glibc, musl and busybox images. That `/tmp` must be writable and allow executing files; where ripgrep cannot run, `grep` is a tool error saying why. From source, `make ripgrep` fetches the pinned binaries — `make test`, `make eval`, the release targets and the Dockerfile run it — and a build made without it logs a warning at startup and its `grep` reports that it carries none. The worker tarballs and the server image ship [NOTICE](../../NOTICE), [LICENSE](../../LICENSE) and [THIRD_PARTY_LICENSES](../../THIRD_PARTY_LICENSES), the license texts of what that ripgrep links.

- **Every refusal of an authenticated request is logged** ([#540](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/540)) — Each 4xx answered to a request whose credential verified — one its own lane then refuses included — writes one Info line, `request refused`, with the method, the path without its query string, the status, the error type, the wire message and the request id; the path and the message are capped at 512 bytes. An unauthenticated request writes none, so it cannot drive the log's volume. The line exists because several of the reference's sentences the wire now carries name nothing — `Not found`, `Cannot modify archived agent`. Detail only the server knew and a sentence drops gets a line of its own beside it, under the same request id: the stale-version 409's expected and current versions among them.

- **The reference's own API key update route, and its workspace read** ([#820](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/820)) — `POST /api/console/organizations/{org}/api_keys/{id}` updates a management key on the reference's path, with no workspace segment; `…/workspaces/{workspace}/api_keys/{id}` stays as an alias. `GET /api/console/organizations/{org}/workspaces/{id}` answers the reference's recorded 404 with `details`, for every id, and renders no workspace.

- **A shared fixture corpus ties the two hand-written `.tf` readers together** ([#762](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/762)) — `deploy/gcp/check_split.py` and `tools/kmsrole/hcl.go` read the same Terraform subset in two languages and cannot share code, so until now they were kept in agreement by prose. That was not holding: three consecutive commits read the same heredoc rule three different ways, and each divergence was caught by a reviewer running the terraform binary rather than by a test. [tools/tfcorpus](../../tools/tfcorpus) is the tie — whole `.tf` files with, beside each, the blocks a reader must return or the refusal it must give. Both suites read the same manifest, so a rule that moves in one reader and not the other now fails on the side that did not move. The new `make tf-corpus-check` re-asks terraform for each file's `fmt` exit, because a corpus written from a comment pins the comment and both of the boundaries this closes were rules the two readers agreed on and terraform did not. That exit is all terraform is asked: it says whether a file parses, never where the binary closed a heredoc, so a row's expected blocks stay held by the two readers having to agree.

- **`make gcp-kms-role-check` holds each GCP identity's Cloud KMS role to what its binary's code names** ([#750](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/750)) — `tools/kmsrole` reads the key-level roles out of the Terraform under [deploy/gcp/](../../deploy/gcp/) and every `Encrypt`/`Decrypt` identifier out of the in-module packages each `cmd/` binary transitively imports, and fails when an identity is granted less than its binary names. It runs in CI beside the other `gcp-*` checks, outside `make verify` because the Go gate does not depend on the GCP tree; `go run ./tools/kmsrole` prints the table it derived. This closes the mechanism behind #748, where the executor's role said Encrypter while its code had decrypted for three tagged releases — nothing went red, because the cipher's startup probe only encrypts, so both processes went Ready and the deploy was green while every private-repository clone and vault-credentialed MCP dial lost its credential. It is a floor, not a split: it never asks for a role to be narrowed. On the cipher key it refuses rather than guesses whatever it cannot read honestly — an unknown role, an unattributable member, a conditional, counted or `ignore_changes` grant, an override file, a module, an IAM deny policy, grants split across two Terraform roots. A role granted *above* the key is the one asymmetry: read literally it refuses, unreadable it ignores, since that can only add permissions it never saw.

- **Installing a release into your own GCP project is documented** ([#749](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/749)) — every GCP instruction built the images into Artifact Registry first, so an operator deploying a *release* had to infer the rest. [docs/deploy-gcp.md](../../docs/deploy-gcp.md) now has the path: the five `make` targets are unchanged, the build and install collapse into one `helm upgrade --install` from `oci://ghcr.io/opensdlc-dev/charts/managed-agent-platform`, the values file wants **no** `image:` block because the chart's defaults already resolve to that release's images, and `executor.gateImage` is the one image value it must set. It also names the trap: take `sandboxPlacement` from `deploy/gcp/staging-values.yaml`, not from `terraform output -raw helm_values_mode1`, whose `image:` mapping silently replaces those correct defaults with Artifact Registry coordinates the release never pushed to. `make gcp-env-tfvars` still needs the Cloud Build API and its default service account even though nothing builds. And [deploy/gcp/README.md](../../deploy/gcp/README.md) now carries the `kubectl create secret generic` its own text promised: the seven-key mode-2 Secret previously existed as a worked command only inside `.github/workflows/deploy.yml`.

### Changed

- **Upgrading from v0.4.0 applies migrations 0041–0047 in one transaction, which holds each table lock it takes until it commits or rolls back** — The first v0.5.0 controlplane, brain or executor to start runs all seven, the migrations of #720, #663, #643, #685, #674, #578 and #856 in that order. It takes `sessions`, `session_threads`, `deployment_runs`, `work_session_tokens`, `files` and `deleted_sessions` ACCESS EXCLUSIVE, and while it holds them every read and write of those tables, from any replica, waits. The run's length grows with three pieces of work: 0041 clears stray stamps from `session_threads` and then validates its CHECK over every row, 0044 scans `memory_stores` to backfill archived stores' `updated_at`, and 0046 builds three indexes on `files`, measured under 0.4 seconds on a million rows. 0043, 0045, 0046 and 0047 give up a lock they cannot have within 2 seconds; 0041, 0042 and 0044 set no bound of their own, so the run can wait for theirs indefinitely unless the database, the role or the DSN sets a `lock_timeout` or `statement_timeout`. A give-up or a deadlock rolls the whole run back, releasing every lock, and starts it again after 1, 2, 4, then 8 seconds; a start whose fifth attempt fails exits with the error, and the next start tries again.

- **CI and the release images now build with the same pinned Go, 1.26.8** — `go.mod`'s new `toolchain go1.26.8` line is the pin. Every `actions/setup-go` step installs it; until now CI installed 1.26.0, from the `go` line. The [Dockerfile](../../Dockerfile)'s build stages start from the official Go image at `1.26.8-bookworm`, pinned by its multi-arch digest. Before, they used the floating `1.26-bookworm` tag, which shipped whichever patch release was newest on the day of the build. So the standard-library fixes a release ships are the ones CI tested, and the Go toolchain a release compiles with no longer depends on the day it is built. The pin covers that build toolchain only: the runtime images still start from the floating `debian:stable-slim` and install unversioned apt packages. `make pins-test` now fails if a setup-go step stops reading `go.mod`, if a workflow sets `GOTOOLCHAIN`, or if any Go image reference in the tree names another release or has no digest. A local `go` older than 1.26.8 downloads and runs 1.26.8; a newer one, or any under `GOTOOLCHAIN=local`, keeps itself.

- **The Codex reviewer runs `gpt-6.1-sol` at `xhigh`, both pinned** (`.claude/skills/run-reviews/SKILL.md`). This supersedes `gpt-5.6-sol` with an effort inherited from the user's Codex config. That config is not stable: on 2026-10-04 it held `low`, so reviews that inherited it ran at low effort. An account that cannot use a model gets HTTP 400 instead of a substitute, so a Codex pass that errors is not a clean verdict. The skill names the CLI's model list (`~/.codex/models_cache.json`) and the verified fallbacks, `gpt-6-astra` and `gpt-5.6-sol`. The /code-review confirmation step now names the current Opus, `claude-opus-5-5`.

- **A session's file copy is deleted like any other row; rolling back below migration 0046 is unsupported** ([#856](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/856)) — Migration 0047 drops the copy-delete guard and tombstone trigger 0046 added for older binaries, and `map.copy_delete` with them; the reference count on the object-delete queue stays. **Upgrading:** binaries built before 0046 are not supported against this schema, so a rollback below it, a failed `helm upgrade --atomic` included, is unsupported.

- **Sandbox tools refuse input they do not understand, and `grep` lists files by default and searches as ripgrep does** ([#827](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/827)) — `bash`, `read`, `write`, `edit`, `glob` and `grep` answer an input property their schema does not declare with a tool error naming it and the ones they accept, where they used to drop it and run anyway — so a `grep` sent `-i` searched case-sensitively without saying so. This holds on the executor and the BYOC worker, on Anthropic- and OpenAI-protocol routes alike. A `grep` with no `output_mode` now returns the matching files' paths, the reference's default, not `path:line:text` lines; `"output_mode": "content"` gives those. And `grep` is ripgrep now, not the image's GNU grep: Rust regex syntax, not PCRE; hidden files searched but `.git` and five other version-control directories skipped, as are binary files under a directory, what a git repository's `.gitignore` names and the memory sync's own files (unless a path names them), and `node_modules` no longer skipped otherwise; answers list in path order, which costs rg its parallel search. **Upgrade BYOC workers with the platform**: an older worker drops the new options and answers `path:line:text`, a newer one under an older platform answers paths where the model was promised lines, and the work protocol carries no worker version to catch either.

- **A mounted file is the session's own copy, as on the reference** ([#578](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/578)) — Every create, resources add and deployment fire mints a `files` row per file resource, echoed in `resources[].file_id`: a fresh id, session-scoped, never downloadable, with the upload's name, size, type and expiry. It shares the upload's object, so deleting the upload leaves the mount working; the object goes once no row names it. The default mount path and a deployment still name the upload. `GET /v1/files` without `scope_id` now leaves session-scoped files out, outputs included. Earlier sessions keep naming their uploads. **Upgrading:** migration 0046 locks `files` for its index builds (under 0.4s per million rows); binaries built before it are not supported against its schema (#856). [docs/DIVERGENCES.md](../DIVERGENCES.md) registers what is inferred.

- **A deployment echoes each resource's `mount_path` as it was sent** ([#849](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/849)) — As the reference was recorded doing, a deployment's file and repository resources now read back with the `mount_path` the request gave: `/uploads/report.csv` reads back as `/uploads/report.csv`, not `/mnt/session/uploads/report.csv`, and an omitted one reads back with no `mount_path` key. The resolved path is still stored and is what every fire mounts, so a rolling update or a rollback mounts the same paths. Create and update still refuse a path that cannot resolve, and two resources whose resolved paths collide or nest, such as `/uploads/x` beside `/x`; that refusal now names both spellings sent and what they resolve to. A deployment also refuses a `mount_path` spelling longer than 1024 bytes, since it stores and echoes it. Deployments stored before the upgrade keep echoing their resolved paths. Finish a rollout from a release before #848 before editing deployments: an older pod saving a new pod's echoed `/uploads/x` stores its own doubled resolution.

- **A message sent while the session rests on a tool response is refused** ([#842](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/842)) — A `user.message` or `user.define_outcome` posted while the primary thread is idle awaiting a custom tool's result, a self-hosted worker's result or a tool confirmation is now a 400 in the reference's words — ``Invalid user.message event at events[0]: waiting on responses to events [sevt_…]; only `user.tool_confirmation`, … may be sent`` — where it used to be queued behind the call. The send's own answers count first, wherever they sit in it, and so does an interrupt: a message beside the results that free the session, or behind the documented interrupt-and-redirect, is read as before, and one sent while the primary is still running queues as before. A client that sent a message to a session waiting on a call must now answer the call, or interrupt, first; a client such as the console receives the 400. [docs/DIVERGENCES.md](../DIVERGENCES.md) says which waits beyond a custom call's are inferred.

- **Adding a file to a session needs a usable read tool** ([#842](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/842)) — `POST /v1/sessions/{id}/resources` now refuses a file when the session's agent has no `agent_toolset_20260401` entry leaving `read` enabled, with the reference's 400: ``Missing required tool: file resources require the read tool to be usable (enabled and not always_deny) on the session's `agent_toolset` ``. To unblock an existing session, enable `read` on it through a session update: it keeps the agent version it was created with, so updating the agent reaches only sessions created after. Session create, and so a deployment run, still attaches files to any agent: no recording shows the reference refusing that.

- **Three more recorded answers adopted** ([#842](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/842)) — A work poll's `reclaim_older_than_ms` under 1 is now 400 `reclaim_older_than_ms: Input should be greater than or equal to 1`, and an unparseable one the same validator's integer sentence, where both used to mean the 5000 ms default; an over-large one is still clamped. An agent create naming a `type: "anthropic"` skill that exists nowhere is 400 ``Agent has invalid configuration: `skill_id` `…` not found``, and one naming a skill this platform holds — imported, or a custom skill an anthropic entry names — at a version that does not resolve is ``… version `…` not found``; a reference to one of the reference's prebuilt skills (`docx`, `pdf`, `pptx`, `xlsx`) is checked only for a version of a pin's form, imported or not, with a warning in the log where it does not resolve here. Custom references, agent updates and session overrides are unchanged. A self-hosted worker now downloads a skill pinned by a legacy numeric version by the version's id, as the reference's worker does; the control plane still takes the number from older workers. And `x-should-retry: false` now rides the refusals the reference was recorded sending it on — the memory 409s, the skills, environment, file and work API refusals, unknown paths and every console refusal — so the SDKs stop retrying them; [docs/DIVERGENCES.md](../DIVERGENCES.md) lists them.

- **An answer's `session_thread_id` no longer refuses it** ([#841](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/841)) — A `user.tool_confirmation`, `user.tool_result` or `user.custom_tool_result` whose `session_thread_id` names another thread, an unknown one or no thread id at all was a 400; it is now accepted and stored, and echoed, on the thread of the call it answers, as the reference was recorded doing for a confirmation. A value that is not a string is still refused.

- **Six refusals answer the reference's recorded status** ([#841](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/841)) — Where a recording shows the reference answering with another status than ours, this platform now follows it, in its words: an agent path id that is not an agent id (`/v1/agents/undefined`) is 400 `Invalid agent ID.` on all four agent routes, not 404, while the reference's own id format reaches the 404 an absent agent gets; a thread path id that is not a thread id (`sth_…`) is 400 `Invalid thread ID: …`, not 404; a work id with none of the reference's prefixes (`POST …/work/poll`) is 400 `Invalid work ID format: …` on every work-item route, not 404; a `user.interrupt` naming a thread that is not this session's is 404 `Thread not found: …`, not 400; an environment delete the sessions block is 409 `Environment has N active sessions. Use force=true to delete anyway.` with `x-should-retry: false`, not 400 — forced, the same 409 in our words, since `force=true` still deletes no session here; and a session's memory store id with the right prefix but a token outside our id alphabet reaches the recorded 404, not a 400. A client keyed on the old statuses must follow; the console branches on none of them. [docs/DIVERGENCES.md](../DIVERGENCES.md) names the routes that take a recorded answer unrecorded.

- **Environment keys are refused in the reference's words** ([#840](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/840)) — A revoked environment key the platform minted now answers 401 `authentication_error` "OAuth access token has been revoked." on every public route, management routes included; a management key beside it is served wherever the route takes one, and on a management route so is a human credential. An expired or unknown key, and a revoked pre-0021 key, keep their answers: `invalid environment key` on the worker routes, `x-api-key header is required` on management routes. A live key sent as a Bearer to a management route, with no human credential beside it, gets the reference's recorded refusal: a 401 "Authentication failed" on `GET /v1/agents`, a 403 `permission_error` on `GET /v1/skills` and `GET /v1/skills/{id}`. The key no longer reads `GET /v1/skills/{id}`, so an expired or unknown key there, or a Bearer no other lane takes, now gets `x-api-key header is required` instead of `invalid environment key`. A skill's versions, a version and its `/content`, all a worker reads, still serve it; other management routes keep the missing-key 401. Only a Bearer with the `sk-map-env01-` prefix is looked up there, so a management key's request costs no extra query. A key still goes with its deleted environment, a 401 where the reference's work stats answer 404; [docs/DIVERGENCES.md](../DIVERGENCES.md) says why.

- **Error messages are the reference's own wherever a recording holds them** ([#540](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/540)) — An error this platform raises for a condition the reference was recorded refusing now carries the reference's `message` verbatim, ids and values in place: a stale agent `version` answers `Concurrent modification detected. Please fetch the latest version and retry.`, an unknown body field `Failed to parse request body: unknown field "x"`, an unknown path `Not found`, a missing environment `Environment env_… not found.`, and so on across every resource, the work API and the console namespace; a deployment run's `error.message` takes the reference's run sentences where recorded. Status codes, error types and `details` do not change; a few checks now run in the reference's order. An error no recording reaches keeps its wording unless it shares a helper with a recorded one — the unknown-field sentence reaches every strictly decoded body, the unknown-path and unsupported-method ones every route — and [docs/DIVERGENCES.md](../DIVERGENCES.md) lists each such extension. A client matching our old wording must match the new; the console matches on status. **Upgrade self-hosted workers before or with the control plane:** an older worker misreads an archived memory store's new refusal as one file's, so each file it pushes there stays un-synced, even after an unarchive, until its content changes.

- **The console namespace answers its recorded edges as the reference does** ([#820](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/820)) — **Deploy managed-agent-console with [console#187](https://github.com/OpenSDLC-Dev/managed-agent-console/pull/187) first**: an organization segment other than `default` is now a 401 `authentication_error` when it is a UUID (a 400 otherwise, not a 404), and an older console reads that 401 as its operator's token refused and signs them out. Environment keys are issued on `cloud` and archived environments (200, not 400), and the key listing takes a `limit` above 100. A `cloud` environment's key cannot touch its environment: its poll is a 400, its work listing a 404, its stats zeros with `workers_polling: null`, and the environment's sessions, their events and the files they mount answer it a 404. It reads skills, as recorded. An archived `self_hosted` environment's key keeps working, so its queue drains. A management key's name is 1–500 characters as sent, untrimmed. API key create takes `principal_id`: a value that is not a `user_` or `svac_` id is a 400, a well-formed one a 404. What stays inferred is in [docs/DIVERGENCES.md](../DIVERGENCES.md).

- **Memory stores omit `archived_at` until archived, and null or empty update bodies get the reference's answers** ([#817](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/817)) — Create, get, list and update rendered `"archived_at": null` on an unarchived store; they now leave the key out, and an archived store still carries its timestamp. On `POST /v1/memory_stores/{id}`, `{}`, which was a 200 that changed nothing, is now a 400 "at least one of name, description, or metadata must be provided"; a null `metadata`, which kept the bag, gets the recorded parse error (a null inside the bag still deletes its key); and a null or empty `name` reads "name cannot be empty". Memory create and update give the recorded words for a null `content` or `path`, an empty update and a null precondition hash, e.g. "v1_update_memory_params: at least one of content or path must be provided". **Deploy order:** the first-party console typed `archived_at` as required, so roll out a console release carrying [managed-agent-console#185](https://github.com/OpenSDLC-Dev/managed-agent-console/pull/185) before this release. What the recordings leave open is in [docs/DIVERGENCES.md](../DIVERGENCES.md).

- **A session thread's `stats` and `usage` are `null` until its first status transition** ([#674](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/674), part 3) — The thread list, get and archive responses rendered both as objects from birth. A primary thread that has never run now renders both `null`, as the reference does, and a thread born running (a spawned child, or the primary of a session created with `initial_events`) renders both from birth. Migration 0045 adds a `transitioned` flag to `session_threads`, set by a thread's first status change and on every existing thread, so a thread created before the upgrade keeps rendering objects even if it never ran. - **The system prompt points at `/mnt/session/uploads` instead of listing a session's file mounts** ([#681](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/681)) — The "Mounted files" block, one bullet per mount with its path, filename, MIME type and size, is replaced by the reference's own sentence as a recording quoted it: "User uploads (files uploaded to the session by the user) are available at `/mnt/session/uploads`. Use `ls` on that directory to see available files." No file is listed, so the agent finds its uploads with `ls`. A mount at its default path, `/mnt/session/uploads/file_<id>`, therefore no longer tells the model the original filename or MIME type; pass a `mount_path` that carries a meaningful name where that matters. The sentence still appears only while the session has at least one live file mount, and a file added to a session that already has one no longer changes the system prompt. A mount stored outside `/mnt/session/uploads` — possible only for a resource written by an unreleased build before [#323](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/323) — is still named, by path alone and quoted, after the sentence, or instead of it when no live mount lies under that directory. The gating and the sentence's placement remain inferences, registered in [docs/DIVERGENCES.md](../DIVERGENCES.md).

- **The six sandbox tools' schemas are closed, as the reference's were recorded** ([#822](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/822)) — `bash`, `read`, `write`, `edit`, `glob` and `grep` now carry `"additionalProperties": false`, and `edit`'s `old_string` carries `"minLength": 1`, two keywords a 2026-09-02 recording showed the reference handing the model. The Anthropic-protocol adapter sends them; the OpenAI-protocol adapter strips both from every built-in tool, as it does the web tools' keywords since [#682](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/682). The tools run as before: edit already refused an empty `old_string`. The request does change: an Anthropic-protocol route in front of a backend that refuses these keywords (vLLM's `/v1/messages`, or a gateway in front of Gemini) now rejects the tool list of any agent with a built-in tool enabled, where turning the web tools off used to keep them out. Other recorded differences stay on purpose, registered in [docs/DIVERGENCES.md](../DIVERGENCES.md): `bash`'s `restart` and `timeout_ms` and `edit`'s `replace_all`, from the SDK's typed inputs; relative `file_path`s, which the skills block relies on; `read`'s `view_range`; and five tools' descriptions, ours. `grep` took the reference's properties and description, and every sandbox tool now refuses a property it does not know ([#827](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/827)).

- **The memory-stores prompt block takes the reference's recorded structure, with guidance true to this platform** ([#672](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/672)) — The block a session's model sees for its attached stores now follows the one recorded from the reference: a persistence paragraph, the heading `Available stores (write only inside the directories listed below):`, and one name-first bullet per store — ` - "notes" → /mnt/memory/notes/ (read-only)` — with its instructions on the next line, behind an `Instructions: ` label. The reference's guidance is kept where it holds here; what describes a live FUSE mount is rewritten for this platform's sync at tool-run boundaries, including the ways a change goes silently unsaved — a deferred sync, the 100 KiB and 2,000-file caps, non-UTF-8 content, a refused path, a read-only store, a newer store version winning. With no writable store attached, the sections urging the model to write are left out. A store deleted since attach keeps its NOT AVAILABLE line, which the reference does not print, because a write there is never saved. A name's quotes are escaped and instructions labelled, so a caller's text cannot pass for a store or a hedge. Agent-visible only; no REST shape changes. A prompt or eval matching the old wording (`Memory stores.`, `- /mnt/memory/notes — notes (read_only)`) needs updating.

- **The web tools hand the model the reference's definitions** ([#682](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/682)) — `web_fetch` and `web_search` now carry the schemas and descriptions a 2026-09-02 recording of the reference echoed. The schemas add `"format": "uri"` on `url`, `"minLength": 2` on `query` and `"additionalProperties": false` on both. The descriptions are long usage guidance. `web_search`'s query guidelines end with today's date in UTC, rendered per request, so the definitions, and any prompt cache keyed on them, turn over daily. The Anthropic-protocol adapter sends the keywords as recorded. The OpenAI-protocol adapter strips `format`, `minLength` and `additionalProperties` (and `unevaluatedProperties`) from the built-in tools' schemas, so a backend that accepts only part of JSON Schema does not reject the default tool list. Custom and MCP tool schemas keep every keyword on every backend. The executor refuses a `web_search` query under two characters, counted untrimmed; a blank query is still refused. `web_fetch`'s text says it fetches only URLs the user gave or a search returned, which [#823](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/823) enforces. The six sandbox tools' recorded schema differences are settled by [#822](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/822).

- **Error bodies carry the reference's `details` member where it was recorded** ([#664](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/664)) — Some errors now nest a `details` object inside `error`, with the recorded keys and values: `GET /v1/files/{id}/content` on an upload (`error_code: file_not_downloadable`), an environment update that changes its kind (`error_code: invalid_config_type_change`), and the work heartbeat's 412 (`error_code: heartbeat_precondition_failed`, `error_visibility: user_facing`, and `current_state`, the item as the refused beat found it). On the console namespace the 404s for an unknown environment, environment key, workspace or API key carry `error_visibility: user_facing`, the environment's with `error_code: environment_not_found`. **A malformed id there is now a 400 `invalid_request_error`, not a 404**, as recorded, with a message of ours: one missing its prefix or carrying bytes that cannot be stored. A UUID is a well-formed environment key id, and an API key update reports an unknown key before it judges the body. Messages of the errors that already existed do not change, and every other error renders byte for byte as before. A heartbeat whose `expected_last_heartbeat` is not a timestamp now answers 404 rather than 412 when the work item does not exist. What still differs is registered in [docs/DIVERGENCES.md](../DIVERGENCES.md).

- **A list's last page omits `next_page` on most routes, as the reference's does** ([#676](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/676)) — Every list used to send `"next_page": null` when no page followed. The reference answers this two ways, by route, and now so does this platform: files, skills, skill versions, environments and an environment's work keep the explicit null, while every other list sends `next_page` only when a further page exists. The sessions list likewise sends `prev_page` only when there is a page before it, never as null. The memories list also carries the recorded `"prefixes": []` on every page, a key the published schema leaves out. The typed SDK's pagers, the `ant` CLI and the console treat an absent key and a null alike, as the end of the list; a client that tests for the key's presence must accept both. The per-route evidence, and the lists whose rule is inferred, are in [docs/DIVERGENCES.md](../DIVERGENCES.md).

- **A verdict on an outcome's last evaluation cycle is acknowledged, whatever it is (#670)** — When no further cycle can run (`iteration + 1 >= max_iterations`), one acknowledgment turn now follows a `satisfied` or `failed` verdict before the session idles, as it already followed `max_iterations_reached`; the turn is told the verdict, and told not to continue working unless client input shares its turn — a message, or the next outcome — which the model then answers instead (`max_iterations_reached`'s prompt now follows the same rule). With budget left, `satisfied` and `failed` still idle directly. This is reading (B) of the one recorded verdict — `satisfied` on the last cycle of a one-cycle budget, followed by an acknowledgment — and is registered as INFERRED in [docs/DIVERGENCES.md](../DIVERGENCES.md). On a cloud session the acknowledgment's own idle schedules the idle outputs harvest.

- **Only a worker's credential may post a `user.tool_result`** ([#662](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/662)) — **breaking for management-key clients.** `POST /v1/sessions/{id}/events` now decides who may post a `user.tool_result` — the result of a built-in toolset call — by the credential that signed the request, as the reference does, rather than by the session's environment kind. A management `x-api-key`, or a human signed in through the identity lane, posting one is refused 403 `permission_error` on any session, and a batch carrying one appends nothing. On a `self_hosted` session a management key used to be accepted, so it could answer a call the worker was to answer; on a `cloud` session the refusal was a 400. Nothing else a management caller posts changes: `user.custom_tool_result`, `user.tool_confirmation` and `user.interrupt` are admitted as before. The environment key and the per-item sessions token are still accepted, so the BYOC worker and `ant beta:worker` are unaffected. A client that posted `user.tool_result` events with a management key must send them with the environment's key instead.

- **One file assembles the mode-2 Secret, for CD and for an operator alike** ([#754](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/754)) — [deploy/gcp/mode2-secret.sh](../../deploy/gcp/mode2-secret.sh) replaces the inline step in `deploy.yml` and the hand-maintained copy of it in [deploy/gcp/README.md](../../deploy/gcp/README.md), which had already drifted: the workflow routes a missing `model-providers` container to the `gcloud secrets create` that fixes it (#755), and the operator's copy never got that, so the same fresh environment fails there with the raw `NOT_FOUND`. What else differs — the log masking, the run-summary annotations, `SECRET_CHANGED` — the script keys off `GITHUB_ACTIONS` itself rather than being told. `make gcp-mode2-secret-test` runs it against a fake `gcloud` and `kubectl` and a real `jq`, holding each refusal the assembly owes — a blank or whitespace-only version of either credential, an embedded newline in the two values read verbatim, five malformed `model-providers.json` shapes, a missing tool — and proving no credential reaches a command line. ### Fixed

- **The platform's sandbox scripts read only what they print, and run as written whatever an image's startup file sets** ([#860](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/860)) — On an image whose `ENV BASH_ENV` file printed, the Kubernetes backend failed every exec (the banner was read as the exit code) and silently corrupted every file read, returning the banner's bytes as the file's — which `edit` could write back — or failed every read behind an `EXIT` trap that printed; a memory store never landed, the package-install probe's answer went unrecognized, and a refused write could carry the banner as its reason. The scripts whose answers the platform parses now print them between begin and end lines carrying a nonce of their own, as `glob` and `grep` already did, and only what lies between is read; a bulk write's report comes from newline-led marker lines a startup printing them verbatim or past the cap displaces. A file that sets `-e` no longer stops a non-root Docker sandbox's bulk writes at their first `chmod`, has Kubernetes report every failing command as killed (137), or spares a runaway its deadline's kill: every platform script turns errexit off as it starts, and the exec wrappers guard each step. One printing past the 1 MiB output cap gets tool errors naming the image, not a retry loop. A library an `ENV LD_PRELOAD` names printing from a script's child lands inside those lines; the [image contract](../self-hosted-security.md) forbids it.

- **On Docker, skills and memory stores materialize under a read-only root filesystem** ([#859](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/859)) — with `SANDBOX_READONLY_ROOTFS=true`, every bulk write failed with `container rootfs is marked read-only`, so no skill and no memory store reached a Docker sandbox; each was logged and skipped, and the agent ran without it. The daemon refuses an archive extracted at a directory outside the writable mounts, and the bulk write extracted every batch at `/`. Under a read-only root a batch is now extracted a directory at a time, each archive at the directory its files land in, so the daemon checks every one as it checks a single write's, and a symlink the sandbox made pointing out of the mounts is refused rather than followed — though not one swapped in during the daemon's own check-then-extract window, which single writes share and [#863](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/863) closes. That is a request per distinct directory plus one for the bookkeeping — a 61-file skill in 10 directories takes 11 — where a writable root still takes two. A batch whose delivery is refused, or whose directory cannot be made, now fails with the single write's errors (not writable, is a directory) rather than the raw daemon or `tar` message — on Kubernetes too.

- **`glob` reads only its own output and says when the image's bash is too old for it, and the sandbox tools refuse input too long to run** ([#827](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/827)) — On an image whose `ENV BASH_ENV` file printed — as it loaded, or from an `EXIT` trap it set — a `glob` answer carried those words as paths; `glob` now reads only what its own script printed between a begin and an end line, as `grep` does. On bash 3.2, which has no `globstar`, `glob` expanded `**` as `*` and answered without saying so; it is now a tool error naming the bash 4.0 it needs. A `glob` whose pattern and path make a command past the 120 KiB one exec argument can carry, and a `read`, `write` or `edit` whose `file_path` is longer than Linux allows — past 4095 bytes once resolved, or with a name past 255 — are refused before they run, with a tool error that says so, where such a path could fail the call as the sandbox's fault, retried until its lease ran out; a `write` or `edit` into a directory that leaves no room under 4095 bytes for the 27-byte temporary name it lands under first says so, where it said the path itself was too long; and a `write` or `edit` whose `file_path`, quoted into the sandbox's own command, takes that command past the 120 KiB is a tool error naming the `file_path` too.

- **A `SKILL.md` without a `name` is accepted** ([#842](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/842)) — On both skill upload routes, and in the operator import, a frontmatter that names no skill now takes the skill directory's name, as the reference does, instead of the 400 `SKILL.md frontmatter is missing name` — read as a named one's directory is, lower case with `_` as `-`, so `My_Skill/` is `my-skill`. The fallback is held to every rule a frontmatter name is, and its pattern and reserved-word refusals say the name came from the directory. A missing description is still refused.

- **A file `mount_path` of `/uploads/<name>` mounts at `/mnt/session/uploads/<name>`** ([#848](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/848)) — The reference reads `/uploads` as the uploads directory itself: recordings of session create, `POST /v1/sessions/{id}/resources` and a deployment fire all mounted `/uploads/<name>` at `/mnt/session/uploads/<name>`, where this platform rooted it a second time, at `/mnt/session/uploads/uploads/<name>`. Those routes, and deployment create and update, now resolve it as the reference does, and so does `uploads/<name>` without the leading `/`. `/uploads` or `uploads` alone mounts the file where an omitted `mount_path` does, `/mnt/session/uploads/<file_id>`. Every other path resolves as before. Nothing stored is rewritten. A deployment created before the upgrade with `/uploads/<name>` keeps firing at the doubled path; sending its echoed resources back keeps that path too, while sending `/uploads/<name>` again moves it. Retrying an add across the upgrade with the same `/uploads/<name>` body is no longer refused as a duplicate of the doubled mount, so the session ends up holding both.

- **A database fault during an event send is a 500, not a 400 carrying the driver's text** ([#841](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/841)) — The checks a `POST /v1/sessions/{id}/events` batch runs against stored state could fail on a query error or a cancelled request. Those checks route an interrupt's thread claim, match tool results and confirmations to their calls, and validate `define_outcome`; session create's `initial_events` goes through the define-outcome check too. Every such failure was answered 400 `invalid_request_error` with the database error text as the message. The client was told the fault was its own, the SDK did not retry, and internal text left the server. These checks now return typed refusals for the client's mistakes, which keep their 4xx answers. Any other error takes the opaque internal 500.

- **On Kubernetes, a command that overran its deadline and then exited is reported as timed out, on a loaded cluster too** ([#832](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/832)) — a command that killed its in-pod watchdog, ran past its deadline and then exited could come back with `TimedOut: false` and its own exit code when the cluster was busy. The only witness was a liveness probe that is itself an exec into the pod, and under load it ran after the command had already exited. The exec wrapper now also records how long the command ran, from the pod's `/proc/uptime`. Against the deadline the watchdog enforces — the requested timeout rounded up to whole seconds — a run longer than it plus 0.5 s is a timeout whatever the probe saw. The record only ever adds a timeout, never removes one; the docker backend is unchanged.

- **The worker force-stops work whose heartbeat is refused or whose lease is not extended, as the SDK worker does** ([#813](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/813)) — when a heartbeat answers `lease_extended: false` beside a live state, or fails with a `4xx` other than `412`, `408`, `409` and `429` (a `404` for work that is gone, a `401` or `403` for a refused key), the bundled worker now cancels the run and force-stops the work item, as the reference Go SDK worker does. It used to release the item without a stop. A `412` (now even one that arrives as the run finishes) and transient failures that outlast the lease's TTL release it unstopped. A force stop that fails in turn is only logged; under a revoked key the next poll is refused too, and the worker exits on it as before. When such a refusal comes before any beat has extended the lease, the worker now backs off before its next poll as it does after a failed poll (up to 1 s, doubling per such item to 60 s), because the control plane re-queues the session's unanswered calls on that stop; the SDK worker polls again at once. A stop the control plane asks for is not followed by one. A heartbeat answered `409` is now retried, as the SDK worker retries it, instead of ending the run.

- **Work objects carry `"actor": null`, and a memory store's first archive moves its `updated_at`, as the reference's do** ([#680](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/680), [#685](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/685)) — Every work object the work API returns, from poll, list, get, metadata update, ack and stop, now carries `"actor": null`: every recorded reference body has the key, and the published schema lacks it, so the typed Go SDK files it under `JSON.ExtraFields`. The work `id` stays `work_…` where the reference uses the session's id, a deliberate difference [docs/DIVERGENCES.md](../DIVERGENCES.md) records. The first archive of a memory store now sets `updated_at` to `archived_at`, as the reference and every other archive route here do, and a repeat archive changes neither. Stores archived before the upgrade are backfilled: a migration moves their `updated_at` to their `archived_at`.

- **A graceful work stop of acked work goes `stopping`, and the worker's claim learns of it** ([#810](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/810)) — a graceful `POST …/work/{work_id}/stop` of `starting` work (acked, but no heartbeat yet) now answers `200` `stopping` instead of stopping the work outright, as the recorded reference service does. The worker's `NO_HEARTBEAT` claim on such work now answers `200` with `lease_extended: false`, `state: "stopping"` and `last_heartbeat: ""` instead of `412`, and changes nothing. The worker then force-stops the work, so its session is re-armed once. If no worker claims it, a poll finalizes it after its startup lease and the one-minute wind-down window. A sessions token now stays valid while its work is `stopping`, so a worker that learns of the stop late can still finish it; past the one-minute window it reaches only that work's heartbeat and stop. Every other failed claim still answers `412`, and a graceful stop of queued work still stops it outright. `last_heartbeat` keeps its format whenever a heartbeat exists.

- **Work Stop answers 200 with the work object, and a repeat stop is no longer a 409** ([#804](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/804)) — `POST /v1/environments/{environment_id}/work/{work_id}/stop` now returns `200` with the `BetaSelfHostedWork` after the transition, rendered as `GET …/work/{work_id}` renders it, instead of a bodiless `204`. The recorded reference service answers every one of its 27 recorded stops this way, which falsifies the reading 0.2.0 acted on when it moved this route to `204`. A stop of work already stopped, or a graceful stop of work already stopping, now answers `200` with the item unchanged instead of `409`, and re-arms nothing. The generated Go SDK's typed `Stop` now decodes the response instead of failing it, and `ant beta:environments:work stop` prints the object. The bundled worker accepts both this `200` and an older server's `204` or `409`.

- **A terminal grading settlement no longer depends on when a child's ending notice landed (#801)** — After a `satisfied` or `failed` verdict with budget left, or a failed grader call, the coordinator now chains only on client input or on a message from a child that is still live, never on an ending notice. Before, an archive notice landing during the grader's call ran an extra coordinator turn, while the same notice landing a moment earlier, or a child's "ended without reporting" notice, did not. An unread notice keeps `processed_at: null` until the coordinator's next request reads it.

- **A session whose MCP server its environment blocks is refused at create, as the reference refuses it (#571)** — Such a session used to be created and start running. It then emitted a `session.error` on every work cycle, because the platform checked a `limited` environment's networking only when dialling the server. `POST /v1/sessions` now answers 400 `invalid_request_error` with the reference's recorded message, which names each blocked server and host: `MCP server host(s) blocked by environment network policy: "<name>" (<host>). Add these hosts to the environment's allowed_hosts, or set allow_mcp_servers=true.` The session is never created. `allowed_hosts`, including a `*.` wildcard, and `allow_mcp_servers` admit a server as they did at dial time. A `self_hosted` environment, which has no networking, and an `unrestricted` one admit every server. A deployment run that hits the check now settles on `mcp_egress_blocked_error`, and a scheduled fire pauses the deployment. The dial-time check stays, because an agent's `mcp_servers` can change mid-session. **Upgrade note:** a create that used to succeed on such an environment now fails, and a scheduled deployment whose agent declares such a server pauses on its first fire after the upgrade; add the host to `allowed_hosts` or set the flag, then unpause it.

- **A thread an answer moves is written in processing order, a denial's result after a resume** ([#793](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/793)) — When a `user.tool_confirmation`, `user.tool_result` or `user.custom_tool_result` moves a thread, the send now makes the move itself, where the answer is consumed and in receipt order with any `user.interrupt` beside it, so an answer received ahead of an interrupt no longer lets the session fold idle on the gate it cleared and then run again (one thread's answers straddling another's interrupt in one send still move it once, registered in docs/DIVERGENCES.md). A resume's running pair follows the answer and precedes what the resumed turn reads: on the primary thread, a denial's `agent.tool_result` and a `user.message` posted beside the answer, as every recorded primary denial lists them. A thread left waiting on another call re-idles right after the answer, ahead of input still pending. A child's denial result stays ahead of the child's running event, and a denial that leaves another call waiting still writes its result at once, where the reference holds it until the thread resumes (docs/DIVERGENCES.md). A replayed request now answers a turn's tool calls in their order, which OpenAI-compatible backends may require. Rows already on the log keep their old order.

- **A message posted while a model request is in flight is read after the reply that never saw it, and `processed_at` is stamped when an input is consumed** ([#793](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/793)) — A `user.message`, `user.define_outcome` or delivered `agent.thread_message_received` that lands mid-request now replays after that request's reply and tool results, where the next request consumed it, instead of merged ahead of the reply. After an `end_turn` reply the chained request used to end on the assistant's turn, a prefill that Claude 4.6 and later models reject with a 400 `invalid_request_error` (https://platform.claude.com/docs/en/api/errors, "Prefill not supported"), so the session idled on `retries_exhausted`; on other routes the model continued its own reply. Existing sessions replay in the new order on their next turn, at one prompt-cache miss. The grader's and dreams' transcripts use the same order. `processed_at` is now stamped when the consuming request starts, 1 µs before its `span.model_request_start`, as the reference stamps it, not when the turn settles; `agent.thread_message_received` is null until then. Every `user.interrupt` is stamped on receipt, with any confirmation it supersedes. An outcome turns `running` as the request reading its `user.define_outcome` starts, never staying `pending` through that work. The list and stream still show each event at its receipt position.

- **A denied tool call is answered with the reference's sentence (#60)** — When a client denied a `user.tool_confirmation`, the `is_error` result the platform wrote carried the bare `deny_message`, or "The user declined this tool call." when there was none. It now carries the reference's text: `Permission to use <tool> has been rejected.`, followed by ` Rejection message: <deny_message>` when one was given. Every denial in the 2026-09-12 and 2026-09-19 recordings has one of these two forms. An MCP call is named as the model was offered it, `mcp__<server>__<tool>`. Results already on a session's log keep the text they were written with. Every recorded denial refuses a `bash` call, so how the reference names any other tool in this sentence is still an inference (#78).

- **A work item's `started_at` is stamped when it enters the queue, as the reference stamps it (#542)** — The work API rendered `started_at` null until a worker's first heartbeat, and cleared it again on every poll hand-out. The reference sets it on a freshly enqueued item still `queued`, re-stamps it when an item re-enters the queue, and leaves it untouched through poll, ack, heartbeat and stop. The 2026-09-19 self-hosted recordings show this for 11 enqueues and 2 re-queues, on `ant` 1.10.0 and 1.34.0. Enqueue now stamps it, and a poll that reclaims a dead worker's `starting` or `active` item stamps it afresh. Heartbeats no longer touch it, so a polled or acked item renders a timestamp where it used to render null. No client this project knows of reads the field. An item with no stamp takes its `created_at` at its next poll, ack or claim heartbeat. That covers an item enqueued before the upgrade, or one polled by a replica not yet upgraded. Nothing else is backfilled.

- **A commit's events are written in the order they are processed, as the reference lists them** ([#793](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/793), [#539](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/539)) — A `user.message` or `user.define_outcome` that wakes a session now follows the running pair it causes, on the list and the stream, for a send, a redirect, a create's `initial_events` and a dream stage. An interrupt follows the results and outcome ends it writes and precedes its idle pair, and `processed_at` now says the same. A send's answers keep their place among its interrupts, one thread's in the order its calls are processed with a denial's result beside it; an answer still queued behind an earlier call comes last, unprocessed. A report, a `send_to_agent` that wakes a child, and an ending notice follow the target's running event, and input that wakes nothing comes last. The POST echo keeps the posted order. Rows already on the log keep their old order, which an older brain replica still writes during a rolling upgrade; a client that reads these events by position sees them reordered. A child's resume of an idle session keeps this platform's shape, registered as deliberate in docs/DIVERGENCES.md. Archiving a session now marks a live outcome `interrupted` whatever its primary is parked on; GET used to report it as still live. A denial posted ahead of an interrupt of its thread now answers its call instead of being lost.

- **Thread messages name their peers the way the reference does** ([#675](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/675)) — `agent.thread_message_received` always names its sender now: a message from the coordinator carries its session agent's name in `from_agent_name`, which was `null`. `agent.thread_message_sent` names its target only when that target is a child, so a child's message to its coordinator omits `to_agent_name` instead of sending `null`. Both follow a recording of the reference, which contradicts the SDK's note that `from_agent_name` is absent for the primary agent. A client reading `to_agent_name` must accept the key being absent; the console already does. Rows already stored keep their nulls, and once every brain runs this release the model sees no change: replay renders any message from the coordinator, old row or new, as `[message from your coordinator]`, so no child's cached request prefix moves. A brain of an earlier release renders a row written since by the coordinator's name instead — beside new brains during a rolling upgrade, and for good after a rollback — which misses that child's cached prefix and can give one coordinator two names in one request, nothing worse; replace the brains together to avoid the upgrade window.

- **A spawned child's own event list opens with its status, then its task** ([#675](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/675), part 3) — A child a coordinator's `create_agent` spawns now lists `session.thread_status_running` before the `agent.thread_message_received` carrying its task, the order every recorded reference child shows; it used to list them the other way round, as v0.4.0 does. A child spawned before the upgrade, or by an older brain replica during a rolling upgrade, keeps that old order for good: its log is append-only, lists in seq order, and is not backfilled. The session and primary thread views are unchanged: each spawn still reads `session.thread_created` and then `agent.thread_message_sent`, with the child's status cross-posted after them. All four events still commit in one transaction; docs/DIVERGENCES.md records what that leaves different from the reference.

- **A query string that does not parse is refused rather than half-read** ([#796](https://github.com/OpenSDLC-Dev/managed-agent-platform/pull/796)) — Go's query parser silently drops a pair it cannot decode (`%zz`, or a pair holding a bare `;`) and, past Go's default ceiling of 10,000 pairs (GODEBUG `urlmaxqueryparams`), the whole query, so such a parameter used to read as never sent: `DELETE /v1/memory_stores/{id}/memories/{mid}` deleted without its `expected_content_sha256` precondition, `GET /v1/agents/{id}?version=1%zz` served the latest version, and the agent, session, session-event, deployment, deployment-run, dream, skill, file, memory-store, memory and memory-version lists answered with everything their filter should have excluded. Those routes, and the thread-event list that shares the session-event list's handler, now answer 400 `invalid_request_error` ("malformed query string: …"); every other route reads its query as before. The SDK and the `ant` CLI encode every pair they send, so they meet the 400 only past the ceiling — 10,000 `types[]` values on the session-event list, say — where such a list used to answer unfiltered. The reference's own answer is unrecorded ([#78](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/78)).

- **The primary thread's running pair is emitted session-first, the order the reference gives it** ([#674](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/674), part 2) — Wherever `session.status_running` is emitted beside the primary's `session.thread_status_running` (a session woken, a session created with `initial_events`, the brain's reclaim of a running session), it is now appended first; this platform had emitted the thread event first, where every `session.status_running` in the recorded reference sessions comes before the primary's. The idle pair already matched (the thread event, then the session event) and is unchanged; `rescheduled`, never recorded, keeps the idle order. Differences stay open on [#793](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/793), recorded in docs/DIVERGENCES.md: the pair still follows the `user.message` that wakes the session, where the reference writes it ahead of the message; and a child's resume of an idle session pairs `session.status_running` with the child's own thread event, now also session-first, and leaves the primary idle, where the reference pairs it with the primary's and wakes and later idles the primary. The executor now refuses any other URL with an error result, and fetches the given URL exactly as it was written, so nothing the model appends, a fragment included, is sent. A URL counts as given when it appears in what a person wrote into the session (a message, an outcome, a denial's message, an operator's system message, a web_fetch call they confirmed), or in a successful `web_search` or `web_fetch` result, a fetched page's links included. Messages between agents, failed results and other tools' output do not count, and a URL longer than 8 KiB is refused, as is one the session holds too many URLs on its host to check. Redirects stay unchecked: the reader backend follows them itself and does not report where it landed ([#831](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/831)). An agent that relied on fetching a URL it composed, or a bare domain written without `https://`, now gets an error and can find the page with `web_search` first.
