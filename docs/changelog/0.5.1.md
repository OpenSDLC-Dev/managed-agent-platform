## [0.5.1] - 2026-10-04

### Fixed

- **A memory store whose landing failed no longer turns untrusted for the sandbox's life** ([#867](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/867)) — when a store failed to land in a sandbox (a failed memories read or listing, a failed write), its directory could fill with no marker: the same run's sync pulled into it, the agent wrote into it, or the reaper's sync did. The next run then held the store untrusted and pull-only until the sandbox was replaced, and withheld every edit the agent made there. Now the executor and the BYOC worker write the marker first, with an empty baseline ahead of it, as soon as the directory is found empty and before the store is read. A landing that fails after that leaves a marked directory, and the next sync completes it: the store's memories are pulled, the agent's files are pushed, and the store wins any path both sides hold. A sync that finds an empty directory with no marker file now lands it with the marker, as the reference worker does. This covers the run's syncs and the reaper's alike. A directory the marker never reached can still turn untrusted if the agent writes into it before a sync lands it. Examples are a failed marker write, a failed read of the store row on the executor, or a directory listing that does not answer.

- **A file mount that is gone, or that failed to land, no longer re-lands every other mount over the agent's edits** ([#877](https://github.com/OpenSDLC-Dev/managed-agent-platform/pull/877)) — Re-provisioning a live sandbox re-streamed every file mount whenever one was missing (the agent moved `a.csv` away) or an earlier pass had failed to land one (its file deleted or expired, or a write fault) — the latter on every turn while that file stayed gone — overwriting what the agent had done to the others. The `.files_materialized` marker, its format unchanged, is now read per mount: a pass lands only the mounts it does not record under the file the session names at that path now, and those one presence probe finds gone, and keeps the rest. The probe lists the absent paths in one framed exec per ~120 KiB of paths (44 for 5,000 mounts of 1 KB paths), and a probe that does not answer keeps what is there. A marker that cannot be read or parsed still re-lands the whole set. The executor and the BYOC worker alike.

- **On Kubernetes, a command SIGKILLed just past its deadline by something other than its watchdog is reported as timed out, on a loaded cluster too** ([#838](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/838)) — a command that had killed its in-pod watchdog and was then SIGKILLed less than 0.5 s past its deadline, by the node's OOM killer say, could come back as exit 137 with `TimedOut: false` when the cluster was busy. The only witness was the pre-deadline liveness probe, an exec into the pod that under load answered after the kill. The exec wrapper's run-time record from #832 now also reads `/proc/uptime` just after the watchdog's launch, and a SIGKILL that ends a run longer than the deadline less 50 ms, counted from there, is a timeout. That is the line the probe already drew, from a later starting point. The record only ever adds a timeout, and only one a punctual probe would also have given, unless the wrapper stalls between reaping the command and its last reading or the node is suspended mid-command (`/proc/uptime` counts suspended time), as #832's overrun record already allowed. The docker backend is unchanged.

- **A command past its deadline dies with its children on an image that sets `SHELLOPTS`** ([#866](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/866)) — on Docker, an image with `ENV SHELLOPTS` set to anything, even nothing, let the exec wrapper's job control (`set -m`) reach the command's shell through the exported variable. That shell put each of its jobs in a process group of its own, so the deadline's group kill took the shell and missed its children: the timeout was reported, and a `sleep 300` ran on until the container died. An image whose `SHELLOPTS` names `monitor` did the same on Docker, and worse on Kubernetes, where the command was reported as exiting 0, not timed out, while it ran on. Both exec wrappers now turn job control off before the command starts; the rest of the image's `SHELLOPTS` still reaches it. A startup file or command that turns job control back on itself takes its jobs out of the kill's reach, as `setsid` does ([image contract](../self-hosted-security.md)).
