## System overview

An open-source, self-hostable platform for long-horizon agents, wire-compatible with
Anthropic's Claude Managed Agents: the real `ant` CLI and the Anthropic SDKs drive this
server unchanged. An agent is three independently-swappable pieces:

- **Session** — an append-only **event log** in Postgres. The single source of truth:
  all durable state lives here, and everything else can be rebuilt from it.
- **Brain / harness** — the loop that calls the model and routes tool calls.
  **Stateless and horizontally scalable**: a crashed brain loses nothing, because any
  fresh brain replays the log and continues.
- **Sandbox ("hands")** — a disposable per-session container that runs tools. Cattle,
  not pets: a dying container is one tool-call error, not a lost session.

```
  ant CLI / Anthropic SDK ──REST(x-api-key)──▶ ┌── controlplane ───────────────────────────┐
  (wire-compatible)                            │  /v1/agents /environments /sessions       │
                                               │  /sessions/{id}/events  (POST + SSE)      │
                                               │  /environments/{id}/work/* (BYOC worker)  │
```

## Process topology

Four binaries under `cmd/`, each independently deployable and scalable; all state in
Postgres, all coordination through it:

| Binary | Role |
|---|---|
| `controlplane` | The wire-compatible REST surface: resource CRUD, the event log endpoints (POST/list/SSE), the work API for BYOC workers, auth (management `x-api-key`, worker environment keys), and the session state machine. |
| `brain` | The harness pool. Claims `model_turn` work, replays the session's event log to rebuild context, calls the model provider, writes the resulting events, enqueues tool work, suspends. |
| `executor` | The built-in sandbox worker for platform-managed (`cloud`) environments. Claims `tool_exec` work, runs the tool inside the session's sandbox container, posts `agent.tool_result`. Also claims `web_exec` work — web_fetch/web_search, run in its own process with no sandbox, for **both** environment kinds — `outputs_harvest` work, the deliverables snapshot of `/mnt/session/outputs/` a cloud session's outcome-grading cycle begins with, and `mcp_exec` work — the MCP tool discovery that fills `mcp_catalogs`, likewise in its own process with no sandbox and for **both** environment kinds, though nothing enqueues one yet: the driver is claimed and exercised by its tests, and the production path that schedules discovery arrives with the brain's `mcp_toolset` expansion (plan 29 slice 4). |
| `worker` | The distributable BYOC worker for `self_hosted` environments. Same pull protocol as the executor, run on customer compute, posting `user.tool_result` — the real `ant beta:worker` works against the same API. |

Processes never talk to each other directly. The brain and the executors communicate
only through the control plane's event log and work queue — which is what makes
"customer-run worker with zero inbound network access" the same code path as the
platform's own executor, just deployed elsewhere.

## Execution flow

**Fully asynchronous through the event log and the work queue.** One turn:

1. A client POSTs `user.message`; the session goes `running` and a `model_turn` work
   item is enqueued.
2. A brain claims it, replays the log into provider messages, and streams the model's
   response — writing `agent.message` / `agent.thinking` events (with opt-in
   `event_start`/`event_delta` SSE previews) and `span.model_request_start/_end`.
3. A tool call becomes an `agent.tool_use` event plus a `tool_exec` work item; the
   brain suspends (it holds nothing in memory a crash could lose). A turn carrying a
   web tool (web_fetch/web_search) enqueues a `web_exec` item instead — the platform
   executor answers the web calls in its own process (both environment kinds, no
   sandbox) and chains the `tool_exec` for any sandbox tools on the same turn, so a
   BYOC worker never observes an unanswered web call.
4. For a platform-managed (`cloud`) environment the executor claims the item straight
   off the Postgres queue (`FOR UPDATE SKIP LOCKED`, lease + reclaim); for a
   `self_hosted` environment a BYOC worker claims the same kind of item over the wire
   work API (`poll`/`ack`/`heartbeat`/`stop`, lease expiry, dead-worker reclaim) — the
   same pull semantics at two deployment points. Either materializes the agent's
   skills into the freshly provisioned sandbox (`{workdir}/skills/<name>/`, versions
   resolved at use time, per-skill failure tolerated), runs the tool, and posts the
   result event (`agent.tool_result` platform-managed, `user.tool_result` self-hosted).
5. The commit that appends the result also enqueues the next `model_turn` — only once
   every tool use in the turn is answered. A brain claims it (brains wake by polling the
   queue; Postgres LISTEN/NOTIFY serves the SSE fan-out, not the brain), replays, and
   continues until the model stops calling tools, then writes `session.status_idle`
   with `stop_reason.end_turn`.

**Outcome grading** (plan 21). A session with an active outcome (`user.define_outcome`)
does not idle on `end_turn`: the settlement commits `span.outcome_evaluation_start`,
flips the outcome entry to `evaluating`, and schedules a grading cycle — on a cloud
environment by enqueueing an `outputs_harvest` item, whose executor-side settlement
snapshots `/mnt/session/outputs/` into the files registry (session-scoped rows,
downloadable through `GET /v1/files`) and chains the grading `model_turn`; on
self_hosted by requeueing the turn item directly (the platform cannot reach a BYOC
sandbox — grading is transcript-only there). The grading claim runs one grader call —
rubric + deliverables + transcript, no tools — and settles the verdict under the
session lock: satisfied/failed/max_iterations idle the session, needs_revision feeds
the grader's findings back and runs another agent cycle.

**Permissions / human-in-the-loop.** A tool whose resolved `permission_policy` is
`always_ask` suspends the session *before* execution: the brain writes
`session.status_idle` with `stop_reason:{type:"requires_action", event_ids:[…]}` naming
the blocked `agent.tool_use` events (stamped `evaluated_permission:"ask"`). A client
answers each with `user.tool_confirmation{tool_use_id, result:"allow"|"deny",
deny_message?}`; allow releases the tool to the queue, deny synthesizes an
`is_error:true` `agent.tool_result` carrying the deny message, and the turn resumes
either way.

**Interrupting.** Not every stall has an owner to wait for: a `self_hosted` worker fleet
that never comes back, a custom tool the client never answers, a confirmation nobody
sends. `user.interrupt` is the one call that ends a turn from outside it — the control
plane answers whatever the turn left outstanding, settles the session `idle` on
`stop_reason.end_turn`, and cancels the session's work items so the claimant still running
it commits nothing. Sent together with a `user.message`, it is also how a client redirects
a working agent in one request.

**Crash recovery is replay.** Sessions are never bound to a brain: any brain can pick up
any session's next turn from the log. A sandbox container dying surfaces as one
tool-call error; a worker dying strands its lease, which `poll` reclaims after expiry.

## Wire-compatibility model

The public REST API mirrors Anthropic's Claude Managed Agents resource model — paths,
JSON fields, ID prefixes (`agent_` `env_` `sesn_`/`session_` `sevt_` `work_` …),
pagination and error envelopes, and the `{domain}.{action}` event taxonomy (SSE deltas
use `content_delta`, not the Messages API's `content_block_delta`). The typed schema in
the pinned `anthropic-sdk-go` checkout is the ground truth; client behavior comes from
the `ant` CLI source (see [REFERENCE_PROJECTS.md](./REFERENCE_PROJECTS.md)). Where we
deliberately diverge — or infer behavior the references don't pin down —
[DIVERGENCES.md](./DIVERGENCES.md) is the single registry; the verifier resolves
wire-compat findings against it.

Not everything an operator needs is on that wire. The reference mints environment
keys from its **console**, on a private backend no SDK or CLI route touches, so a
self-hostable platform has to own that surface — and it lives under `/api/`,
deliberately outside `/v1`, where nothing can be mistaken for or collide with what
the real `ant` CLI speaks. The convention for such a surface is **mirror, don't
invent**: its paths copy the reference console's own segment-for-segment
(`/api/oauth/organizations/{organization_id}/environments/{environment_id}/tokens…`,
observed live 2026-08-10), the observation is dated in the plan, and every
departure from what was seen is registered in DIVERGENCES.md like any other. Auth
is the management `x-api-key`, now through `dispatchAuth`'s own `/api/` arm —
plan 30 reached the same lane by fallthrough (no other predicate can match an
`/api/` path, since each is either a `/v1/` prefix test or the gate's exact
equality against the fixed `/internal/v1/gate/config`) and asked that a future
off-`/v1` lane re-check that rather than inherit it; plan 31 slice 2 was that
lane and made the arm explicit. The namespace is off-wire and console-shaped,
not a separate permission tier for a key-authenticated caller — with SSO
configured it does become the first **role**-gated surface, at `admin`, which
constrains humans and changes nothing about what a management key may do.
Future console-facing endpoints follow the same rule rather than opening a
naming argument — and must re-check that auth reasoning rather than assume a
blanket `/v1/` prefix rule covers every lane.

Model access is **config-driven**: a provider is constructed from `protocol`
(`anthropic` | `openai`) + `model` + `base_url` + `api_key` (+ optional headers), and a
`model_providers` routing table maps an agent's model string to a provider instance.
The Anthropic-protocol adapter is near-zero-conversion and works against any endpoint
speaking Anthropic Messages; the OpenAI-compatible adapter is the platform's one lossy
conversion seam, confined to `internal/provider/openai` and tested hard. Providers are
built with `WithoutEnvironmentDefaults`, so ambient `ANTHROPIC_*` credentials can never
leak to a configured third-party endpoint.

## Package reference

What each package does and where its pieces live, in repo-layout order. Descriptions
originate from the delivery-time records (migrated from HISTORY.md, 2026-07-18) and were
freshness-checked against the code on migration; treat the code as authoritative when
they drift. Where one file carries several distinct responsibilities, it gets one row per
responsibility (`file.go — aspect`). Ordering is by layer: the domain and wire surface
first, then the execution chain, then the shared infrastructure.

### internal/domain

Zero external dependencies (stdlib only), enforcing the rule that the domain layer never
depends on adk-go, genai, or a provider SDK.

| File | Contents |

| `id.go` | `ID` with wire-compatible prefixes (`agent_`, `env_`, `sesn_`, `sevt_`, `work_`, `vlt_`, `sesrsc_`, `depl_`, `drun_`, `file_`, `skill_`, `skillver_`); accepts the alternate `session_` form on input. CSPRNG + Crockford base32 generator (`idAlphabet`, shared with `Valid`). `Valid()` shape-checks an id (a known prefix + a Crockford token) so the API rejects a malformed or unstorable path/query id (404/400) before it binds as a 500. |
| `event.go` | Full `{domain}.{action}` event taxonomy (user / agent / session / span) plus stream-only `event_start` / `event_delta`. Helpers `Domain()`, `Inbound()`, `Persisted()`. `Event` envelope, `StopReason`, `ContentBlock`. |
| `session.go` | `SessionStatus` state machine (`idle` / `running` / `rescheduling` / `terminated`), `Usage`, `Scope` (org/workspace/project), `Session`, `SessionResource`. |

### internal/api

The wire-compatible control-plane surface: resource CRUD, the events endpoints and their
state-machine triggers, auth, and the work API.

| File | Contents |
|---|---|
| `server.go` | Route table (Go 1.22 method patterns) + `NewHandler`. **Updates are `POST /v1/{resource}/{id}`, not PATCH** (SDK is authoritative). Envelope-shaped 404/405 fallbacks. `?beta=true` and `anthropic-*` headers accepted and ignored. Per-request OTel server span continuing the caller's `traceparent`. Auth dispatch runs before the router on the escaped path: work routes take the environment Bearer key; the session-events subtree, the bare session GET, the skill read+download routes (`isSkillReadPath`), and the single file-content route `GET /v1/files/{id}/content` (`isFileReadPath`) are dual-auth (worker Bearer or management `x-api-key` — the worker materializes skills and file mounts over its environment key); everything else — including the rest of the `/v1/files` registry (the metadata GET, list, mutations) and the session `resources` sub-endpoints — is management-only. The file lane is narrower than skills' by design and its download handler is environment-scoped — it serves a worker only files some session in its own environment mounts (`files.go`). **With identity configured** (plan 31 slice 2, #56) the management arm gains a second credential and the `/api/` console namespace its own explicit arm: `dispatchManagementAuth` tries `x-api-key` first and the human lane only when no key is offered, so a Bearer or an assertion riding alongside a management key can never vouch for it and a caller cannot attach a second credential to change which role check applies; a **bad** key stays on the machine lane and 401s rather than falling back. "Offered" is one predicate (`apiKeyOffered`) reading **every** value of a field HTTP permits to repeat — `Header.Get` returns only the first, so an empty `x-api-key` ahead of a real one used to read as no key at all and moved the request onto the human lane — and a repeated field counts as offered whatever its values, so it reaches `requireAPIKey`, which refuses a duplicate outright. One rule in both places: an ambiguous credential is a 401, never a lane change. A single empty value still counts as absent, which is the pre-existing rule the worker lane relies on. `Authorization` has the same duplication exposure and needs no such treatment: `bearerToken` reads `Get`, so a leading empty field makes the request look like it carries no Bearer — which denies, never over-authorizes. `dualAuth` splits the Bearer branch once more — a JWT silhouette to the human lane, anything else to the worker's environment key — which is one-way safe because a key this platform minted is `sk-map-env01-` plus base64url and holds no dots (a grandfathered pre-0021 key whose value an operator chose could misroute and then fail verification: a 401, fail-closed). The route adapters take a minimum role (`s.handle`/`s.handleNoContent`, and `roleGate` for the three streaming routes that have no adapter), so every route states one beside its path. Slice 2 registered all of them at `identity.RoleNone` — which denies every human — except the console environment-key surface at `identity.RoleAdmin`; **slice 3 annotated the remaining 53** per plan 31's matrix (23 `viewer` reads, 25 `developer` mutations, 5 `admin` credential surfaces), for 56 identity-reachable routes at the end of that plan, relaxing the floor one route at a time rather than opening it wholesale. Plan 32 slice 2 added the three management-key console routes at `admin`, making it 59. The `admin` tier bounds who may read, write, mint or validate a secret — **not** every route that touches one: a `developer` can still destroy credentials through their container (archiving a vault nulls every credential's ciphertext, deleting one cascades them away, deleting an environment cascades its keys), and the session-resource routes seal a `github_repository` token at `developer` because mounting a repository is the session lifecycle that tier exists for. The registrations still at `RoleNone` are the eight work-API routes and the gate-config read. Normally spelled they dispatch to a machine lane before the minimum is read, so it means "no role to check" — but that is not the whole story, and the difference is load-bearing: `dispatchAuth` classifies `EscapedPath()` while `ServeMux` matches the decoded path, so `/v1/environments/{id}/%77ork` misses `isWorkPath`, takes the **human** lane, and reaches the work registration once decoded. `RoleNone` is what refuses it (`403 permission_error`, pinned by `TestAnEncodedPathCannotSlipPastTheWorkLane`) — a live denial, not a placeholder. Under a management key those handlers are reached with `requireRole` a no-op, and what closes them is their own scoping (`workScope`'s environment check, `getGateConfig`'s empty session id). Three tests keep the constant's two uses apart: `TestEveryIdentityReachableRouteDeclaresARole` parses this file's registrations and fails on an identity-reachable route left at the floor, on a machine-lane route given a role, **and** on one declaring no role at all (nothing at runtime can do this — `http.ServeMux` does not expose its patterns, so a request-driven test could only check the routes someone remembered to list); `TestTheMatrixCoversEveryAnnotatedRoute` joins those registrations to the enforcement table in both directions, so a route in one and not the other fails; and `TestRoleMatrixIsEnforcedOnEveryRoute` drives four callers — including one whose claims map to **no** role, the only tier denied everywhere and so the denied-case control for the `viewer` routes — against every route over real HTTP. With `IDENTITY_MODE` unset or `disabled` the verifier is nil and every branch above collapses to what it was — byte-for-byte on every request shape but the repeated `x-api-key` just described, which `requireAPIKey` refuses in **all** modes. That refusal is the one behaviour this plan changes in a default deployment: deliberately not gated on the verifier, because one rule in both places is what stops lane selection and authentication disagreeing about which value is the key, and it can only ever deny a request no client sends. |
| `auth.go` | `x-api-key` middleware against `api_keys` (SHA-256 hash only). A key authenticates only while `status = 'active'` and unexpired — expiry is evaluated **in the query, against the database's clock**, so a lapsed key stops working the instant it lapses and no sweeper can be down when it does; `expired` is therefore derived, never stored. `EnsureAPIKey` gives **rotation-by-restart** semantics: ensuring a new key under a name archives the previous ones (archive-before-insert), so a leaked `CONTROLPLANE_API_KEY` dies on rotation, and it records a `partial_key_hint` — the only part of a key that survives issuance, since the plaintext is hashed, masked by anchoring on the known issued-key prefix rather than on the value's last separator (base64url's alphabet contains `-`, so a last-separator rule would publish most of a minted key against an unsalted hash). Adopting an existing row **clears** its `created_by` and `expires_at`: naming a value in `CONTROLPLANE_API_KEY` makes it env-var-managed, and an inherited issuer would put the bootstrap key outside the index below while an inherited expiry would let the process boot over a credential `authenticate` already refuses. `api_keys_one_live_unissued` keeps "one live key per name" a schema invariant for the rows `EnsureAPIKey` owns (those with no `created_by`), so concurrent mints fail the loser; console-issued keys are deliberately outside it, because the reference lets several live keys share a name (plan 32). Authenticated key ID becomes the audit-only `sessions.created_by`. |
| `identitylane.go` | The **human lane** (plan 31 slice 2, #56): `identityCredential` reads the credential the deployment's mode owns — in `oidc` mode a Bearer with the JWT silhouette (`identity.LooksLikeJWT`), in `trusted_proxy` mode the configured assertion header and **never** a Bearer, so a caller cannot present a token the proxy did not vouch for. `requireIdentity` verifies it, logs the closed-vocabulary `Reason()` against the request id, provisions the principal, and puts an `identityPrincipal{ID, Role}` on the context. Provisioning sits on the authentication path deliberately: a verified token already proves the human exists, and a request whose author could not be recorded should not proceed to act as them — so a database failure here is a 500, not a 401 that would send an operator hunting the IdP. `requireRole` is the whole enforcement point and applies to this lane alone (a machine credential carries no role, so it returns nil without reading the minimum). | `envauth.go` | Environment-key auth: the `Authorization: Bearer` resolution and the session-scope middlewares that confine a worker to its own environment. Resolution rejects revoked, expired and unknown keys through one branch, so the 401 is identical for all three. |
| `envkeys.go` | Environment-key issuance (plan 30, #43): `IssueEnvironmentKey` generates the secret server-side (256 CSPRNG bits behind an `sk-map-env01-` prefix), returns it once and stores only its SHA-256 hash, with a name and a one-year `expires_at`; `ListEnvironmentKeys` pages an environment's live keys newest-first; `RevokeEnvironmentKey` retires one — idempotent, and scoped to the owning environment so a key id is neither revocable nor confirmable from another. | `consoleapi.go` | The **console API** (plan 30 slice 2, #43) — the off-wire operator surface over `envkeys.go`, under `/api/oauth/organizations/{org}/environments/{id}/tokens…` mirrored from the reference console's private backend: `POST …/tokens` issues (200, RFC 6749 `{access_token, expires_in}` — the plaintext's only appearance, and refused on a `cloud` or archived environment), `GET …/tokens` lists under the dialect's offset-paginated `{data, pagination}` envelope with a nullable `expires_at`, `POST …/tokens/{token_id}/revoke` retires one (204, idempotent). Issuance runs its kind/archive check and its insert in one transaction under `FOR SHARE` on the environment row — the idiom session create uses — so a concurrent archive cannot mint a key on an archived environment and a concurrent delete answers 404 rather than a foreign-key 500; the token response carries `Cache-Control: no-store` (RFC 6749 §5.1), since that body is the plaintext's only appearance. `{org}` accepts only the reserved `"default"`; `{token_id}` is shape-checked by `domain.ValidWithPrefix` rather than `checkID`, because `envkey_` stays out of `domain.knownPrefixes` — that set is what every `/v1` path validates an id against, and admitting a private prefix would widen all of them. Plan 30 gave it no `dispatchAuth` arm — no other lane's predicate can match an `/api/` path (four test a `/v1/` prefix or segment, and the gate's tests exact equality against `/internal/v1/gate/config`), so `/api/` fell to the management `x-api-key` by construction — while asking that a future off-`/v1` lane re-check the reasoning rather than inherit it. | `apikeys.go` | Management-key issuance and listing (plan 32 slice 2, #378), the `api_keys` half of what `envkeys.go` is for `environment_keys`. `IssueManagementKey` mints `sk-map-api01-` plus 43 base64url characters, stores the hash and a `partial_key_hint`, and records the issuer — non-NULL `created_by` being exactly what puts an issued row **outside** `api_keys_one_live_unissued`, so issued keys may share a name as the reference allows while `EnsureAPIKey` keeps one-live-per-name over the rows it owns. `ListManagementKeys` returns every row newest-first with no paging: archived ones, because the reference returns them and its console filters client-side, and the env-var-managed one, because a listing that hid the credential the caller is authenticating with would misdescribe what can reach the API. `managementKeyColumns` is the single spelling of the projection every read shares, and where `expired` is **derived** — `status = 'active' AND expires_at <= now()`, the exact complement of `authenticate`'s liveness test, on the same clock, so a listing can never call a key active that the next request is about to refuse. Only an `active` row derives; a disabled key keeps reporting `inactive` past its expiry (INFERRED in docs/DIVERGENCES.md — the reference's own rendering of that combination is unobserved). |
| `consoleapikeys.go` | The **management-key console surface** (plan 32 slice 2, #378): `POST`/`GET` on `/api/console/organizations/{org}/workspaces/{workspace}/api_keys` and `POST …/{key_id}`, all three at `admin`. The prefix is `/api/console/`, not the `/api/oauth/` above — the reference uses both and each surface keeps the one it was recorded under. Issuance returns the whole resource plus `raw_key`, which is **not** the RFC 6749 envelope `envkeys.go` returns: the reference runs two dialects on two surfaces and each is mirrored where it belongs. The listing is a **bare array**, a third collection shape for the same resource beside the Admin API's `{data, first_id, has_more, last_id}` and this platform's own `{data, next_page}` — and the only one we serve, since there is deliberately no `/v1` twin (both absences registered in docs/DIVERGENCES.md). `expires_at` is the caller's optional absolute instant with no duration vocabulary; absent means never, the spelling the reference's console uses, and a past instant is refused rather than minted dead. The update route reads the row `FOR UPDATE` for two decisions. A key nobody issued is managed by `CONTROLPLANE_API_KEY` and is listed but not the console's to change — renaming it would break rotation-by-restart, which archives the incumbent by name, and leave two live credentials under one name. And `archived` is **terminal**: a patch that would move a row out of it, or rename one in it, is refused and points at `inactive` for the disable that can be undone — otherwise two of the three states mean the same thing and an operator who retired a key cannot rely on it. Re-archiving is not a transition out and is accepted as a no-op, so a retried Delete is not an error. A third refusal covers the state where the row would change but nothing usable would: re-activating a key past its `expires_at`, which this route cannot extend, would answer 200 with a resource reporting `expired`. All three are INFERRED — the reference's behaviour on each is unobserved. |

Two shapes are normalised to reach that fallback rather than defeat it: an *explicit* empty text block, which a server may legally send and which would otherwise be that rejected block, and a resource carrying no bytes either way — an empty file read over MCP — which becomes text naming its address rather than a document whose source holds nothing. `capMCPBlocks` then holds the whole answer to `toolset.MaxOutputBytes`, the budget a built-in tool's output gets — blocks charged their marshalled size in order and kept or dropped whole (half a base64 payload decodes to nothing), a trailing block naming what was dropped. A leading block is exempt when every string inside it was already capped where the block was built (`alreadyCapped`: a text block, or a document whose source is text — body through `toolset.CapOutput`, and the two labels a document carries about its resource through `capLabel`, a 2 KiB ceiling that is what keeps the exemption's premise true, since a URI is a title and a server sending megabytes of one is using a label as a payload), so an over-long answer of either shape is truncated rather than dropped — without the document arm the cap on a text resource could never reach the log at all, since a capped body plus its wrapper always exceeds the whole budget. The exemption stops there: a leading image or base64 document is bounded by nothing but the transport's megabytes and has no truncation to fall back on, so an over-budget one is dropped like any other, because a result saying the image was too large is something a model can act on where a half-decoded payload is not. The pass as a whole is bounded by the same `Config.MCPPassTimeout` discovery uses, and for the same reason: the calls are serial, the endpoints are third-party, and this process runs one work item at a time. It is bounded differently in one respect — the budget is checked *between* calls and never cancels one, because a call cut mid-flight would be answered as though the server had failed, and a tool with a side effect would have run with nothing on the log saying so. So a pass overruns by at most one call, commits the answers it did make, and leaves the rest outstanding for the chain below to hand the item back for; nothing runs twice. The first call is made whatever the budget says, or a bound short enough to have expired before the loop would answer nothing, requeue, and spin the queue instead of slowing it. `answerMCPCalls` is the one transaction — results, follow-on work, and the item's fate together, all-or-nothing like the web driver's, so a dead context re-runs the unanswered calls rather than half-settling. | `brain.go` — the turn | Claim → replay → generate → **settle the turn atomically**: the emitted events (`agent.message`, tool intents), `span.model_request_end`, the status change, the usage fold, the processed watermark, and the work item's fate are ONE settlement transaction under the session row lock, with the queue's lease proof inside it. (Two things commit mid-stream, outside it: `span.model_request_start` and completed `agent.thinking` events — a brain that dies mid-turn can leave a dangling span start or a duplicate thinking event on the log; replay skips both. The recorded crash-window residue.) That settlement commit is both the liveness guarantee (API triggers serialize on the same lock — a tool result posted mid-settle either sees the live item, suppressed, or the completed one, enqueued; never the gap) and the integrity guarantee (a brain that lost its claim rolls the settlement back — the log never carries a loser's tool intents, which could never all be answered and would poison every future replay). A turn is classified on the tool blocks it produced, not on the stop reason they arrived with — nothing in the Messages schema ties the two (`max_tokens`, `stop_sequence`, `refusal` and a non-compliant `end_turn` can each carry a complete tool block, and the reference SDK's own agentic loop reads the blocks for that reason), and settling such a turn as finished would commit intents nothing ever runs (#181). Both writes are **atomic**: the bytes land under a temporary name in the target's own directory (`filefault.go`'s `TempName`, prefix `.map-write-`) and are renamed into place, so a transfer that fails part way through leaves the target holding what it held — or nothing, where there was nothing — and a failure the write itself sees sheds the residue rather than leaving a partial mount on the disk (a write whose exec could not be run, or whose shell was killed before it could clean up, leaves what it delivered — under the temporary name, never the target's; docker's rename-refused route is the one where the sandbox uid *cannot* shed it — the daemon extracted the temporary as root into a directory that uid cannot write, measured on non-root images — so there the daemon is asked to take it back: an empty archive entry extracted over the temporary, executing nothing, leaving the name without the payload. Best effort, deliberately — it raises no error of its own, and a daemon that refuses it leaves the residue the sandbox user already could not shed. The **bulk** write is covered on the same terms (#316): its shed is the sandbox user's `rm` too — in the rename script and in the discard exec alike — so both passes now *name* on stdout what that `rm` could not take (a member by its manifest index, the two bookkeeping files as `m`/`d`), and the docker backend empties exactly those in **one** archive, because a batch refused under a root-owned parent leaves every member behind at once and ten thousand round trips is not a cleanup. A *successful* batch is asked too, its last act being the `rm` of the two bookkeeping files the same root extraction landed in the workdir. The report steers nothing: the shell counts a manifest the sandbox can rewrite, but the index is resolved against the platform's own list, so what is emptied is always one of the paths that batch chose. Two things about the report are the sandbox's to attack and are answered rather than assumed — an image owns this stream before the script does (`bash -c` sources `BASH_ENV`), so only what follows the shed's own opening line counts and a stream without one is no report at all; and the manifest the shed walks is a file in the sandbox's workdir that a command in there can delete, which would leave the pass with nothing to name and stranded every member, so a shed that lost its list says *that*, and the one branch that knows the members were delivered (the rename's reported fault) answers it by emptying the platform's whole list instead. The rename's own exec-error branch keeps `rm` and nothing more, for the single write's reason above; and unlike the single write's, this emptying needs the shed exec to have run at all — a sandbox that can no longer exec keeps a failed batch's payload, the alternative being a HEAD per member). Being a rename, it replaces the *name*: a symlink at the target is supplanted by a regular file (what the docker daemon's extraction always did — the backends now agree), and the parent directory must be writable. The target's permission bits would go with the name too, so both backends put them back first — the temporary file is chmod'd to the target's mode before the move (#204), so a script made executable in bash survives being rewritten; only an existing regular target has bits worth carrying (one that did not exist lands 0644 on both backends, fixed by the platform rather than by the image — a tar header on docker; on k8s a `umask 022` the write script sets before its `tee`, #212, and a `chmod 0644` on the file it creates, because a parent directory's default POSIX ACL decides those bits over the umask, #213 — and a symlink's own mode is not taken, `stat -c %a` being an lstat that would report its 0777). Docker's temporary file is the daemon's, not the sandbox user's, so an image whose default user is not root cannot chmod it and lands 0644 where k8s preserves the mode (#209). A target that cannot be renamed onto at all — a bind-mounted file, a device node — is refused with `ErrNotReplaceable` before the move, identically on both backends, by the shared `__map_unreplaceable` probe, asked so the classification never depends on the write being able to start: k8s's write script asks it twice — before creating the temporary file (a read-only root refuses that creation), draining the refused body before exiting because an early exit that leaves a large body unread deadlocks the exec stream (its three failure branches — a refused `mkdir`, a temporary that cannot be created, a `tee` that dies part way — drain the same way, #304), and again after the body lands, just before the rename, where docker's rename has always asked — and docker — whose daemon refuses the archive PUT outright under a read-only rootfs, before any script — asks it in an exec of its own when the PUT fails (#205, #303); the node or mount is left what it was, neither supplanted nor written through, and bash redirection remains the way to write through one (#205). `WriteFiles(files []FileWrite)` is the **bulk** write: a whole set of files costs a fixed couple of execs — one on k8s, two on docker — where the same files written one at a time cost one exec each, most of what a small write costs, and up to 10,000 of them for one skill (#206). `bulkwrite.go` holds the half the backends must not drift on: `NewBulkWrite` builds one archive carrying a manifest (`tmp\0target\0` per member), a deduplicated parent-directory list, and one entry per member under a temporary name **in its own target's directory** (so each rename stays inside one filesystem, and is therefore atomic); the `__map_bulk_rename` shell both backends embed then walks the manifest doing what a single write's rename does per member — save the unreplaceable probe, which only the single writes make (#205; bulk's one caller writes under the workdir) — after a pass that moves nothing and only checks every member arrived, so a short delivery lands nothing at all, and one batched `chmod 0644` over the delivered members, because a non-root `tar` leaves a created file's bits to the parent directory's default POSIX ACL where a root one and the docker daemon's untar both set them (#213). `__map_bulk_prepare` makes the members' directories **inside the sandbox** (which is also what classifies a blocked path) and `__map_bulk_discard` sheds what a batch that ended badly left. The archive carries no directory entries deliberately — an explicit one would chmod a directory that already exists. Who makes a missing parent is load-bearing rather than incidental: the docker daemon extracts on the host as root, so parents it created belonged to root and a non-root sandbox could rename nothing into them (measured: the batch failed where the file-at-a-time loop succeeded), which is why docker delivers the bookkeeping, prepares, then delivers the members. The k8s backend extracts in the pod, where everything is already the sandbox user's, so it needs one exec. Directories a batch creates land 0755 on both — the platform's answer, not the image's, and deliberately not the single write's `mkdir -p`, which takes the image's umask — because the daemon fixes 0755 on the host whatever the image says and the two backends have to agree. A parent's default POSIX ACL still decides a created *directory's* bits on either backend, as it did a created file's before #213. Each member is atomic on its own, but the **batch is not a transaction**: the first failure stops the run, what landed stays landed, and the error names the member it stopped on. Only skill materialization uses it. ### internal/mcp

The MCP client (docs/plan/29_mcp-toolset.md, #45) — a thin wrapper over the official
`github.com/modelcontextprotocol/go-sdk`, which is a dependency of this package and its
test-support twin `internal/mcp/mcptest` alone. The
SDK's types never appear in the wrapper's surface: an MCP tool reaches the rest of the
platform as this package's own `Tool`, so the domain model stays Anthropic-native (design
principle 1) and a wire-schema question is never answered by a third-party struct.
Connections are per-work-item — connect, ask, close — which the 2026-07-28 revision makes
affordable by removing protocol-level sessions: nothing accumulates on the server that a new
connection has to re-establish, and there is no affinity between discovering a server's tools
and later calling one. What is per-work-item is the MCP session and not the socket:
`DefaultClient` is package-level and keeps an ordinary net/http connection pool, so two work
items reaching one origin may share a TCP connection or multiplex over one HTTP/2 connection.
The state worth not sharing is protocol state, and there is none. Not free, though: a connection still negotiates, and what that costs
depends on the server — against a 2026-07-28 one a single `server/discover` round trip (two,
where the SDK retries it after an unsupported-version answer), and against an older one that
discover plus the legacy `initialize` and `notifications/initialized`, three requests, before
`Connect` returns. That handshake is what per-work-item connections cost; a client with no
state to lose is what they buy.
Its caller is the executor's MCP driver (`internal/executor/mcpwork.go`), which connects once
per work item to discover a server's tools into `mcp_catalogs`. Nothing calls `CallTool` yet —
offering MCP tools to a model is a later slice.

| File | Contents |
|---|---|
| `mcp.go` | `Connect(ctx, Config)` → `Conn`, with `ListTools` and `Close`. `Config` carries the server URL, an optional bearer token, and an optional `*http.Client` (nil selects `DefaultClient`, which production uses; a caller supplies its own only to reach a test server, since a supplied client replaces the guarded one wholesale — the executor's egress check sits in front of the dial rather than substituting the client). `ListTools` follows pagination to the end and returns `Tool{Name, Description, InputSchema}` — JSON-tagged with the **Anthropic** field names (`input_schema`), so a catalog row is stored as-is and needs no second translation at request assembly. An empty listing is a fact, not an error — the nearest documented case is Anthropic's *Messages API* connector logging a warning for a `configs` entry naming a tool the server does not offer; the managed-agents pages say nothing, so this follows by analogy rather than by citation. The listing treats the response as hostile, because the endpoint is customer-supplied and the SDK decodes rather than validates it (docs/DIVERGENCES.md carries each reading): pagination is driven here rather than through the SDK's `Tools` iterator, which hides the cursor — the only thing that distinguishes paginating from looping — so a cursor the server has already used fails on its second sighting (every cursor is remembered, not just the previous one: an alternating pair never repeats consecutively, and under a 2026-07-28 negotiation a server that sends a positive `ttlMs` with a page has its re-requests answered from the SDK's own cache with nothing on the wire, so those pages draw nothing from the byte bound either) and a server that never stops issuing new ones fails at `maxToolPages`; a second entry claiming a name already taken is dropped, since a name is what a `configs[]` entry and a model's `tool_use` address and duplicates would reach a model as two definitions sharing one name; an entry the platform cannot faithfully hand to a model is skipped rather than failing the listing — an unusable name (empty, over 128 bytes, or outside `[A-Za-z0-9_.-]` — the SDK's own `validateToolName`, which the SDK itself never enforces: `AddTool` logs a violation and registers the tool anyway, and no client-side path checks it, so this is the first place it can be caught), a schema present and not a JSON object, a schema whose root `type` is anything but `object` (**absent included**, which is how `{}` is refused), and a schema **absent or null** — MCP requires the field, and synthesizing `{"type":"object"}` for it, or reading `{}` as though the server had, publishes a contract the server never offered. The SDK's own server agrees: `AddTool` panics unless the decoded type is `"object"`. Free text is not validated: a description is passed through as written. Three bounds sit under the page limit, none in the protocol. Two are on a `RoundTripper` wrapping whatever client the caller supplied and the third is applied by `ListTools` itself: `MaxResponseBytes` (8 MiB **in total across a connection's responses**, bodies in full and header blocks as far as they can be counted — per-response would not bound a listing, since 100 pages of 8 MiB is 800 MiB and both ends retain it: under a 2026-07-28 negotiation the SDK puts each `tools/list` result into a per-cursor cache unconditionally and holds it until that cursor is re-requested or the server sends `notifications/tools/list_changed`, while this package holds its own re-marshaled copy of every accepted schema. Header blocks are charged too, but only as far as they can be counted after parsing, so the byte bound is two bounds rather than one. net/http bounds a *single* response's block and nothing bounds their sum, so a body-only budget let a paginating server move a hundred megabytes past a bound that said eight; charging the block from `resp.Header` closes that for headers the client can see, and cannot close it for the three routes that miss that map: a **1xx informational block**, which never enters `resp.Header` at all and which a server may send repeatedly before its final response (a one-off probe under net/http's 10 MiB default, not a retained fixture, measured 91.8 MB across 100 pages for 3,900 bytes charged — the gap this package then closes rather than one surviving its cap); **padding whitespace or folded continuations**, which textproto trims and joins before the map exists (against a raw listener whose only other header is Content-Length, a value of one character followed by 200,000 spaces reconstructs to 49 bytes against 200,048 on the wire, a factor of 4,083 — both halves move with whatever else the response carries, so the fixture is named rather than just the pair); and **trailers**, which arrive after the body — bounded to a few kilobytes by net/http's read buffer over HTTP/1.1, but taking the full per-block cap over HTTP/2, where the acceptance boundary was bisected to 65,856 bytes accepted and 65,857 refused — exactly the raw cap plus h2's 320. All three are held instead by `maxHeaderBytesPerResponse`, the raw limit `DefaultClient` sets in place of net/http's 10 MiB default, and it caps a header **block** rather than a response: over HTTP/1.1 that is nearly the same thing (net/http resets the limit per 1xx block only for a request carrying an `httptrace` with `Got1xxResponse`, and the SDK installs none), but over HTTP/2 — which this client explicitly enables — it becomes the connection's `maxHeaderListSize` and applies per decoded block, measured with a one-off probe rather than a retained fixture, though each figure follows from the constants — an 80 KiB final block refused while ~120 KiB split across Early Hints and the final block is accepted, and ~180 KiB with a trailer on top still accepted; what the suite retains is the boundary itself, driven either side of it. So a cycle carries three capped blocks, and the cap is `MaxResponseHeaderBytes` **+ 320**, since net/http pads it by an assumed ten fields at h2's 32-byte per-field accounting on the way to `SETTINGS_MAX_HEADER_LIST_SIZE` (`adjustHTTP1MaxHeaderSize`). **That cap bounds a peak, and no cumulative header ceiling follows from it.** Several revisions of this row published one anyway and every one was falsified — by whitespace padding, by mistaking a block for a response, by claiming a socket total no header arithmetic can produce, and by multiplying a per-block cap by a response count. That last is the one that matters, because it is what all of them needed: a bound on how many responses a connection answers, and go-sdk v1.7.0 has none: the handshake, `maxToolPages` pages and the closing `DELETE` come to 104, but a server that rejects the first `server/discover` with a supported-version list is probed twice (`for range 2`), and any response sent as `text/event-stream` may end on a priming `id:` with no call response, which sends `handleSSE` round its reconnect loop — the #679 no-progress cap resets on every id that advances, the server sets the pace through the SSE `retry:` field, and the SDK's own TODO beside `connectSSE` records that a limit on total attempts for one logical request is still missing. A fixture in the suite drives exactly that: **around two thousand responses to a single listing in three seconds**, in three of the 120 seconds `ListTimeout` allows, against the 104 the arithmetic multiplied by. It counts responses and deliberately says nothing about their bytes — an earlier revision reported `responses × 50000` as bytes delivered, false by more than two orders of magnitude, since `net/http` trims a padded header value in `writeSubset` *before writing it*. One thing here is bounded and worth stating: `headerBytes` charges every response at least the twenty-odd bytes of its status line, so the byte budget caps the response count too, at a few hundred thousand. Its product with a maximal block is left unstated on purpose, under the rule this row kept failing: do not multiply by a quantity nothing bounds. Deriving a figure is fine where both terms are enforced somewhere — the 800 MiB above is `maxToolPages` times `MaxResponseBytes`, and the few hundred thousand just above is that budget over a floor `headerBytes` guarantees — and the withdrawn product was not that: it multiplied an enforced per-block cap by a response count with no bound at all. Which is why every attempt to publish it has been wrong, including one that named the rule and broke it in the same sentence. Those blocks are parsed and dropped per response rather than retained, so they cost bandwidth and not memory, and the loop ends on whichever of the byte budget or `ListTimeout` arrives first. Nothing here bounds socket traffic and nothing can (one-byte DATA frames, PING floods); that is `ListTimeout`'s to bound, while these byte bounds are about memory. The header cap itself is pinned by fixtures with absolute margins rather than by arithmetic — a 16 KiB block accepted, three 30,000-byte informational blocks refused — which between them kill a mutant in either direction, including the 1 KiB tightening that would break every real server and that stayed green under an inequality. 64 KiB is set generously rather than tightly, the cost of too low being a working server this client cannot reach: the referent is nginx's `proxy_buffer_size` cap on an upstream's header block, one memory page by default — 4k or 8k depending on platform, so this is eight to sixteen times it), `ListTimeout` (2 minutes for the whole listing, taken as a parameter internally so a test can drive a budget short enough to observe), and a `DialTimeout` fallback deadline for any request reaching the transport without one — which is how the SDK's session-ending DELETE is bounded, since it rides a `context.WithCancel(xcontext.Detach(ctx))` with no deadline and no link to the caller's cancellation, and a caller-supplied client may set no `Timeout`; and `ListTools` on a zero-value `Conn` errors rather than dereferencing a nil session. `listPage` recovers around the one SDK call: go-sdk v1.7.0 dereferences every decoded `tools` element without a nil check, so `"tools": [null]` panics the client — and the caller is an executor shared by every session on the host, where a Go panic is not confined to its goroutine. Transport is Streamable HTTP only — the SDK negotiates every protocol version from 2024-11-05 up over it, while the separate HTTP+SSE transport of 2024-11-05 is deprecated ("New implementations SHOULD NOT adopt it") and a client-side fallback to it is deliberately not wired. The standalone SSE stream is disabled: 2026-07-28 removed the GET endpoint it used, and a per-work-item connection wants no server-initiated messages — and the setting is load-bearing under test rather than decorative, since go-sdk serves 2026-07-28 only from a stateless handler, so every fixture negotiates 2025-11-25, the era in which the SDK still opens that GET (a test counts them). `DefaultClient` is guarded twice — `internal/dialguard` on each dial it makes, and redirects refused, since following one would replay the request and its `Authorization` header to a target the per-hop guard vets but never approved. Its transport is spelled out rather than cloned from `http.DefaultTransport`, which makes three settings decisions: no `Proxy`, because a proxy moves the dial off the target and leaves the address guard vetting the proxy while the proxy fetches whatever the URL named; `ForceAttemptHTTP2`, because setting `DialContext` at all disables HTTP/2 unless it is set, so the guard would otherwise downgrade every https server to HTTP/1.1; and idle-connection reaping, because this transport is package-level and outlives every connection made through it. Both guards live on that client, and so does the raw header cap — a caller supplying its own client gets none of the three, which for the header cap means bounded on bodies and unbounded on the padded, informational and trailing blocks the response budget cannot charge, which is why the bearer wrapper does not lean on them: a token is injected by wrapping a **copy** of the caller's client, and only for the endpoint's own origin. Both halves are needed: the copy stops the token sticking to a shared client, and the origin check stops it riding a redirect, since `net/http` strips `Authorization` across an origin change only for headers set on the outbound request — one a RoundTripper adds is invisible to that logic, so without the check a 307 to another host simply gets the token added again. `Connect` also closes the SDK connection itself when `client.Connect` fails after the transport opened one — go-sdk v1.7.0 returns the error without closing, leaking the session (reported upstream as modelcontextprotocol/go-sdk#1154) — which needs a one-method `Transport` wrapper to capture the `Connection`. It is passed back unchanged as a fidelity choice rather than a hard requirement: a substituted connection still negotiates (the SDK's own `LoggingTransport` substitutes one), but the SDK delivers `sessionUpdated` through a type assertion to an unexported interface, so a substitute silently drops the `Mcp-Protocol-Version` header from every post-handshake request of a legacy negotiation — which is the negotiation this client mostly gets. The requests this package issues itself — the listing and the call — carry W3C trace context in their `_meta` under the bare key names `traceparent`/`tracestate` — the convention MCP 2026-07-28 documents in SEP-414, deliberately un-namespaced so a carrier written by any OpenTelemetry SDK drops in unrenamed, and one the go-sdk does not implement (it fills only the `io.modelcontextprotocol/*` protocol keys, and only where absent, so a supplied map is added to rather than replaced). The handshake ahead of them carries no `_meta`, and that gap is the SDK's: it builds `server/discover` — and a legacy negotiation's `initialize` and `notifications/initialized` — itself, with no hook for a caller's metadata. So the same context also rides an HTTP `traceparent` header on **every** request, written by the transport (`withTraceContext`), which the SDK cannot withhold because the transport is this package's: a connection is traced from its first packet, and one that fails — the case with no later request to carry the trace — correlates too. A server reading SEP-414's `_meta` and one reading headers see the same trace; both carriers are the propagator's own output. |

| `dialguard.go` | `IPAllowed(ip)` refuses loopback, link-local (cloud metadata), the unspecified address and multicast — and the IPv4 target inside six IPv6 transition forms — NAT64 `64:ff9b::/32`, 6to4, Teredo, the RFC 4291-deprecated IPv4-compatible `::/96`, RFC 2765's IPv4-translated `::ffff:0:0:0/96`, and RFC 5214 ISATAP (`00-00-5E-FE`, which rides any prefix and so is decoded *in addition to* the others rather than as one of them; only the identifier's `u` bit varies, and leaving the group bit free too — the natural reading of "u/g" — over-refuses ordinary global-unicast addresses whose identifier happens to sit there) — so `64:ff9b::7f00:1` cannot smuggle `127.0.0.1` past it. An address it cannot read at all (nil or the wrong length — what `net.ParseIP` returns for a name) is refused rather than admitted, since every class predicate answers false for one. Six is not every form. 6rd's embedded address sits at a provider-parameterised offset an address does not carry, and neither does a NAT64 deployment's own Network-Specific Prefix (below). RFC 2529 6over4 is left out by decision rather than blindness: its identifier is specification-fixed (32 zero bits then the IPv4 address), but that is indistinguishable from the ordinary habit of writing a host part as `prefix::a.b.c.d`, so decoding it would refuse a measured 6.6% of such addresses — and RFC 2529 §5 lets the real link-layer address differ from the identifier anyway, so the decode would not even be authoritative. NAT64 yields **six** candidates, one per RFC 6052 prefix length, because the address alone does not say which layout its deployment uses and reading only the low 32 bits is wrong in **both** directions — admitting, since under a `/48` prefix `64:ff9b:1:a9fe:a9:fe00:808:808` carries `169.254.169.254` in bytes 6,7,9,10 while its low 32 bits read as `8.8.8.8`; and refusing, since RFC 6052 puts the SHOULD-zero suffix in those same low 32 bits for every length from `/32` to `/56`, so the low-32 reader saw `0.0.0.0` instead of a target and refused *every* conformant mapping under the two layouts a deployment can use inside this prefix, `/48` and `/56`, whose suffix covers all four of those bytes. (`/32` and `/40` are arithmetic, not deployments: RFC 6052 fixes the well-known prefix at `/96` and the shortest prefix available inside `64:ff9b::/32` is RFC 8215's local-use `/48`, from which a `/48`, `/56`, `/64` or `/96` translation prefix may be carved.) A candidate decoding to the unspecified address is therefore skipped as padding, which is what makes six candidates usable and is the one way the rule is not additive against its predecessor: `64:ff9b::`, `64:ff9b:1::` and `64:ff9b:1:808:8:800::` are admitted where the probe's guard refused them — the first two prefix base addresses with no target and nothing listening, the third a conformant `/48` mapping of `8.8.8.8` whose low 32 bits are the zero suffix. The skip is a rule and not a NAT64 list: a 6to4 wrapper under `2002::/32`, a Teredo address whose low 32 bits are all-ones and an ISATAP identifier carrying `0.0.0.0` are admitted by the same line. Only `64:ff9b::/32` is decoded at all; an operator's own Network-Specific Prefix carries no mark identifying it, so a deployment translating through one gets no NAT64 decoding, which makes this hardening on the one prefix an attacker can count on rather than a general answer. The measured price is not determined by a deployment's prefix length — the prefix bytes decide it too, and can decide it entirely: zero for the well-known prefix (bytes 4–11 are zero by definition, so the `/32` through `/56` readings are skipped as padding and the remaining `/64` reading is `0.0.0.x`, which matches no blocked class), 12.8% (`/48`), 6.6% (`/56`, `/64`) or 0% (`/96`) on an otherwise-zero RFC 8215 local-use prefix, and **total** for a legal NSP whose own bytes read as a blocked class under a shorter layout (`64:ff9b:1:7f00::/96` reads as `127.0.0.0` under `/48`). Fail-closed and unavoidable without being told the layout. It checks the address **and** its decoded target rather than replacing one with the other, which is what keeps a wrong decode able only to add a refusal: `::1`'s low 32 bits decode to `0.0.0.1`, which no rule calls loopback, so replacing would have admitted it. The IPv4-compatible, IPv4-translated and ISATAP cases close three gaps the guard carried from the validate probe: the mapped form (`::ffff:127.0.0.1`) is refused by `net.IP`'s own predicates, while for those three `To4` answers nil, every predicate in the refusal list answers false, and `IsGlobalUnicast` affirmatively answers true — so nothing refused them. RFC 1918 is deliberately **allowed**: this platform's premise is on-prem / in-VPC operation, so the guard is the floor beneath an agent's egress policy, not the policy itself. `Control(allow)` builds the `net.Dialer` hook that runs the predicate on the **resolved** address of every dial, which is what makes DNS rebinding ineffective; `allow` is a parameter rather than a hard-wired call so a caller can hand in a closure over its own overridable seam (the api probe's test override) and have that seam consulted on each dial; the closure itself is captured once. A refusal names the resolved address and says only that it is disallowed — never which class matched, and never whether anything is listening, since it is produced before any `connect(2)` — so a caller that surfaces it cannot become an internal-host oracle. |

Text a server controls is stripped of `U+0000`, and a tool whose *schema* decodes to one is dropped whole instead: in JSON a NUL is six characters rather than a byte, so the schema is decoded and its strings and keys searched for the code point, because the escape that spells it is routine inside a `pattern` and refusing on the text would drop tools carrying no NUL at all — while stripping it there would corrupt a schema that legitimately contains it. jsonb cannot hold one, and a rejected INSERT faults the item before `queue.Complete`, so one NUL in one description would reclaim-loop that session's discovery for good. The listing is also bounded by a fixed budget of server-chosen text (`maxCatalogTools`, 256 KiB of names, descriptions and schemas), and once it is spent the remaining tools are dropped whole rather than truncated — half a schema is worse than an absent tool. The per-response limit alone would not hold this: a session may declare twenty servers, so twenty answers at that limit would store a hundred and sixty megabytes against one session, which the brain then has to read back and assemble into every request. A reason is additionally cut down to scheme://host, by value and then by shape — an `mcp_servers` entry is customer-supplied and may carry a credential in its userinfo or its query, and everything that builds a reason quotes the endpoint back. By value first because the endpoint is a string the driver holds, so the renderings a message can contain are enumerable rather than guessable: the declared bytes, `url.URL`'s `String` and `Redacted`, net/http's `***` variant, and each of those through `%q`. Shape alone could not reach it — a URL is recognized in prose by where it *ends*, a space must end it, and `?agent=my agent&…` is a URL this platform accepts and dials, so a pattern stops mid-query and leaves the rest beside a host that reads as redacted. The pattern pass stays as the second one, for URLs the platform did not supply (a redirect target, one a server names itself) — and then validated as UTF-8 and capped. Postgres rejects an invalid byte sequence on a text column exactly as it rejects a NUL, so the validation runs twice for two different reasons: once on arrival, because a server chooses this text and need not send UTF-8 (Go's HTTP parser accepts obs-text in a header value, and an SDK error quoting such a header carries those bytes in), and once after the cap, because cutting a byte slice mid-rune produces the same invalid sequence out of input that was clean. The pattern itself stops only at whitespace and angle brackets — not at a quote, since `'` is a legal sub-delim. The pass as a whole is bounded (`Config.MCPPassTimeout`, five minutes — the same budget bounds the execution half): the dials are serial and this process runs one work item at a time, so without it twenty declared servers at the per-server bounds would hold every other session on the host for the better part of an hour, with the lease keeper renewing throughout so nothing reclaims it. A server the budget does not reach is a `failed` row like any other. `settleMCP` is the one transaction: the rows, the chained `model_turn`, and the item's completion together, so a discovery pass never settles silently and leaves the session waiting on a turn nothing else enqueues. Under the session row lock it re-reads both what the agent declares and whether the session is still live — a pass runs for minutes, so `sessionForRun`'s check is stale by now, and a session archived or terminated in between gets no rows and no turn, only the item completed. Every other executor settlement inherits that from `events.AppendInTx`, which refuses an archived session under this same lock; discovery appends no event, so it asks directly. The turn is chained on `events.HasUnansweredToolUse` like every other settlement — `mcp_exec` and `tool_exec` are different queue kinds and nothing keeps one from settling while the other is in flight, and a `model_turn` sent with an `agent.tool_use` unanswered assembles a request the Messages API rejects; whichever settles last finds the set answered, so the gate costs no wakeup. It takes the session row lock and re-reads the declared array from inside it, dropping any row the agent no longer declares at that url — the dials happen outside the lock, so a patch that removes a server mid-pass would otherwise find no row to invalidate and then have one written behind it that nothing revisits, since discovery only ever walks the declared array. A dead context commits nothing and the reclaim re-runs the whole pass — discovery is idempotent, so that costs round trips and nothing else. |

| `s3/transport.go` | `endpointWord`, the client's `http.RoundTripper` (wrapping minio-go's own transport — `http`'s would gunzip an object's bytes and lose its length), so what minio-go decodes from an error response is what the endpoint said. | `gcs/gcs.go` | The GCS-native backend on `cloud.google.com/go/storage` (docs/plan/22, #240), the alternative to reaching Google Cloud Storage through its S3-interop XML API — the difference is the credential: interop needs an HMAC key pair, downloaded key material a deployment stores and rotates, where this authenticates with Application Default Credentials, on GKE a Workload Identity binding and no material at all. resolves to. `Bindings` projects the winners to the sandbox-visible half — each `secret_name`
paired with a `vltph_` placeholder derived per `(session, secret_name)` (`internal/egress`), so a
re-provision or the gate recovers the exact token already in the sandbox. `Credentials` projects
the same winners to the gate half — the same placeholder plus the secret decrypted through the
`secrets.Cipher`, the credential's own networking (`unrestricted`, or `allowed_hosts` for
`limited`), and its `injection_location` arms — which the per-session gate substitutes back for the
placeholder at egress time; the plaintext secret lives only in the resolving process's memory,
never injected into the sandbox. A cipher is required once the session has any active
`environment_variable` credential (even one whose ciphertext was purged); a decrypt
failure or a tampered/short sealed document fails the whole call (fail-closed, and error messages
carry credential ids, never secret bytes), while an active credential whose ciphertext was purged
is skipped so its placeholder simply egresses literally. An archived vault contributes nothing —
the query guards the vault's own `archived_at` directly, not only the credential's, so the
"archived vault delivers no credential" guarantee holds even if the archive cascade ever left a
stale credential row. This package does the store read and cipher call; `internal/egress` stays
I/O-free.

### internal/identity

The platform's human-authentication boundary (docs/plan/31_console-sso-rbac.md slices 1–2) — a
strict OIDC relying party over `github.com/go-jose/go-jose/v4`, with no vendor SDK; slice 2's
identity lane in `internal/api` is its one consumer. `Verify` authenticates one compact JWT and returns an
`Identity` (issuer, subject, email, display name, `Role`): the signature allowlist is a required
parameter of go-jose's parser, so `alg:none` and HS256 are refused before any key lookup; a `crit`
or `b64` header is refused outright and equally early, since go-jose permits `crit:["b64"]` and
separately honours a bare `b64` (verifying over the raw payload) while RFC 7797 §7 forbids `b64` in
a JWT at all; `iss` is
exact, `aud` must contain the configured audience, `azp` is checked when `aud` carries several,
and non-empty `sub` and `exp` are required because go-jose checks neither. `sub` is additionally bounded at **255 bytes** — the number OIDC Core §2 states in characters ("MUST NOT exceed 255 ASCII characters"), identical for a conforming subject and stricter for a non-conforming one; a non-ASCII `sub` is not refused outright, since denying every human on a provider with that conformance bug would cost far more than it buys — and **refused** rather than truncated past it, because `sub` is half the key a principal row is stored under, so shortening one would merge two humans sharing a prefix, while an unbounded one rides inside the token cap and past PostgreSQL's B-tree tuple limit. The returned `Identity.Issuer` is the **configured** issuer, not the token's: they differ for exactly one provider (Google mints two spellings of one identity), and returning whichever arrived would store that human twice under two principal ids. Every rejection is one
`*Error` whose `Error()` is a constant string, the detail behind `Reason()` for the caller's log —
no oracle distinguishes expired from bad-signature from wrong-audience, and no log line or error
carries a token byte or a URL credential (a key-set URL may be a signed URL whose query string is
the credential, so URLs are redacted into logs and errors alike; the one attacker-supplied value
logged on purpose is the `kid`, truncated, at Debug). `Role` (`viewer` <
`developer` < `admin`, plus `RoleNone`) is deliberately not a `domain` type: it is a declared
divergence that never appears on a `/v1` path or in a `/v1` body, and `AtLeast` fails closed at
both ends, so a mis-annotated route denies. Roles come from a configurable claim on every request
and are never stored — the IdP stays authoritative — reduced to the single strongest mapped value
by rank, so neither claim order nor map iteration order can change the answer; how a claim NAME is
read is fixed by the name and never by the token — a URI-shaped name (`https://corp.example/roles`,
the namespaced convention Auth0 requires) is one flat key, any other dotted name
(`resource_access.console.roles`, the Keycloak shape) is a path — because the alternative, trying
the flat key and falling back to walking, lets a user-settable flat claim outrank a nested one. Key material is a kid-indexed set with a **bounded
lifetime**: a five-minute TTL checked before the map lookup (so a key the provider removed stops
verifying within that bound rather than living in the cache forever), a thirty-second refresh
cooldown, hand-rolled single-flight under the same mutex as the cache, a per-fetch deadline, a
128 KiB body cap, and no redirects — over `internal/dialguard`'s address guard, because the
`jwks_uri` this package fetches arrives inside the remote issuer's discovery document. Two modes
share that one verifier: `oidc` (discovery from the issuer, or a pinned `IDENTITY_OIDC_JWKS_URL`
that skips it) and `trusted_proxy` (a signed assertion header; the `gcp-iap` preset pins Google's
header, issuer, ES256 and global key set, which is why its audience is required and is the entire
tenant boundary). That mode refuses at construction to have `Authorization` or `x-api-key` named as
its assertion header: those carry machine credentials, and naming one would invert the mode's own
rule from the other end — the API layer would read a raw `Authorization` value as an assertion and
hand a worker's environment key to the verifier. The role map is validated and **copied** at construction, so the live policy cannot be edited
through the map the caller passed in. `FromEnv` returns `(nil, nil)` when `IDENTITY_MODE` is unset
or `disabled` —
the optional-dependency shape `blob.Store` and `secrets.Cipher` already use, concrete-typed so
`== nil` is correct — and every other misconfiguration fails startup rather than open.

### internal/identity/identitytest

The fake OpenID Provider the verifier's tests drive: an httptest discovery document and JWK Set,
minting for all five allowed algorithms, rotation and retirement, request counters, and the
failure overrides a verifier must survive (malformed or oversize key sets, non-200s, redirects, a
blocked handler for the single-flight and deadline paths). `MintRaw` assembles a token by hand
because the two that matter most cannot be built through any signing library — the `alg:none`
forgery and the key-confusion token MACed with the published RSA public key's DER. It deliberately
does **not** import `internal/identity`: with no cycle, that package's own in-package tests may use
it and so may any later consumer. `Clock` is an atomic test clock, so a `-race` run may advance
time while verifications are in flight — the suite contains no sleeps.

### internal/gatetoken

The scoped bearer credential a session's egress gate presents to the controlplane's internal
gate-config endpoint (docs/plan/12_vaults-credentials.md slice 4). `Mint` issues an opaque `gtk_`
value (256 bits of CSPRNG entropy, Crockford base32) — internal-only, never on the `/v1` wire, so
`gtk_`/`gatetok_` are deliberately absent from `domain`'s wire-prefix set (the `apikey_`/`envkey_`
precedent). `Ensure` stores only the token's hash (`session_gate_tokens`) as the session's one live
token, revoking any predecessor in the same transaction — a replacement gate re-mints, and a partial
unique index backstops one-live-per-session. `Revoke` is the no-successor half of that (#197): it
marks the live token revoked without minting, for the gated→ungated reshape where no replacement
gate will ever re-mint — idempotent, so a provider that revokes before tearing the gate down can
safely retry both. `Authenticate` resolves a token to its session, joined
against `sessions` so it fails closed once the session is archived; there is no wall-clock expiry
(validity is the session's lifetime), so a controlplane outage longer than any TTL cannot be misread
as a revocation, and a deleted session's token cascades away. Hash-only storage mirrors
`internal/api`'s environment-key issuance. The token authenticates the internal gate-config
endpoint (`internal/gateconfig`, below); the gate runtime that presents it is `internal/gaterun` /
`cmd/gate` (below), wired into the Docker sandbox provider (the executor supplies the two-step
`Generate`/`Persist` minter — and the `Revoke` — over its pool to both backends' providers).

### internal/gateconfig

The gate ↔ control-plane config contract and the gate-side client for it (docs/plan/12, slice 4).
`GET /internal/v1/gate/config` (handled in `internal/api`, on its own `gtk_`-token auth lane —
`requireGateToken`, selected by path so it never crosses the management or worker lanes) returns one
session's `Config`: the environment's request-level `Networking` policy and its resolved, decrypted
vault `Credential`s (placeholder, plaintext secret, the credential's own `allowed_hosts` arm,
injection locations, and the non-secret `credential_id`). The endpoint decrypts through the same
`vaultresolve.Credentials` path the gate-side resolution uses, so a leak-safe error (credential ids,
never secret bytes) is a property of that one function. Rendering the config is also where the
controlplane detects the reference's `credential_host_unreachable_error`: a *configuration conflict*
— a credential whose `allowed_hosts` includes an entry the environment's `limited` networking policy
does not cover (`egress.HostSet.CoversEntry`) — appended post-commit as a `session.error` event
naming `credential_id` and `vault_id` (hostnames only, never a secret), best-effort once per
(session, credential): the dedupe is an events-table check-then-append, so a concurrent duplicate
fetch can rarely double-emit the advisory. Detection re-runs every fetch, so a healed or
newly-introduced conflict tracks vault edits without a restart; the emission runs detached from the
request (its own goroutine, unhooked from the request's cancellation but bounded by its own
10-second deadline), so the config a live gate is waiting for is
neither delayed nor failed by it — append failures are logged and swallowed. `Client.Fetch` presents the token as a Bearer
credential and maps a 401 (revoked token / archived session) to a fail-closed `ErrUnauthorized`,
distinct from a transient error — the signal a periodic-fetching gate uses to choose between stopping
and keeping its last-known-good config. Neither the endpoint nor the client is on the public `/v1`
wire (DIVERGENCES). The gate runtime that drives the client is `internal/gaterun` /
`cmd/gate` (below); both sandbox providers wire the sidecar (Docker: slice 4-i; K8s: slice 4d).

### internal/gate

The per-session egress gate (docs/plan/12_vaults-credentials.md, D3): a forward proxy the sandbox
reaches through `HTTP_PROXY`/`HTTPS_PROXY`, and the enforcement point of the two-level gate. It is
transport-only — it holds one session's resolved credentials and opens sockets, but reads no store
and emits no events. It runs inside the `cmd/gate` container image as a sidecar of the sandbox on
both backends; `internal/gaterun` (below) is the runtime that drives it — firewall, privilege drop,
and the fetch-and-swap loop that keeps its credential set current. The Docker sandbox provider wires
the sidecar (shared network namespace, proxy env, teardown; slice 4-i); the K8s provider runs it as a native sidecar in the sandbox pod (slice 4d).

| File | Contents |
|---|---|
| `policy.go` | `policy` — the environment's request-level networking gate (the first of the two levels): `unrestricted` admits every host (its safety blocklist unpublished by the reference, deferred and recorded INFERRED), `limited` admits only `allowed_hosts` (via `egress.HostSet`), an unknown type fails closed. Plus the hop-by-hop header set a forwarding proxy must strip (`removeHopByHop`, honoring the `Connection` header on both the forwarded request and the returned response). |
| `gate.go` | `Gate` — an `http.Handler` forward proxy. `CONNECT` is host-filtered on its target and, if admitted, tunnelled opaquely (no substitution — the #166 TLS gap): the tunnel forwards bytes the server buffered past the `CONNECT` line, propagates a half-close in either direction, and closes only when both directions do — bounded by an activity-based idle deadline (`TunnelIdleTimeout`, default 5m) that tears down a tunnel only when **both** directions have gone quiet, so a one-way stream never trips it and gate swaps never touch a running tunnel (the watchdog is owned per handler invocation). A plain-HTTP request is host-filtered, then its header values and body are rewritten through `egress.Engine.Substitute` (the second gate level — a credential's own `allowed_hosts`) before it is forwarded and the response streamed back; a credential the host does not admit is left as its literal placeholder (never the secret) — documented reference behavior, not an error — and its placeholder (never the `*Credential`, which carries the secret) is surfaced through the diagnostic `OnUnreachable` seam, which the deployment wiring leaves unset: `credential_host_unreachable_error` is a config-conflict event the controlplane emits at gate-config render (`internal/api`), never a gate report. The body buffered for substitution is bounded by `MaxBodyBytes` (default 10 MiB) — a larger sandbox-controlled body is refused `413` rather than read unbounded. |

### internal/gaterun

The testable runtime of the `cmd/gate` sidecar (docs/plan/12, slice 4): everything the gate does
that is not a raw syscall, kept out of `cmd/` so the coverage gate reaches it. It owns the firewall
policy and its verification, the DTO→`gate.Config` conversion, and the fetch-and-swap loop, behind
`Firewall`/`PrivDropper`/`Fetcher` interfaces the `cmd/gate` adapters satisfy with `iptables`/`syscall`/`gateconfig.Client`.

| File | Contents |
|---|---|
| `firewall.go` | `Ruleset(uid)` — the three owner-match rules, order load-bearing (first-match-wins): loopback `ACCEPT` (all intra-netns loopback), owner-match `ACCEPT` for the gate's own uid, catch-all `DROP`. They live in a chain the gate owns outright (`ChainName`, `MAP-GATE-EGRESS`), jumped to from `OUTPUT` position 1 — not inlined into `OUTPUT` — so the gate *reconciles* with a netns whose `OUTPUT` already carries foreign rules (CNI/mesh rules in a K8s pod netns): `Apply`'s contract is an atomic rebuild of the owned chain followed by ensuring the single first-position jump, never flushing `OUTPUT` or touching its policy, and idempotent under re-apply (a restarted sidecar). Ordering is the fail-closed guarantee — the chain is complete before the jump steers traffic into it — and every chain verdict is terminal, so foreign rules below the jump are unreachable and the semantics equal owning the whole chain. `Setup` (which refuses a non-positive or oversized gate uid via `CheckGateID` — uid 0 is a silent no-op drop, an oversized id truncates in the syscall) applies via the `Firewall` adapter, lists both families back, and `CheckListing` requires the owned chain to be *exactly* those three rules token-for-token (a foreign `ACCEPT` ahead of the `DROP`, or a rule that only resembles ours — a colliding uid prefix, `-o lo0`, `! -o lo` — is rejected) **and** the first appended `OUTPUT` rule to be exactly the jump (a rule above it would decide traffic before the policy; rules below are tolerated) before it lets `PrivDropper.Drop` run; a firewall that did not take aborts with the process still root, so it never serves fail-open. This is the egress fail-closed invariant: the sandbox shares the gate's netns, and only the gate's uid may reach the network. |
| `gaterun.go` | `Convert` maps a fetched `gateconfig.Config` to the transport-layer `gate.Config` (a credential's networking `unrestricted` becomes the `egress` engine's per-credential `Unrestricted`). `SwappableHandler` is the `http.Handler` the server binds: an `atomic.Pointer[gate.Gate]` the fetch loop swaps under live traffic, wrapping each request in an `egress_request` span (`semconv` HTTP method + server address). |
| `loop.go` | `RunFetchLoop` — fetch immediately, then on a ticker: a good config swaps in a fresh `gate.Gate`; `ErrUnauthorized` (revoked token / archived session) swaps in a deny-all gate and returns terminal so the binary shuts down; any transient error keeps the last-known-good gate serving; ctx-cancel returns nil. |

## Security invariants

- **Credentials never enter the sandbox.** Tool credentials (vaults) reach the wire only
  at egress time: the sandbox sees opaque `vltph_` placeholders, and the per-session gate
  substitutes the real value on admitted plain-HTTP egress alone (both backends when the
  executor opts in; in-sandbox HTTPS keeps its placeholders until #166). Model
  keys live in the brain's provider config; the sandbox sees none of them. Provider adapters redact the credentials they were configured with
  — the api key, a `base_url` userinfo password, an auth header — out of the errors that
  quote an endpoint (`internal/provider/redact.go`), so an endpoint echoing the request's
  auth header back cannot land the key in a `session.error` event, which is append-only
  and re-served to clients. Matching is verbatim against the configured value in each
  form it is known to reach an error in — decoded, percent-encoded, base64 in a derived
  `Authorization: Basic`, and as written — and by design does not chase a credential an
  endpoint re-encodes into some form of its own. A model's *successful* output is a
  trusted boundary and is never redacted: it is the content the session exists to record.
  `provider.Config` has no redacting `String`, so it must not be formatted whole.
- **A session is not a context window.** The harness may replay, slice, or rewind the
  event log before feeding the model; context strategy is never baked into an
  irreversible compaction.
- **Auth is scoped.** Management calls carry `x-api-key` (hashed at rest,
  rotation-by-restart); workers carry an environment key scoped to exactly one
  environment's work queue — a worker can neither read nor write another environment's
  sessions. Environment keys are hashed at rest too, issued one per host so a
  compromised host is revoked alone, and expire a year after issue; revoked,
  expired and unknown are one indistinguishable 401. Issuing and revoking them is
  a **management** operation on the off-wire console API, so an environment key
  can never mint or retire another — but equally, that surface delegates no
  authority the management key did not already hold, and is not a separate
  permission tier.
- **Humans authenticate through the deployment's own IdP, and the platform stores no
  authority** (plan 31, #56). Off by default: with `IDENTITY_MODE` unset or `disabled`
  no JWT is accepted anywhere and the surface is the machine-credential platform
  above — byte-for-byte on every request shape but one, a repeated `x-api-key`
  field, which is refused as ambiguous in every mode rather than resolved by header
  order (`server.go`). Configured, a human's token is verified against its issuer's JWKS —
  algorithm allowlist, exact `iss`, `aud` containment plus `azp`, required `sub`/`exp`,
  keys only from the key set and only while its bounded lifetime holds — and never
  minted here; every **credential** rejection is one indistinguishable 401, which is
  what makes the 500 from a failed principal provisioning meaningful rather than
  noise: it says the credential was good and the database was not, so an operator is
  not sent hunting the IdP for an outage. The machine lanes always
  resolve first, so a second credential can never change which lane, and so which role
  check, a request takes. The request's role is computed from the IdP's claim on **that
  request** through the operator's map: `principals` records who signed in, never what
  they may do, so revoking a group at the IdP takes effect on the next request rather
  than after someone remembers to mirror it. Enforcement is one check at the control
  plane, stated per route as a minimum role, and fails closed — an unannotated route
  denies every human, as does a human whose claims mapped to nothing.
- **Sessions are not bound to an end-user.** Scoping keys are org/workspace/project
  (reserved, single-tenant defaults in v1); end-user ownership is an application-layer
  concern hooked on session `metadata` and the audit-only `created_by`.
- **The container is the boundary.** Tools run inside the per-session sandbox with no
  host filesystem access; the toolset does no lexical path confinement that a `bash`
  call could walk around, because the container itself is the wall. That wall is
  hardened when it is built, not left to the operator: every sandbox is created with
  cgroup limits and capability drops (`sandbox.Hardening`, defaults on), which is also
  the only containment for a process that escaped the exec deadline's process-group
  kill by calling `setsid`.
- **The platform runs nothing in a sandbox as anyone but the sandbox's own user.** No
  privileged exec, on either backend — the operator's `SANDBOX_RUN_AS_USER` (or the
  image's own user) is who every command runs as, cleanup included. One place had to be
  designed around it: docker's daemon lands a write's temporary as root, so a refused
  write leaves one where the sandbox uid cannot unlink, and the obvious `exec -u 0`
  cleanup was measured to be unboundable — `docker exec -u 0` starts with `AT_SECURE=0`
  and runs the image's own binary and libraries, so an image's `BASH_ENV`, `LD_PRELOAD`
  or `LD_DEBUG_OUTPUT`, or an `/etc/ld.so.preload` no environment setting closes, all
  reach it. The daemon empties what it landed instead, executing nothing (#310) — and
  the same for a **batch**, whose two sheds now name on stdout what their own `rm` could
  not take so the daemon can empty what is left in one archive (#316) — best effort, and
  with the exec-error branch's carve-out, exactly as the single write's. What
  pins the invariant is structural — docker's `execConfig` carries no `User` field to
  set, so no exec can name one — with a real-image row
  (`TestTheRootShedRunsNoAgentCodeOnANonRootImage`) covering the shell-hook channel
  behind it; what an operator must configure around it is docs/self-hosted-security.md.
- **A skill archive is verified before it is extracted.** The registry records the
  archive's sha256 at upload (Postgres) while the bytes live in object storage; both
  materialization halves check the object they read back against that digest before
  extracting it into a sandbox — the executor from the version row, the BYOC worker from
  the `x-skill-archive-sha256` download header, since it never touches the database.
  Bit-rot, truncation, and whole-object substitution are refused (`corrupt` outcome,
  skipped like any other per-skill miss rather than faulting the run). Two limits are
  deliberate: a version predating the digest column records none and is read unverified
  (logged), and a digest served by the same control plane that serves the bytes proves
  storage integrity, not provenance.

How these invariants divide between what the platform enforces and what a self-hosting
operator must configure — sandbox image hardening, capability drops, non-root execution,
read-only rootfs, egress policy, environment-key rotation — is
[docs/self-hosted-security.md](./self-hosted-security.md).

## Observability

OpenTelemetry is built in, not bolted on. Trace context propagates as W3C `traceparent`
across every process hop that continues a trace — HTTP headers between processes, and a
`trace_context` column that carries a turn's trace through `tool_exec` work items to
executors and BYOC workers (a `model_turn` item deliberately stores none: nothing reads
it back; the brain's `model_turn` span roots the turn's own trace instead) — so one
session's turn is one trace across process boundaries. All three claimants of the work
queue wrap a claimed item in a consumer span standing for its handling end to end — the
brain's `model_turn`, the executor's and the BYOC worker's `tool_exec` — and each reports
its item-handling faults from inside that span, so those logs are reachable from the red
span they describe. (The worker's heartbeat path is the exception and stays uncorrelated:
its lease-loss warnings are logged outside the run's span, and a cancellation-caused
reclaim deliberately leaves the span unset.) Anthropic
`span.*` wire events and OTel spans are emitted from the **same instrumentation point**
(they cannot drift); the business metrics ride the same points — model-request duration,
token-usage counters and the cache-token breakdown in `internal/events/metrics.go`,
session-status transition counts and approval (HITL) wait in
`internal/events/statusmetric.go`/`approvalmetric.go` (both recorded **after** the
transaction commits, so a rolled-back transition counts nothing), time-to-first-token
measured from the work claim in `internal/brain/telemetry.go`, tool-run duration in
`internal/toolset/telemetry.go`, and skills-materialization outcomes/duration in
`internal/executor/telemetry.go` and `internal/worker/telemetry.go` (same instrument
names, two scopes). Queue `depth`/`pending`/`workers_polling` are OTLP
observable gauges (`internal/queue/metrics.go`) sampling the same work-stats view the API
serves — registered once by the control plane, reported per self_hosted environment. A
configured OTLP endpoint bridges
`slog` records — trace-correlated where a span is in reach — to the collector.
`internal/telemetry` owns init, propagation, and the shared process startup/exit sequence
that keeps a binary's fatal-exit log ahead of the flush that would drop it; an empty
endpoint is a fully-offline no-op.

## Testing architecture

Four tiers (see README's table for the opt-in contract): unit/contract tests and
dependency-integration tests run on every PR and call no model — the store, API, queue,
sandbox, and toolset suites run against real Postgres and real Docker/Kubernetes, and a
missing daemon or cluster is a hard failure, not a skip. The live tiers are consented by
environment variable (`RUN_LIVE_MODEL_TESTS`, `RUN_EVALS`), configured by the gitignored
`.env`, and fail rather than skip when misconfigured (`internal/modeltest` owns the
contract).

Backend variability lives behind interfaces, and where more than one backend exists the
contract is a **shared suite**: every sandbox provider passes
`internal/sandbox/sandboxtest` (a backend that declares the gate seam also runs the gated
egress rows against the real gate image), and both model-provider protocol adapters pass
`internal/provider/providertest` (the cross-provider invariants — stream termination,
`tool_use` stop, usage-nil-only-when-the-endpoint-reported-none, cancellation, `Close`;
the wire request shape, redaction, and the OpenAI lossy conversions stay per-package) — a
new backend inherits the whole battery. The queue still has one production implementation
(Postgres) contract-tested in its own package; a second queue backend would owe the same
extraction. The merge gate is `make verify`
(build, linux/arm cross-compile, vet, gofmt, `go test -count=1`, and **≥90% total
statement coverage** over the logic packages of `./internal/...`). On top sits the eval
system (`make eval`, [plan 02](./plan/02_evals-system.md)): fifteen deterministic regression
tasks driving whole sessions through the public API against a real model, graded
code-only with per-trial nonces and Platform/Model/Either failure classing. `repo-answer`
is the one trial whose expected answer is not nonce-derived — it lives in a fixed private
GitHub fixture repository, whose privacy stands in for the nonce a fixed remote cannot
carry (#358). The registered set is pinned by an offline test, so adding or dropping a trial
fails `make verify` until that pinned list moves with it, and the failure names the two
documents — this one and README.md — whose spelled-out counts must move too. The tier stays out
of the merge gate — it spends money and minutes — but a scheduled workflow
(`.github/workflows/evals.yml`, daily plus manual dispatch) runs it against the `MODEL_*`
and `EVAL_GITHUB_REPO_*` secrets of the `evals` deployment environment — which admits only the default branch, so a
dispatch cannot borrow the credential onto an unreviewed ref — and a break in the
whole-session path therefore surfaces on the next scheduled run instead of at whoever's next
manual one. That job carries the same fail-not-skip rule: with the secrets unset it is red,
never green-and-silent — a green job means the suite ran and passed, never that it was skipped.

Beside the evals sits the top-level `acceptance/` suite (plan 21): the define-outcomes
doc example driven end-to-end through the latest Go SDK. Its deterministic rehearsal —
a scripted model standing in for the real one — runs in the merge gate like any other
suite; the live variant (`TestLiveDefineOutcomesAcceptance`) points the same harness at
a running compose stack and a real model, consented by its own tier variable
`RUN_LIVE_ACCEPTANCE_TESTS` (whole sessions cost an order of magnitude more than the
`RUN_LIVE_MODEL_TESTS` single-turn smoke, which therefore must not buy them) with the
`ACCEPTANCE_*` variables naming the stack's key, model, and base URL.
