- **An MCP client, and one shared address guard under the platform's customer-URL dials — plan 29 slice 2 (#45)** — `internal/mcp` is the platform's MCP client: a thin wrapper over the official `github.com/modelcontextprotocol/go-sdk`, which becomes a dependency of that package alone. `Connect` opens one connection to one server, `ListTools` reports what it offers, `Close` ends it — connections are per-work-item, which the protocol's 2026-07-28 revision makes affordable by removing protocol-level sessions: nothing accumulates on the server that a new connection must re-establish, and there is no affinity between discovering a server's tools and later calling one. Per-work-item means the MCP session rather than the socket; the HTTP client is process-wide and pools connections as usual, because the state worth not sharing is protocol state and there is none. Not free — a connection still negotiates, a `server/discover` round trip against a 2026-07-28 server, or that plus the legacy `initialize` and `notifications/initialized` against an older one, before `Connect` returns — so what per-work-item connections cost is that handshake and what they buy is a client with no state to lose. The SDK's types stop at the package boundary; a tool reaches the rest of the platform as the platform's own `Tool`, JSON-tagged with the Anthropic field names (`input_schema`) so a stored catalog row needs no second translation before it is handed to a model. Pagination is followed to the end, up to a hundred pages, and a server offering no tools is a fact to record rather than an error — the nearest documented case is Anthropic's Messages API MCP connector, which logs a warning rather than failing when a `configs` entry names a tool the server does not offer; the managed-agents pages say nothing either way, so this follows that posture by analogy rather than by citation. **A server's answer is structure to be validated, not data to be trusted**, because the endpoint is customer-supplied and the SDK decodes a response rather than checking it. An entry the platform cannot faithfully hand to a model is skipped rather than failing the whole listing: an unusable name (empty, over 128 bytes, or outside `[A-Za-z0-9_.-]` — the MCP SDK's own rule, which the SDK itself never enforces: registering a tool with a violating name only logs, and nothing checks it client-side, so this is the first place it can be caught), a schema that is present and is not a JSON object, one whose root `type` is anything but `object` including absent (which is how `{}` is refused), and — MCP requires the field, so its absence is malformed rather than "takes no arguments" — a schema that is absent or null. A second entry claiming a name already taken is dropped too, first one winning: a name is what a `configs[]` entry and a model's `tool_use` address, so duplicates are an ambiguity rather than two tools, and they would reach a model as two definitions sharing one name in a single request. What is *not* validated is the free text: a description is passed through as the server wrote it. A server that hands back a cursor it has already used, or never stops issuing new ones, fails the listing rather than spinning inside a work item that holds a queue lease, and a connection that reads more than 8 MiB **in total across every response**, or spends more than two minutes on one listing, ends the same way — so trickling bytes cannot hold the lease either. Every cursor is remembered rather than only the previous one, because a server alternating between two never repeats one in consecutive answers — and it can make those repeats free: under a 2026-07-28 negotiation a page sent with a positive `ttlMs` is answered from the SDK's own cache without reaching the wire, so it draws nothing from the byte bound. That bound is cumulative because a per-response cap does not bound a listing: a hundred pages of eight megabytes is eight hundred, and both ends retain it — the SDK holds each page under its cursor until that cursor is asked for again or the server announces its tool list changed, while the client holds its own re-marshaled copy of every accepted schema. It covers **header blocks as well as bodies**, which is not decoration and is not the whole story either: net/http reads and allocates a response's headers before the client sees it, bounds one response's worth at ten megabytes by default, and bounds their sum not at all — so a body-only budget let a paginating server move a hundred megabytes past a bound that said eight. Charging the block closes that for headers the client can *count*, and counting happens after parsing, which three routes miss: a `1xx` informational block never enters the parsed headers at all and a server may send many before its final response (91.8 MB across a hundred pages, for 3,900 bytes charged), padding whitespace and folded continuations are trimmed and joined before the map exists (a 200,076-byte response reconstructed to 75), and trailers arrive after the body — held to a few kilobytes by net/http's read buffer over HTTP/1.1, but taking the same per-block cap as anything else over HTTP/2, where a 65,821-byte trailer value is accepted and retained. So a second bound holds the raw block — 64 KiB rather than net/http's ten megabytes — and it caps a header *block* rather than a response, which matters because this client enables HTTP/2, where each decoded block is capped on its own: measured, an 80 KiB final block is refused while ~120 KiB split across Early Hints and the final block is accepted, and ~180 KiB with a trailer still is. A response cycle therefore carries three capped blocks, and the cap is 64 KiB **+ 320**, because net/http pads it by an assumed ten fields at HTTP/2's 32-byte per-field accounting on the way to `SETTINGS_MAX_HEADER_LIST_SIZE`. A test drives real HTTP/2 blocks either side of that cap, and another drives informational blocks either side of it, so the constants have to describe net/http rather than only each other. **What the cap bounds is a peak, and no cumulative header ceiling follows from it** — four attempts to publish one were each falsified in turn, the last multiplying the per-block figure by the 104 responses a connection was thought to serve, and every one of them needed a bound on how many responses a connection answers that go-sdk v1.7.0 does not have. A server that meets the first `server/discover` with a supported-version list is probed twice; and any response delivered as `text/event-stream` may end on a priming `id:` carrying no call response, which sends the SDK round its stream-resumption loop again — the no-progress retry cap it grew for exactly this resets on every id that advances, the server sets the pace through the SSE `retry:` field, and the SDK's own TODO beside the reconnect records that a limit on total attempts for one logical request is still missing. A fixture in the suite drives it: **2,027 responses to a single listing in three seconds, delivering 96.7 MiB of header padding nothing here can charge** — three of the 120 seconds the listing budget allows, against a ceiling that had claimed 27.60 MiB in all — and it is written to go red if that upstream limit ever lands, which is how the claim would learn it may tighten again. So what is bounded is the peak and not the sum: one header block at a time, plus 8 MiB cumulative for everything that can be accounted. The blocks that cannot are parsed and dropped per response rather than retained, costing bandwidth rather than memory, and the loop ends on whichever of the byte budget or the listing timeout arrives first. What none of it bounds is what a server can put on the socket, which no count of headers models and which one-byte DATA frames or a PING flood inflate without limit; the two-minute listing budget is what answers that, and these byte bounds answer memory. A third bound covers the request the SDK detaches from every context we control — it sends the session-ending DELETE on a context stripped of deadline and cancellation, so a server that accepts it and never answers would hang `Close` and hold the queue lease; that request now gets a deadline of its own regardless of what timeout a supplied client carries. A `"tools": [null]` response, which panics the SDK itself, is contained at the call rather than allowed to take down an executor shared by every session on the host. docs/DIVERGENCES.md records each of those readings, since none of them is reference behavior. **Transport is Streamable HTTP only.** The SDK negotiates every protocol version from 2024-11-05 up over it, so an older server is still reached; the separate HTTP+SSE transport of 2024-11-05 is deprecated in the spec, which tells new implementations not to adopt it, so the client-side fallback to it is split out rather than shipped with the base — docs/DIVERGENCES.md records the choice and what a legacy-only server sees until it lands. The standalone SSE stream is disabled: 2026-07-28 removed the GET endpoint it used, and a connection that asks one question and closes wants no server-initiated messages. **The dial guard is now one implementation, not two.** `internal/dialguard` holds the rule the vault-credential validate probe has enforced since plan 12 — loopback, link-local (cloud metadata), the unspecified address and multicast refused on the **resolved** IP of each dial it sees, so a DNS rebind cannot slip one past a name that resolved innocently a moment earlier — and refused equally for the IPv4 target inside six IPv6 transition forms (NAT64, 6to4, Teredo, IPv4-compatible, IPv4-translated, and ISATAP). A seventh, RFC 2529 6over4, is deliberately left undecoded: its identifier is specification-fixed, but the pattern is indistinguishable from the ordinary habit of writing an IPv6 host part as `prefix::a.b.c.d`, so decoding it would refuse a measured 6.6% of those addresses — and RFC 2529 lets the real link-layer address differ from the identifier anyway. The probe and the MCP client, the two places the platform resolves a host a customer named, now share it — the MCP half through the guarded client the package builds for itself, which is what production uses and what a caller gives up by supplying a client of its own. RFC 1918 stays deliberately allowed: this platform's premise is on-prem operation, where an MCP server legitimately lives on the operator's own private network, so the guard is the floor beneath an agent's egress policy rather than the policy itself. That client also refuses to follow redirects, because following one replays the request and its `Authorization` header to a target the per-hop guard vets but never approved as a destination. Its transport is written out rather than inherited from `http.DefaultTransport`, which makes three settings decisions rather than omissions: no proxy, since a proxy would move the dial off the target and leave the guard vetting the proxy while the proxy fetched whatever the URL named; HTTP/2 explicitly attempted, since installing the guard's dialer would otherwise silently confine every https server to HTTP/1.1; and idle connections reaped, since the transport is process-wide and outlives every connection made through it. A bearer token is then injected by wrapping a **copy** of the caller's HTTP client, and only for the endpoint's own origin — a second line that does not assume the first, since a caller may supply its own client (the seam a test needs) and that client's redirect policy is its own. Both halves are load-bearing: the copy stops the credential sticking to a client that may be shared, and the origin check stops it riding a redirect — `net/http` strips `Authorization` when a redirect changes origin, but only from headers set on the outbound request, and a header a RoundTripper adds is invisible to that logic, so without the check a `307` to another host would simply have the token added again. Nothing calls the client yet — the catalog and the executor's discovery driver are the rest of this slice.
