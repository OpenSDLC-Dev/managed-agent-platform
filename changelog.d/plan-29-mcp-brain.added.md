- **An agent's MCP tools reach the model — plan 29 slice 4b (#45)** — An `mcp_toolset` expanded to nothing at request assembly; it now expands to the tools its server reported. The brain reads the session's catalog, offers each enabled tool as a model tool definition, commits a call on one as `agent.mcp_tool_use`, and schedules the MCP driver that answers it — which is the half slice 4a shipped ahead of this one so a rollout could not strand a call. **The model sees `mcp__{server}__{tool}`; the wire never does.** The reference's own protocol carries a call's server in a field of its own, so the name it shows the model is bare — but this brain assembles one flat `tools[]` for an ordinary Messages endpoint, which has no such field, and two servers offering `search` would be two definitions under one name. So the prefix is ours and forced by architecture rather than chosen, it exists only inside a provider request, the event carries the bare `name` and `mcp_server_name` exactly as the SDK types them, and replay puts the two back together — because the assistant `tool_use` block this log re-sends on every later turn has to name a tool that turn's request actually offers. **A tool can be declared and not offered, and that costs one tool rather than the turn.** A Messages tool name must match `^[a-zA-Z0-9_-]{1,64}$` — documented in one place, the tool-use guide's parameter table, and in neither the API reference nor the SDK types — while an MCP server may have a 255-character name and 128-character tools, so a pair legal on both wires composes into a name the endpoint would reject, and it would reject the whole request, every turn, on a log that keeps replaying the same agent. The length is settled before the name is built, since a listing holds thousands of tools and neither half is capped where it is stored; a pair that does not fit is dropped, while a byte outside the class is replaced with `_` rather than costing its tool, because the class an MCP tool name may use includes `.` and a server publishing `github.create_issue` would otherwise offer nothing at all. A name already taken is dropped too — by the agent's own `tools[]` (the author's definition wins over a third party's listing), by an earlier MCP tool, since flattening a pair is not injective (a server `a__b` offering `c` and a server `a` offering `b__c` are one string), or by another name that mangles alike; declaration order settles all three, rather than escaping a separator the reference never publishes. So is every tool of a server whose listing failed, a `configs[]` entry naming a tool the server does not report — the only one of these the docs settle: a warning, never an error, because an MCP server's tool list is unknowable when the agent is written — and a definition past the 256 KiB of MCP tool definitions one request carries, which bounds across an agent's twenty declarable servers what the catalog's own cap bounds within one. Two further drops are silent on purpose — a listed tool with no name, and a name a server reported twice — because both are already refused where a listing is read, so reaching either means a catalog row nothing on this platform wrote, and warning every turn about a state that cannot arise is noise rather than news. The reported ones are log lines, at most sixteen a turn with a count standing in for the rest: no wire event describes one, `session.error` names connection and authentication failures and this is neither, and the brain's skills and mounted-file injection already put an unresolvable reference in the log rather than on the session stream. Plan 29 proposed a `system.message` and that is corrected here — the event is client-sent, carries a documented placement rule, and replays into the *system prompt*, so one per turn would grow the prompt without bound. **A turn waits for a listing it has never had.** An `mcp_toolset` whose server has no catalog row is not assembled at all: no model call, the item is handed straight back as MCP work, and the discovery driver chains the turn once the listing is in — one round trip per session, and the alternative silently misses the agent's whole reason for declaring the server on its first turn. It waits before any outcome entry leaves `pending`, because a turn that suspends never began work. A *failed* row is an answer rather than an absence, so the turn runs without that server's tools instead of suspending to re-dial an endpoint that just refused, which would loop for as long as the server stayed down — and the retry runs where the reference documents it, on the idle→running transition: a wake that begins a new work cycle drops the session's failed rows — a message or a new outcome on an idle session, and the same pair redirecting a turn an interrupt just ended — so the next turn re-dials those servers once, and a server that stays down costs one dial per message rather than one per turn. A row written for an endpoint the agent no longer declares counts as no row, behind the mid-session patch that already deletes such rows in its own transaction; for the same reason an outstanding call is dialled only where the listing that offered its tool was read, since a mid-session patch can repoint a server between the turn that called it and the pass that runs the call, and the new address is a different party being asked a question it never advertised an answer to. **An MCP call gates like any other ask tool**, since `always_ask` is the MCP toolset's documented default: the intent carries `evaluated_permission`, the turn idles with `requires_action` naming it, and the confirmation resume's MCP arm — shipped a slice early — is live. A turn's platform calls now enqueue one work item of the highest kind they demand, `mcp_exec` over `web_exec` over `tool_exec`, each driver answering its own family and chaining the next. Request assembly and call classification became one resolution over the agent's `tools[]`, which is what makes "what the model was offered" and "what a name it called back means" incapable of disagreeing.
