- **The identity lane — humans reach the control plane, and the first role gate closes** ([docs/plan/31_console-sso-rbac.md](docs/plan/31_console-sso-rbac.md) slice 2, [#56](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/56)) — slice 1's verifier now has a consumer. With `IDENTITY_MODE` configured, a human's token authenticates against the deployment's own provider and the request resolves to a **principal** with a role; with it unset or `disabled` — still the default — nothing here exists and the platform is byte-for-byte what it was, which every one of these behaviours is tested against. Sign-in provisions just-in-time into a new `principals` table keyed on `(issuer, subject)` — never the email, which an IdP with self-service profile attributes lets a user choose — refreshing the descriptive claims on each visit while the id a human is first stamped with stays theirs. Both halves of that key are now pinned to make the promise true: a verified identity reports the **configured** issuer rather than whichever spelling the token carried, so Google's two documented forms cannot store one human twice under two ids; and a subject longer than OpenID Connect's own 255-character bound is refused rather than truncated, since shortening one would merge two humans who share a prefix, while an unbounded one rides inside the token size cap and past PostgreSQL's index-tuple limit — turning every request for that identity into a 500 at provisioning time. The table records who has signed in and deliberately **no role**: the role is the provider's answer on the request being served, so revoking a group at the IdP takes effect on the next request rather than after an operator remembers to mirror it here. Credential dispatch is where the security argument sits, and it resolves machine-first in every branch: a management `x-api-key` wins outright and keeps its frozen full-authority semantics, so a Bearer or an assertion header riding alongside one can never vouch for it and a caller cannot attach a second credential to soften a route's role check — and a *bad* key stays on the machine lane and 401s rather than falling back to the human beside it. That rule is now robust against a repeated header field, which is where it first leaked: HTTP lets `x-api-key` appear twice and Go's `Header.Get` reads only the first, so an empty value placed ahead of a real one read as "no key offered" and moved the request onto the human lane. Lane selection now reads every value, and a duplicated credential header — which no real client sends — is refused outright as ambiguous rather than resolved by header order. On the dual-auth session, events, skill- and file-read routes, where two different credentials now arrive in the same `Authorization` header, the split is by shape: a compact-JWS silhouette goes to the human lane, anything else stays the worker's environment key. That is one-way safe — a key this platform mints is `sk-map-env01-` plus base64url and contains no dots, so it can never be read as a JWT — and the residual case, a grandfathered pre-0021 key whose value an operator chose, misroutes into verification and fails there: a 401, fail-closed, never an over-authorization. In `trusted_proxy` mode `Authorization` is not read as a human credential at all; only the configured assertion header is, since accepting a Bearer would accept a credential the proxy never vouched for — and that mode now refuses at startup to have `Authorization` or `x-api-key` *named* as its assertion header, which would have inverted the rule from the other end. The `/api/` console namespace gains its own explicit dispatch arm, answering the re-check plan 30 asked a future off-`/v1` lane to perform rather than inherit its fallthrough. Every route now states a **minimum role**, and enforcement is the single check at the control plane that reads it. This slice registers every route at the floor — which denies every human, whatever their role — with one exception: the console environment-key surface requires `admin`, listing included, because which hosts hold live credentials and what they are named is itself an inventory. So the lane is born fail-closed and the next slice relaxes rather than closes, and default-deny is not a branch anyone has to remember but a consequence of the role comparison failing closed at both ends. `sessions.created_by` now resolves either lane — the api key's name on the machine lane, the human's principal id on the identity lane — so the audit trail names whoever acted rather than silently recording nothing the moment a human can create a session, and [docs/self-hosted-security.md](docs/self-hosted-security.md) gains the principal-retention section that table's own comment promises: the `last_seen_at` deletion an operator runs on their own schedule, plus the two consequences to know before running it (session history survives, because `created_by` is plain text and not a foreign key; and a returning person is provisioned afresh under a **new** id, so older sessions keep pointing at the old one). A denial names the role the route requires and never the caller's own; a verified token that maps to no role is a 403 rather than a 401, because the caller has proved who they are and an operator's real diagnosis is "your IdP is not sending the group I map", which reads nothing like "your token is bad". Four entries land in [docs/DIVERGENCES.md](docs/DIVERGENCES.md): Bearer acceptance on `/v1` where the reference serves an OAuth token endpoint this platform does not, the three-role model bound to IdP claims rather than a platform user store, `trusted_proxy` having no reference analog at all, and — INFERRED — the `admin`-only gate on environment keys, which the reference's own role documentation may yet justify relaxing to `developer` once a recording shows what it does.
