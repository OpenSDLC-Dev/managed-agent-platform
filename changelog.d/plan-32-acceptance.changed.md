- **Plan 32 archived — the management-key lifecycle accepted against real Casdoor tokens and the real `ant` CLI** ([#378](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/378), [docs/plan/32_management-api-keys.md](docs/plan/32_management-api-keys.md)) — the plan asked for a run that "issues a key over the console API, drives `/v1` with it, disables it and is refused, re-enables it, archives it and is refused again", and that is what ran, over real HTTP against the shipped `deploy/compose` stack with `--profile iam` on a database Casdoor had never seeded: **31 assertions, 0 failures**, no manual database edits. Tokens were minted through the full authorization-code + PKCE exchange against the bundled provider's own OP endpoints, as plan 31's acceptance was. A viewer is **403** on the surface with the wire error envelope; an admin issues a 56-character `sk-map-api01-` key whose `created_by` is that admin's **principal**, so the audit trail names the human rather than a credential; the key then drives both a read and a mutation on `/v1`. Disabling it makes `/v1` answer 401 and re-enabling it restores 200 — the exact sequence a review round found a hole in, now proven end to end. Archiving is refused out of in every spelling (`active`, `inactive`, a rename), and the run also recorded a **repeated archive succeeding** — an observation [#389](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/389) has since overturned by measuring the reference, which refuses that too; see the Fixed entry below. The `CONTROLPLANE_API_KEY` row is listed but refuses console patches and keeps authenticating. Expiry was driven against the clock rather than asserted: a key minted 45 seconds out worked, then answered 401, listed as `expired` (derived, never stored), refused re-activation — and **still archived successfully**, because cleanup must not depend on the clock. The listing carried five rows including archived and expired ones and zero occurrences of any key value. A real `ant` 1.21.0 built from the read-only CLI checkout listed and created agents on a console-issued key, failed with the platform's `authentication_error` envelope the moment the key was disabled, worked again when it was re-enabled, and failed for good once archived. One property was measured because the new docs assert it: with the identity lane live, the management `x-api-key` still reaches these admin-gated routes — `requireRole` binds the human lane only — and a key minted that way records the **issuing key's row id** as an `api_key` actor, so "a management key can mint management keys" is a measured fact stated where an operator meets it. [docs/self-hosted-security.md](docs/self-hosted-security.md) gains **§10, management-key lifecycle**, beside the environment-key section it parallels: the two writers and why they differ (env-var-managed rotation-by-restart, whose inverse is that re-using a previously-archived value revives that row at boot, logged when the row was console-issued and silent when it never left its lane); the three settable states against the one derived one; expiry as the caller's choice where absent means never; and five operator responsibilities, including the audit-trail consequence of leaving SSO unconfigured and the advice to issue one key per consumer so a leak's blast radius is one consumer.
