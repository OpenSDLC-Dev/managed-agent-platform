- **Environment-key tests now pin the invariants their comments claim** ([#362](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/362)) — review of plan 30 slice 2 found four test defects that slice 1 had introduced, on security-adjacent invariants; all four are fixed here rather than carried as backlog, and no production code changed. Stated plainly, because three earlier drafts of this entry got it wrong in the same way: **nothing was ever exposed.** Each defect is an assertion that did not test what its comment said, and in three of the four the underlying invariant was still covered by another test — the exception is the `id DESC` tiebreak in (3), which nothing covered. (1) The index pin for `environment_keys(environment_id)` matched `indexdef LIKE '%(environment_id)%'`, a pattern the *dropped* `environment_keys_one_live` satisfied too, so it could not tell the replacement index from the index it replaced — though a migration 0021 that did nothing was still caught behaviourally, by `TestSecondLiveEnvironmentKeyIsAccepted`. The shape is now read out of `pg_index` instead of pattern-matched: right name, non-unique, valid, non-partial, exactly one key column resolving through `pg_attribute` to `environment_id`, on the `environment_keys` that `search_path` resolves. A UNIQUE, partial, two-column, `INCLUDE`-payload, or left-invalid-by-`CREATE INDEX CONCURRENTLY` variant each turns it red; of those five, only the two-column one already did. (2) The binding assertion had been reduced to "the raw INSERT is rejected", which any error satisfies — an unrelated schema change would have kept it green while proving nothing. It now requires SQLSTATE `23505` on `environment_keys_key_hash_key` by name. Its HTTP half does not restore the single-row scoping check that `TestWorkPollRequiresEnvironmentKey/key_for_other_env` already owns; instead it drops that constraint inside its own database and builds the state #362 actually names — one Bearer token resolving to two `environment_id`s — then asserts the value authenticates *exactly one* of the two environments, which holds whichever row the lookup happens to pick and goes red if the work API's scope comparison is removed. (3) Two ordering assertions could already fail, but at random and for a reason unrelated to the behaviour under test: `ORDER BY created_at DESC, id DESC` over rows whose `created_at` defaults to `now()` falls through to a 120-bit random tiebreak when two keys are issued inside one microsecond, so what the listing returned was decided by clock resolution rather than by the query. Timestamps are now set explicitly in one statement, the paging test pins both pages instead of only its last row, and a new test collapses eight keys onto a single `created_at` to pin the id tiebreak the flake had been hiding. (4) The fourth fix is documentation only and changes no test outcome: `raceMints`'s doc comment still described the retired rotate-on-mint contract, and now states the helper's own contract and what each of its three callers requires of it.
