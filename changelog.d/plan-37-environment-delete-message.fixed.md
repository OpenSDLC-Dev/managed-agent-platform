- **`DELETE /v1/environments/{id}` no longer blames sessions for a deployment's foreign key** — plan 37 slice 1's last piece ([docs/plan/37_scheduled-deployments.md](./docs/plan/37_scheduled-deployments.md), [#51](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/51)). The handler mapped every foreign-key violation to *"environment … still has sessions; delete them first"*, which was harmless while sessions were the only table that could block the delete. Deployments now can, so an operator whose environment had no sessions at all was told to delete some. The refusal now branches on which constraint fired and names the deployments — up to five, with a count of the rest — and it does not tell the operator to remove them, because no route deletes a deployment and archiving one does not clear the reference either: the foreign key does not read `archived_at`. An environment a deployment has ever used can therefore no longer be deleted, so the message says to archive the environment instead. The sessions message is unchanged where a session really is the blocker.
