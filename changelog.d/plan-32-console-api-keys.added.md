- **An admin can issue, list, disable and retire management API keys from the console** ([docs/plan/32_management-api-keys.md](docs/plan/32_management-api-keys.md) slice 2, [#378](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/378)) — until now a deployment had exactly one management credential, the value of `CONTROLPLANE_API_KEY`, and the only way to change anything about it was to restart the control plane. Three routes on the console namespace — `POST`, `GET` and `POST …/{key_id}` under `/api/console/organizations/{org}/workspaces/{workspace}/api_keys` — give an operator the model the reference implements, mirrored from a live recording of 2026-08-13 rather than inferred: issue a named key with an optional expiry and receive the secret **once**, as `raw_key` on the created resource; list every key with a masked `partial_key_hint` and never a secret; disable one **reversibly** and re-enable it; archive one for good. There is deliberately **no `/v1` twin**. The reference withholds key creation from its public API for a stated reason — "new API keys can only be created through the Claude Console for security reasons" — and its read/update pair belongs to an Admin API authenticated by a credential class this platform has no analog of; both absences are registered in [docs/DIVERGENCES.md](docs/DIVERGENCES.md) rather than left as unexplained gaps. Expiry is the caller's choice, as an absolute instant with no duration vocabulary anywhere on the wire, and **omitting the field means never** — the spelling the reference's own console uses. `expired` is a fourth status the server *computes* from `expires_at` at read time and never stores, derived by the exact complement of the comparison that authenticates, so a listing can never call a key active that the very next request is about to refuse. Nothing is hard-deleted: an archived key stays listed, because an archive that erased the row would erase the evidence that a credential ever existed. The whole surface is gated at `admin` — the listing included, since which credentials exist, what they are named and who issued them is itself the inventory an attacker would want — and a key issued over SSO records the issuing human's stable `principal_` id, which is what plan 31's `principals` table was built to make possible. One rule is ours rather than the reference's, because the reference has no env-var-managed credential to have a rule about: the key seeded from `CONTROLPLANE_API_KEY` is **listed but not console-mutable**. Hiding it would misdescribe what can reach the API; letting the console rename it would break rotation-by-restart outright, since `EnsureAPIKey` retires the incumbent by name and a bootstrap row renamed out from under it would survive the next rotation and leave two live credentials under one name.
