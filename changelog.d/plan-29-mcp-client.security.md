- **The dial guard reads every NAT64 layout, refuses IPv4-compatible IPv6, and checks the wrapper as well as what it wraps (#45)** — The address guard that has vetted the vault-credential validate probe's dials since plan 12 read a NAT64 address's low 32 bits and called that the target. That is the `/96` layout, and RFC 6052 defines **six** prefix lengths, each embedding the four IPv4 octets at a different offset around the reserved u-byte — an address does not say which its deployment uses, and guessing wrong admits rather than refuses. Under a `/48` prefix (RFC 8215 reserves `64:ff9b:1::/48` for exactly that), `64:ff9b:1:a9fe:a9:fe00:808:808` carries `169.254.169.254` in bytes 6,7,9,10 and nothing but padding in the low 32 — so the old guard read `8.8.8.8`, called it Google DNS, and would have let a credential URL reach the cloud metadata endpoint. All six layouts are now tried and any blocked candidate refuses the dial, which cannot admit anything the old code refused. It can refuse more, and the cost is stated rather than assumed away: measured over the whole IPv4 space, a legitimate public target on the RFC 8215 local-use prefix is now refused for 12.8% of addresses under a `/48` mapping and 6.6% under `/56` and `/64` — and for **none at all** under a `/96` mapping or the well-known `64:ff9b::/96`, which is the only layout that prefix may use and the case an operator gets without choosing anything. The over-refusal and the bypass live in exactly the same deployments, which is what makes it a price rather than a defect. The same guard decoded three IPv6 transition forms — NAT64, 6to4, Teredo — and admitted the fourth. `::127.0.0.1` and `::169.254.169.254` therefore passed where `::ffff:127.0.0.1` and `::ffff:169.254.169.254` were refused: Go classifies the IPv4-*mapped* form for you, but for the RFC 4291-deprecated IPv4-*compatible* form `To4` returns nil and every address-class predicate returns false, so nothing caught it. It is refused now, and by `internal/dialguard`, so both the probe and the new MCP client get the fix. Unlike the NAT64 layouts above, *this* half is hardening rather than a patched bypass, and the distinction is measured rather than assumed: against a listener on `127.0.0.1`, a connect to `[::127.0.0.1]` never arrives — Linux refuses it outright with `network is unreachable`, macOS drops the SYN and times out — so the address reaches nothing on a host that has not been configured for 6-over-4 tunneling. But a guard that only works because the kernel is also saying no is not a guard. The fix also changed the *shape* of the check, which matters more than the added case: the guard now vets the address **and** its decoded target, where it previously replaced the one with the other. Replacing makes every refusal hostage to the decoder being right about every prefix — `::1` decodes to the IPv4 bytes `0.0.0.1`, which no rule calls loopback, so adding the `::/96` case to the old shape would have turned the most obvious refusal in the list into an admission. Checking both leaves a wrong decode able only to add a refusal, never to remove one.
