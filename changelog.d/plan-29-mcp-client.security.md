- **The dial guard reads every NAT64 layout, refuses IPv4-compatible IPv6, and checks the wrapper as well as what it wraps (#45)** — The address guard that has vetted the vault-credential validate probe's dials since plan 12 read a NAT64 address's low 32 bits and called that the target. That is the `/96` layout, and RFC 6052 defines **six** prefix lengths, each embedding the four IPv4 octets at a different offset around the reserved u-byte — an address does not say which its deployment uses, and guessing wrong admits rather than refuses. Under a `/48` prefix (RFC 8215 reserves `64:ff9b:1::/48` for exactly that), `64:ff9b:1:a9fe:a9:fe00:808:808` carries `169.254.169.254` in bytes 6,7,9,10 and nothing but padding in the low 32 — so the old guard read `8.8.8.8`, called it Google DNS, and would have let a credential URL reach the cloud metadata endpoint. All six layouts are now tried and any blocked candidate refuses the dial. A candidate that decodes to `0.0.0.0` is padding rather than a target and is skipped, which is the one way the change is *not* purely additive — and the reason it has to be is the same misreading, pointing the other way: RFC 6052 puts the SHOULD-zero suffix in the low 32 bits for every prefix length from `/32` to `/56`, so the old guard read `0.0.0.0` and refused **every** conformant mapping under four of the six layouts. It refused `64:ff9b:1:808:8:800::` — a `/48` mapping of 8.8.8.8 — as readily as it admitted the `/48` mapping of cloud metadata. Both are fixed by the same change, and what the skip admits along with them is the residue: an address whose every non-padding reading is benign, `64:ff9b::` and `64:ff9b:1::` among them, prefix base addresses where a translator has no target and nothing is listening. The remaining cost is over-refusal, stated rather than assumed away — including the part that is easy to state too favourably. The size of it depends on a deployment's NAT64 prefix **bytes**, not on its prefix length. The well-known `64:ff9b::/96` — the case an operator gets without choosing anything, and the only layout RFC 6052 permits that prefix — pays nothing at all, because its bytes 4–11 are zero by definition and every speculative reading of them is skipped as padding. On the RFC 8215 local-use `64:ff9b:1::/48` the cost ranges from nothing to everything: with the rest of the prefix zero, a legitimate public target is refused for 12.8% of addresses under a `/48` mapping, 6.6% under `/56` and `/64`, and none under `/96`; but an operator may carve a legal NSP whose own fixed bytes read as a blocked class under a shorter layout — `64:ff9b:1:7f00::/96` reads as `127.0.0.0` under `/48` — and then every address that prefix can express is refused whatever the target. Fail-closed, sometimes total, and not something a guard handed an address without its layout can do better; a deployment that hits it needs the guard told its prefix, which nothing needs today. That same missing knob bounds the fix in the other direction, and an operator should know which prefix they are relying on: only `64:ff9b::/32` is decoded, while RFC 6052 equally allows translating through a Network-Specific Prefix out of the operator's own space, which nothing in an address marks as one — so a deployment doing that gets no NAT64 decoding here at all. This is hardening on the one prefix an attacker can count on being routed, not a general answer to NAT64. The same guard decoded three IPv6 transition forms — NAT64, 6to4, Teredo — and admitted the fourth. `::127.0.0.1` and `::169.254.169.254` therefore passed where `::ffff:127.0.0.1` and `::ffff:169.254.169.254` were refused: Go classifies the IPv4-*mapped* form for you, but for the RFC 4291-deprecated IPv4-*compatible* form `To4` returns nil and every address-class predicate returns false, so nothing caught it. It is refused now, and by `internal/dialguard`, so both the probe and the new MCP client get the fix. Unlike the NAT64 layouts above, *this* half is hardening rather than a patched bypass, and the distinction is measured rather than assumed: against a listener on `127.0.0.1`, a connect to `[::127.0.0.1]` never arrives — Linux refuses it outright with `network is unreachable`, macOS drops the SYN and times out — so the address reaches nothing on a host that has not been configured for 6-over-4 tunneling. But a guard that only works because the kernel is also saying no is not a guard. The fix also changed the *shape* of the check, which matters more than the added case: the guard now vets the address **and** its decoded target, where it previously replaced the one with the other. Replacing makes every refusal hostage to the decoder being right about every prefix — `::1` decodes to the IPv4 bytes `0.0.0.1`, which no rule calls loopback, so adding the `::/96` case to the old shape would have turned the most obvious refusal in the list into an admission. Checking both leaves a wrong decode able only to add a refusal, never to remove one.
