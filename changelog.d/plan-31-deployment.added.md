- **The bundled identity provider — single sign-on that works on a laptop, wired against what Casdoor actually does** ([docs/plan/31_console-sso-rbac.md](docs/plan/31_console-sso-rbac.md) slice 4, [#56](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/56)) — slices 1–3 built the verifier, the identity lane and the role matrix; this gives them a provider to verify against, so "the platform's default IAM works out of the box" is true without an enterprise IdP. `docker compose --profile iam up` adds two services: a pinned **Casdoor** keeping its users in a second database inside the stack's existing Postgres, and a small **Caddy proxy that is the only published way to reach it**. Off by default and byte-for-byte inert when off — with `IDENTITY_MODE` unset the control plane reads none of the other five variables and management auth stays `x-api-key` only, and the profiled services are named as a *soft* dependency because a profiled service named as a hard one makes `docker compose config` fail for the **default** project, which is CI's first compose step. Seven of the plan's Casdoor mechanics did not survive contact with a running one — four specified wrongly, three simply missing — and the corrections are in the plan file in place rather than left for slice 6 to rediscover, because every one of them fails **silently** and they compose into one shape: a stack that boots, logs people in, and authorizes nobody. **The role claim is `groups`, not `roles`.** Casdoor's `roles` claim decodes to an array of role *objects*, and the verifier's `roleValues` collects only the string elements of an array and drops the rest — so mapping `roles` gives every human no role, and no role is denied on every route; `groups` arrives as strings spelled `organization/name`, which is why every `IDENTITY_ROLE_MAP` key carries the organization prefix. **The audience is the application's client id**, because that is what Casdoor puts in `aud`. **The organization is the bundle's own**, never `built-in`, whose users are Casdoor *global administrators* — its REST API refuses to create one there at all — and which is the second reason the map keys are prefixed. The smaller three were equally quiet: the image tag is `casbin/casdoor:3.152.0` and carries no `v` where the release name does, so the plan's `v3.152.0` is a manifest that does not exist; `tokenFormat`/`grantTypes` are `init_data.json` fields on the application rather than environment keys, so setting them in compose does nothing — which matters because `JWT-Standard` drops `groups` from the token entirely; and `dbName`, which the plan had recorded as the MySQL-only key, is required for Postgres too, since `InitAdapter` hands it to `CREATE DATABASE` and panics on an empty string. **TLS in front of the provider is mandatory, not good practice**, and that is a platform rule rather than a compose preference: `internal/identity`'s fetch requires an `https` key-set URL and the guarded dialer beneath it then refuses loopback addresses with no exception, so the two rules close on each other and a plain-HTTP IdP cannot be wired to this platform in any configuration. The proxy the SAML block already required therefore has a second job — it terminates TLS on an unpublished listener the control plane fetches keys through, issuing from a local CA generated on first boot and trusted through `SSL_CERT_FILE`, so nothing private is committed and the Go-side rule is not weakened — while the browser keeps plain HTTP on the published listener, which is the issuer and so the `iss` claim the verifier compares exactly. That proxy is an enforced control and not advice: Casdoor serves its API and its UI from one port, so the browser must reach it and "keep it internal" is not available, which is why Casdoor publishes nothing and the proxy answers 404 to `/api/get-saml-login`, `/api/acs`, `/api/saml/metadata`, `/api/saml/redirect/*` and the whole `/cas/*` tree — five of CERT/CC VU#780781's nine CVEs live on that SAML service-provider path — while leaving the authorization-code routes alone. [docs/self-hosted-security.md](docs/self-hosted-security.md) gains §9 stating that posture plainly, CVE by CVE: which the pinned version fixes (9090, silently, seven weeks before disclosure), which are unpatched upstream but unreachable with no SAML provider configured, which are voided by configuration — and that **zero upstream providers is a security requirement rather than a default**, since the two account-takeover bugs live on the binding path that runs for *any* upstream, a "Sign in with Google" button included. It records one measured detail an operator would otherwise meet by surprise: Casdoor's JWT format embeds the user record in the token, where `password`, `totpSecret` and `hash` come back blank but `passwordSalt` does ride along — not a credential and not reversible into one, but user-record material inside a bearer token a browser forwards. And it says the shape enterprises should actually use: point `IDENTITY_OIDC_ISSUER` straight at your own provider and never start this profile, because the bundled Casdoor is a local-account IdP, not a federation hub — chaining a corporate IdP through it would route every login through exactly the code those CVEs are in. [deploy/compose/README.md](deploy/compose/README.md) documents the profile end to end, including the two consequences of a bundled provider sharing the stack's volumes: the seeded accounts are **well-known dev credentials** committed in the seed file, which is why the proxy publishes on loopback; and `docker compose down -v` takes the IdP's user store with everything else, after which the next boot mints a *different* signing certificate and every token issued before the wipe stops verifying. An eighth mechanic surfaced only by trying to log in, and it is the one with teeth: Casdoor's `InitDb` creates **`built-in/admin`, a global administrator, on the publicly documented password `123`**, *before* it reads the seed — so the setting that looked like the careful choice, `initDataNewOnly: true`, is precisely the one that leaves that credential in place, because it makes the seed's entry for an account that already exists a no-op. Both targets therefore keep the shipped `false` and the seed owns the account; the cost was measured rather than feared, and is narrow — entities the seed *names* are re-applied on restart, so admin-UI edits to those four accounts, three groups and one application revert, while a user created in the UI is untouched.

  **Helm carries the same bundle for a cluster, and deliberately not the same accounts** — `casdoor.enabled` (default `false`) renders first-party Deployment, Service, Ingress, NetworkPolicy and two Secrets — its DSN and its seed — as templates from *one* seed file shared byte-for-byte with compose, now enforced by `cmp` in CI rather than asserted in a comment. What differs per deployment is patched at render time: the three laptop accounts are dropped, because they are real working credentials and a published IdP must not carry documented passwords, while `built-in/admin` is **kept and re-owned** from a new required `casdoor.adminPassword` — leaving it out would not remove the account, only leave `123` on it behind an Ingress. It is seeded as plaintext for Casdoor to hash rather than hashed in the template, which is a determinism decision and not a shortcut: bcrypt salts randomly, so hashing at render would change the seed Secret and the Deployment checksum on every render, rolling the IdP pod on unchanged values and leaving Argo CD or Flux permanently out of sync — the same instability the chart already refuses for `postgresql.password` and the MinIO and OpenBao credentials. Casdoor stores bcrypt on the first boot and through the re-apply path, verified against a running 3.152.0 rather than assumed, so the plaintext reaches that Secret and never the database — the trade `console.clientSecret` has always made. The chart refuses rather than renders where a mismatch would surface as a uniform 401 nobody could distinguish from a forgery: a missing `adminPassword` or `clientSecret`, an `identity.oidc.audience` that is not the client id, an issuer that is not the ingress origin. CI gained a step that renders the chart both ways and asserts all of it, including that a default render mentions no Casdoor at all and that two renders of identical values are byte-identical.

  Review then found four more, all in the chart and all of the same family — a render that succeeds and a deployment that does not work. The seed **is a Secret, not a ConfigMap**, because it carries the console's OAuth client secret and a Casdoor global administrator's password, and `get configmaps` is routinely granted where `get secrets` is not; the mount is the same `subPath` volume, so nothing is paid for it. `console.redirectURIs` is **required**, because the seed's own callback is a laptop's and is replaced unconditionally — an empty list registered an application with no callback at all, and that failure surfaced at the first human's first sign-in rather than at install. `identity.roleMap` is **required whenever a mode is set**, because `parseRoleMap` refuses an empty map at startup, so an omitted role map did not merely deny humans, it exited the control plane and took the machine lanes down with it. And the IdP Deployment now uses `Recreate`: `replicas: 1` alone does not deliver one seeder, since the default rolling update rounds `maxSurge` up to 1 and an upgrade would run two `--createDatabase` and two seed appliers against one database. In compose, `SSL_CERT_FILE` no longer defaults to the bundled CA — it **replaces** Go's default certificate-file list rather than adding to it, so the default stack survived only on the separate directory scan finding the public roots, which is a property of the base image and not of the configuration.

  **GCP uses Google's identity provider rather than ours**, which is the whole point of the `trusted_proxy` mode: the staging Terraform gains `iap_backend_service` and `iap_members`, granting `roles/iap.httpsResourceAccessor` per backend service rather than project-wide, with validations that refuse `allUsers` and `allAuthenticatedUsers` by construction and make members-without-a-backend-service a plan-time error; `iap.googleapis.com` joins the enabled services; and a derived `identity_proxy_audience` output composes `/projects/<number>/global/backendServices/<id>` so the audience and the bindings cannot name different services. The OAuth brand and client are **not** Terraform-managed, and not by preference: `google_iap_brand` is deprecated and the IAP OAuth Admin APIs were permanently shut down on 2026-03-19, so the consent screen is documented as an operator step — with two independent reasons behind it, that a brand has no delete at all and that `google_iap_client` would put a live secret in a state file this configuration promises holds none.
