- **Ending a session now tears its sandbox down in seconds rather than at the next reap interval** — Deleting or archiving a session left its container or Pod running until the executor's reaper next ticked, up to a full `EXECUTOR_REAP_INTERVAL` (60s by default) later. On a laptop stack that looked like a leak; under load it was up to a minute of unpaid CPU and disk per ended session, and no API surface reported sandbox liveness, so nothing could poll for it. The end now publishes a wake the executor listens for, and the sweep it triggers is the ordinary one — same ownership, same per-session lock, same tiers — so idle-TTL and orphan behaviour are untouched and the interval becomes the floor under teardown latency instead of the latency itself. The wake is allowed to be lost: what the sweep reads is the tombstone the ending transaction already committed, so a missed one costs one interval and never a sandbox, and a deployment that sets no listener DSN keeps exactly today's behaviour. Each executor holds one connection for this outside its pool, so size a server's connection limit for `pool_max_conns` + 1 per executor; no existing DSN needs changing. Supersedes the eventual-teardown tradeoff recorded in plan 24's Decision 1 (#354).
