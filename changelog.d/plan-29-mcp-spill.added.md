- **An oversized MCP answer is kept, not just cut — plan 29 slice 4c (#45)** — A tool result is bounded twice over: it is the model's context, and it sits on an append-only log forever. So an MCP answer past that budget was truncated, and the rest was gone. It now lands in the session's sandbox and the model is told the path — the bargain a built-in tool's oversized output has had since #226, and deliberately the same convention: the same budget, the same `/tmp/tool_outputs/<call id>.txt`, one file per call. One convention, so a model that has learned where its truncated output goes is right whichever tool produced it. The notice is its own sentence — `[the full text of this answer was written to …]` — where the sandbox tools' promises the "full output", because that promise would not be true of an answer that also carried an image. **What spills is the answer as the model would have read it**, with none of the caps its inline blocks are held to: every text block, every text resource body named by the URI its inline document block is titled with, and — for a resource link or an audio clip, which this platform describes rather than carries — the same sentence it is described with inline, so the file and the answer never say different things about the same block. An image or a blob is named and not written: bytes nothing useful reads back, bounded by the transport rather than truncated, keeping the whole-or-nothing budget rule they already had. An answer carrying no text at all spills nothing rather than pointing at a file of sentences saying what is missing. **The trigger is whether the answer arrived whole**, reported by the renderer rather than inferred from a length — a length is wrong in both directions. Over the budget does not mean anything was lost: the budget exempts one already-capped block, so two sixty-kilobyte text blocks both arrive, and a size-triggered spill would write a file the model already has and tell it to go and read it. Under the budget does not mean nothing was lost: blocks are charged their *marshalled* size, so five thousand short text blocks sit well under it in text and far over it in JSON, and an answer whose first block is an oversized image loses everything behind it however small that is. The one loss the renderer cannot report is a label eating the budget under that same exemption, so the labels a block is *described* by — a resource link's address, a media type — are now capped where a document's title already was. The notice is a block of its own, after the answer and after the dropped-block notice, riding on top of the budget as that one does, because a pointer to the file holding the rest is worthless if the pointer is what gets cut. **A spill creates nothing**, and that needed a new seam: `sandbox.Provider.Attach`, Provision's read-only half. It hands back the session's running sandbox or `ErrNotFound`, and creates, starts, replaces and restores nothing — where `Provision` *heals*, rebuilding a container whose gate pairing went stale and reclaiming a gated pod that misses its readiness window. Healing is right for a caller about to run the model's tools and wrong for one writing a file it could equally skip: a spill must not cost a session the container it is working in, nor bring one into being for a session that never had one — whose model, having never run a built-in tool, has nothing to open the file with anyway. A session with no running sandbox truncates exactly as before. (Both backends implement it and the shared contract suite pins all three of its promises; the package's long-standing "there is no Attach" note is amended rather than deleted.) **A `self_hosted` session spills nothing**, and that is a deliberate divergence: its sandbox is the customer's, reachable only through a work API that has no MCP surface and no way to hand a file to a container this process does not own. The reference's own behaviour there is unobserved. An endpoint that cannot be reached, or a write that fails, costs the call nothing — the answer is what it would have been, and the model is never pointed at a file that is not there or at one holding nothing. A failed write is not retried for the rest of the pass, since the disk state that refused it will refuse the next call too; a failed lookup is, since it is one cheap read and a daemon that blinked should not cost a later call its file.
