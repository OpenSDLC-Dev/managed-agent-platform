- **An oversized MCP answer is kept, not just cut — plan 29 slice 4c (#45)** — A tool result is bounded twice over: it is the model's context, and it sits on an append-only log forever. So an MCP answer past that budget was truncated, and the rest was gone. It now lands in the session's sandbox and the model is told the path — the bargain a built-in tool's oversized output has had since #226, and deliberately the same convention: the same budget, the same `/tmp/tool_outputs/<call id>.txt`, one file per call. One convention, so a model that has learned where its truncated output goes is right whichever tool produced it. The notice is its own sentence — `[the full text of this answer was written to …]` — where the sandbox tools' promises the "full output", because that promise would not be true of an answer that also carried an image. **What spills is the answer as the model would have read it**, whole and uncapped: every text block, every text resource body named by the URI its inline document block is titled with, and — for a resource link or an audio clip, which this platform describes rather than carries — the same sentence it is described with inline, so the file and the answer never say different things about the same block. An image or a blob is named and not written: bytes nothing useful reads back, bounded by the transport rather than truncated, keeping the whole-or-nothing budget rule they already had. An answer carrying no text at all spills nothing rather than pointing at a file of sentences saying what is missing. **Two things trigger it**, because one would not be enough: the answer's own text past the budget, and the budget having dropped blocks — blocks are charged their *marshalled* size, so five thousand short text blocks sit well under the budget in text and far over it in JSON, and an answer whose first block is an oversized image loses everything behind it however small that is. The notice is a block of its own, after the answer and after the dropped-block notice, riding on top of the budget as that one does, because a pointer to the file holding the rest is worthless if the pointer is what gets cut. **No sandbox is created for a spill.** It goes into the one the session already has, looked up once a pass: the MCP driver is server-side on every environment kind and needs no sandbox of its own, so provisioning one here would put a container behind every cloud session that declares an MCP server — and point its model at a file it has no tool to open, since a session with no sandbox is a session whose agent never ran a built-in tool. A session with none truncates exactly as before. **A `self_hosted` session spills nothing**, and that is a deliberate divergence: its sandbox is the customer's, reachable only through a work API that has no MCP surface and no way to hand a file to a container this process does not own. The reference's own behaviour there is unobserved. A sandbox that cannot be adopted, or a write that fails, costs the call nothing either way — the answer is what it would have been, the model is never pointed at a file that is not there, and neither is retried for the rest of the pass.
