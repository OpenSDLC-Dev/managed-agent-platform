- **A confirmation sent together with the last outstanding tool result no longer strands the session (#45)** — A client may resolve a `requires_action` gate and post an outstanding tool's result in one `POST /events`, and the confirmation branch decided what to run next while counting only the calls the batch *denied* — never the calls its own results answered. The two sibling branches of the same switch had always counted both, because a result that has passed validation and is about to be appended is as answered as one already on the log. The consequence divided by who owned the remaining call. A client-executed one, and the branch read the turn as still outstanding and declined to wake the brain: the batch committed with the session flipped to `running`, every call answered, nothing queued, and no trigger left to fire — the tool-result trigger runs on a *subsequent* send, and a client that has just sent its last result has no reason to make one. The session hung there, and because a running session refuses both, it could no longer be archived or deleted; only a `user.interrupt` recovered it. A platform-executed one, and the same blindness went the other way: the resume enqueued a `tool_exec` (or `web_exec`) for a call the batch had just answered, so an executor provisioned the session's sandbox, found nothing to run, and cost a container start and a round trip — and on a `self_hosted` environment that empty work item was briefly pollable by a BYOC worker. Both are fixed by counting the batch's own results alongside its denials, and both now have a regression test that fails against the previous behavior. Found by review of the gate slice rather than by a report: the defect predates MCP entirely and needs only a built-in tool and a custom one to reproduce.
