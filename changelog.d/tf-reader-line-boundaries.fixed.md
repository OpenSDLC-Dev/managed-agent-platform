- **The two `.tf` readers took a whole file for one line, read past a heredoc opener carrying a comment, and never saw a Unicode heredoc tag** ([#768](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/768), [#766](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/766)) — `deploy/gcp/check_split.py` and `tools/kmsrole/hcl.go` break lines on `\n` alone, so a file separated by U+000B, U+000C, U+0085, U+2028 or U+2029 arrived as one long line: only the first block header matched, and both guards printed `ok` over a file they had not read. Terraform refuses those among structure and reads them as text inside a string, a comment or a heredoc body, so both readers now do the same — inside a `${…}` or `%{…}` too, where the contents are HCL again and neutralising had hidden them, though not inside `$${`/`%%{`, which Terraform reads as literal text. `<<EOT # note`, and `<<EOT` with one trailing space, left both looking at a bare opener once the comment was scrubbed, turning the configuration behind it into string content with the braces balancing again; nothing may follow a heredoc marker on its line now. Review found the same silence one step earlier: Terraform's tag is any HCL identifier, so `<<Ö` opened a heredoc neither reader saw. A tag they cannot match in full is refused now — rejecting a `.tf` Terraform accepts, deliberately — while a `-` inside a tag is read and `<<~TAG`, which Terraform refuses outright, no longer opens one.
