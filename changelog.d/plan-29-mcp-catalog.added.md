- **A session's MCP servers are discovered, and their tools are on record — plan 29 slice 2 (#45)** — A new internal work kind, `mcp_exec`, and the executor driver behind it: for each MCP server a session's agent declares, it connects, lists the tools, and writes the listing into a new `mcp_catalogs` table — or writes why it could not. Nothing is offered to a model yet; what this adds is the record a model's tools will later be assembled from, and the machinery that keeps that record honest. Like the web tools, MCP runs in the platform's own process for **cloud and self-hosted sessions alike** — the Anthropic SDK states three times that MCP tools are server-side, the work API has no MCP surface to poll, and a self-hosted worker's contract is the sandbox toolset alone — so the item is claimed on both environment kinds and offered to a worker on neither.

  **A server being down is a fact about that server, not a failure of the platform.** An unreachable endpoint, a URL that is not http(s), and a connection the session's networking policy refuses all land as a recorded failure and the session's turn proceeds without that server's tools, which is what the reference documents; treating any of them as a fault of the work item would put it in a retry loop against a server that is simply gone. The row is what carries the retry state, and its absence means something different from its presence: no row means never reached, a failed row is re-attempted on the next turn — which is what makes the documented "retried on the next idle-to-running transition" possible without inventing any new state — and a ready row is a listing that is not fetched again. Nothing here disables a server for the rest of a session: no source documents such a state, and one invented here would outlive the outage that caused it.

  **The session's networking policy reaches these dials, and is enforced before them.** Unlike `web_fetch` and `web_search`, which the reference documents as unaffected by networking, an MCP server sits behind the policy — `limited` networking's own `allow_mcp_servers` field exists to admit exactly these endpoints. The platform dials from the executor's process, structurally outside the per-session egress gate, so the check lives at that dial or nowhere; it runs before the connection rather than after, because a refusal that still opened the socket would already have told the server the session exists. The check decides on the environment kind first — a self-hosted environment has no networking block by construction, and is unconstrained beneath the address guard every one of these dials already passes — and then on the policy: unrestricted admits, `limited` admits a host named in `allowed_hosts` or, under `allow_mcp_servers`, the agent's own servers, and **anything else refuses**, which is what the per-session gate does with an unrecognized policy and the direction the two should not disagree in. A cloud environment's config always names a policy when the REST surface writes it, but the schema constrains only the environment kind, and a config-preserving update carries a stored value forward without revalidating it — so reading a missing discriminator as the wire default would make exactly the malformed row the one admitted everywhere. A refusal says which of the two it is, because only one of them has advice an operator can act on: a host `limited` does not admit is a list to add to, while a policy the platform does not recognize admits no host at all — and such a config may carry both admitting fields already, so pointing its owner at the list would point them at a change they have made and nothing is reading.

  **A catalog row can outlive the endpoint it came from, and does not get to.** `mcp_servers` is one of only two agent fields a running session may patch, and a patch replaces the array whole — so a server can be removed or repointed under a row still holding what its old endpoint reported. Those rows are deleted in the patch's own transaction; a row is additionally matched on its URL and not only its name when discovery decides what to re-fetch; and the pass settles under the session's own row lock, re-reading what the agent declares from inside it, so a patch landing while the dials are in flight cannot have a row written behind it for a server it just removed. The three are deliberately redundant: the delete is the mechanism, and the other two are what keep a missed or overtaken delete from being the kind of error that surfaces as a model calling tools that are not there. Rows are per session rather than a cache shared by URL, because two sessions may reach one server with different credentials and be shown different tools, and they are removed with the session.

  **What a server sends is bounded before it becomes storage, and before it becomes the platform's problem.** An MCP endpoint is customer-supplied and its answers are a third party's bytes, so three of them are cut off at the boundary. A `U+0000` anywhere in a tool's name or description is stripped and a tool whose input schema carries the escape is dropped instead of stripped — Postgres `jsonb` cannot hold one, and a rejected write would fault the work item before it completed, so a single NUL in a single description would put that session's discovery in a permanent retry loop against a server it can otherwise reach. A failure reason has the endpoint in it cut down to scheme and host, by value and then by pattern, because an `mcp_servers` entry may carry a credential in its userinfo or its query and everything that builds such a reason quotes the endpoint back. By value because the driver holds the endpoint, so the four spellings a message can contain are enumerable rather than guessable; a pattern could not do it alone, since a URL is recognized in prose by where it ends, a space has to end it, and a URL with a space in its query is one this platform accepts and dials — so the pattern stops mid-query and leaves the credential sitting beside a host that reads as redacted. The pattern pass remains for URLs the platform did not supply. The reason is then and is then validated as UTF-8 and capped. The validation runs on arrival as well as after the cap, because Postgres refuses an invalid byte sequence exactly as it refuses a NUL and a server need not send UTF-8 at all, while the cap can produce an invalid sequence out of input that was clean. And a discovery pass is bounded as a whole rather than only per server: the dials are serial and an executor runs one work item at a time, so twenty declared tarpits would otherwise hold every other session on that host for the better part of an hour, with the lease renewed throughout so nothing reclaimed it. A server the budget does not reach is a recorded failure like any other, re-attempted next turn.
