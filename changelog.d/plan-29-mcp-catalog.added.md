- **A session's MCP servers are discovered, and their tools are on record — plan 29 slice 2 (#45)** — A new internal work kind, `mcp_exec`, and the executor driver behind it: for each MCP server a session's agent declares, it connects, lists the tools, and writes the listing into a new `mcp_catalogs` table — or writes why it could not. Nothing is offered to a model yet; what this adds is the record a model's tools will later be assembled from, and the machinery that keeps that record honest. Like the web tools, MCP runs in the platform's own process for **cloud and self-hosted sessions alike** — the Anthropic SDK states three times that MCP tools are server-side, the work API has no MCP surface to poll, and a self-hosted worker's contract is the sandbox toolset alone — so the item is claimed on both environment kinds and offered to a worker on neither.

  **A server being down is a fact about that server, not a failure of the platform.** An unreachable endpoint, a URL that is not http(s), and a connection the session's networking policy refuses all land as a recorded failure and the session's turn proceeds without that server's tools, which is what the reference documents; treating any of them as a fault of the work item would put it in a retry loop against a server that is simply gone. The row is what carries the retry state, and its absence means something different from its presence: no row means never reached, a failed row is re-attempted on the next turn — which is what makes the documented "retried on the next idle-to-running transition" possible without inventing any new state — and a ready row is a listing that is not fetched again. Nothing here disables a server for the rest of a session: no source documents such a state, and one invented here would outlive the outage that caused it.

  **The session's networking policy reaches these dials, and is enforced before them.** Unlike `web_fetch` and `web_search`, which the reference documents as unaffected by networking, an MCP server sits behind the policy — `limited` networking's own `allow_mcp_servers` field exists to admit exactly these endpoints. The platform dials from the executor's process, structurally outside the per-session egress gate, so the check lives at that dial or nowhere; it runs before the connection rather than after, because a refusal that still opened the socket would already have told the server the session exists. `limited` admits a host named in `allowed_hosts` or, under `allow_mcp_servers`, the agent's own servers; everything else — including a self-hosted environment, which has no networking block at all — is unconstrained, beneath the address guard every one of these dials already passes. The refusal names what would admit the host, and echoes neither the URL nor the transport's own error into the stored reason, since an `mcp_servers` entry may carry credentials in its userinfo.

  **A catalog row can outlive the endpoint it came from, and does not get to.** `mcp_servers` is one of only two agent fields a running session may patch, and a patch replaces the array whole — so a server can be removed or repointed under a row still holding what its old endpoint reported. Those rows are deleted in the patch's own transaction, and a row is additionally matched on its URL and not only its name when discovery decides what to re-fetch. The two are deliberately redundant: the delete is the mechanism, and the URL comparison is what keeps a missed delete from being the kind of error that surfaces as a model calling tools that are not there. Rows are per session rather than a cache shared by URL, because two sessions may reach one server with different credentials and be shown different tools, and they are removed with the session.
