- **The driver that answers an MCP call, and a settlement that schedules it first — plan 29 slice 4a (#45)** — The `mcp_exec` driver had one job, filling a session's tool catalog. It gets its second here: an `agent.mcp_tool_use` that no `agent.mcp_tool_result` answers is dialled, called, and answered. One item still does one job — a pass that finds a call outstanding answers calls and does not discover, since the turn is stopped on that call while a listing is only ever wanted by a turn that has not started. A tool that ran and *failed* is an ordinary result with `is_error` rather than a work-item fault: MCP asks servers to report a failing tool that way so the model can read the error and self-correct, and faulting would reclaim-loop the item against a tool that fails the same way every time. A call the server answered by *refusing* — a JSON-RPC error for a tool it does not have, or a request for further input this platform has no surface to supply — is a result and nothing more: `mcp_connection_failed_error` is the wire's word for a connection that failed, and this one worked, so the model is told to stop calling that tool and no operator is sent after a connection that is fine. The two are told apart by a mark the MCP client sets (`ErrServerAnswered`), because the error message cannot tell them apart; the mark is a boundary rather than a list — every error raised after the SDK call returned is the server's answer, including an answer that arrived and could not be read. A call that never reached its server produces *both* a result and a `session.error` — the result so the turn can continue and every later replay stays valid, the error, typed `mcp_connection_failed_error` and naming the server, so an operator sees a connection to heal; its endpoint is cut to `scheme://host` exactly as a catalog reason is, because an `mcp_servers` entry is customer-supplied and may carry a credential. Its `retry_status` is always `retrying`, an egress refusal included, and that is a correction to plan 29 rather than an implementation of it: the plan read the union as asking whether a retry could help, and the SDK's own variant docs say it describes the session's fate — `terminal` is "the session … will transition to `terminated` state", which this session does not do, since the refused call is answered `is_error` and the turn carries on. Asserting a lifecycle the platform then contradicts is worse than the imprecision of `retrying`, whose own claim — that the server will be re-attempted — is true here every turn. MCP hands back five content types and the wire admits four, so three of those mappings are decisions rather than translations — an embedded resource becomes a titled `document` (a media type the plain-text source cannot carry, since its enum holds one value, is kept in the block's `context` rather than lost), a resource link becomes text naming it rather than a url source the model's own side would fetch unvetted, and audio is described rather than silently dropped — and all three are recorded in docs/DIVERGENCES.md. Two more shapes are normalised on the way out, because a Messages endpoint rejects an empty text block and replay puts an MCP result's content array into a Messages `tool_result` unchanged — so one on this append-only log fails not just this turn but every later one. The same standard applies to the two fields an image's source requires and the one a blob document's does, since a required field left blank is the same kind of hollow block: an image arrives described rather than sent when the server declared no media type or no bytes (MCP requires a mimeType on image content, so neither is a case to guess at), and a blob resource, which has an address to fall back on, takes the platform's pinned extension type instead. An *explicit* empty text block, which a server may legally send, is dropped before it can be that block; and a resource carrying no bytes either way — an empty file read over MCP, as ordinary there as through the built-in read — becomes text naming its address rather than a document whose source holds nothing. The pass is bounded as a whole by the budget discovery already had, renamed to say so (`EXECUTOR_MCP_PASS_TIMEOUT`, still five minutes): the calls are serial and this process runs one work item at a time, so an unbounded pass would let one turn's slow servers hold every other session on the replica. The bound is checked between calls and never cancels one — a call cut mid-flight would be answered as though the server had failed, and a tool with a side effect would have run with nothing on the log saying so — so a pass overruns by at most one call, commits what it answered, and hands the item back for the rest, which is a shape the four-way chain already had. Its first call is made whatever the budget says, or a bound short enough to have expired before the loop would answer nothing and spin the queue instead of slowing it. An answer is held to the same 100 KiB budget a built-in tool's output gets, because a tool result is on the append-only log forever and rides every later replay — blocks charged in the order the server sent them and kept or dropped whole, with a trailing block naming what went, since a silently short answer reads as the tool's whole output. A leading block is exempt when every string inside it was already capped where the block was built — a text block, or a document whose source is text — which is what makes an over-long answer of either shape truncated rather than dropped; without the document arm, the cap on a text resource could never reach the log at all, since a capped body plus its wrapper always exceeds the whole budget, and a 150 KB text file reached the model as a one-line notice. "Every string" is what the exemption rests on, so it holds the two labels a document carries about its resource — the URI it is titled with and the media type its `context` names — to a small ceiling of their own: neither is content, a label past 2 KiB is a label being used as a payload, and left uncapped they walked past the answer budget inside the one block that budget exempts. A leading image or base64 document gets no exemption: it is bounded by nothing but the transport's megabytes and cannot be truncated, and a result saying the image was too large is something a model can act on where half a base64 payload is not. Production calls go through a client whose request cap is the whole call's two-minute budget, which answers the question the timeout constant's own comment had left open: a call through the thirty-second dial client would have failed every tool slower than a handshake, whatever that constant said. Settlement is four-way now, and an outstanding MCP call comes first at every one of the four sites — the confirmation resume, the sandbox driver, the web driver, and the MCP driver itself. That ordering is correctness rather than preference: only this platform's driver answers an `agent.mcp_tool_use` (a client may post neither the call nor its result, and a BYOC worker's contract has no MCP surface at all), so the `tool_exec` that would otherwise come next is the one kind a customer-hosted worker claims and cannot finish. The MCP driver chains by handing its own item back rather than enqueuing a second one, since `Enqueue` is keyed `(session_id, kind)` over the live states and would be dropped on conflict with the item still running — silently, since a conflict is not an error. The scheduling side ships ahead of the emission on purpose: the brain and the control plane are separate deployments, so a rollout runs a new brain against an old control plane, and a brain that emitted an MCP call while a control-plane replica still lacked its resume arm would strand the call — the session left running rather than idle, which is the worse of the two, since a running session also refuses archive and delete and only a `user.interrupt` gets out of it. Nothing emits an MCP call yet, so all of this is inert until the brain does.
