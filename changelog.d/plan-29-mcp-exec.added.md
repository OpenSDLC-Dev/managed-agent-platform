- **The driver that answers an MCP call, and a settlement that schedules it first — plan 29 slice 4a (#45)** — The `mcp_exec` driver had one job, filling a session's tool catalog. It gets its second here: an `agent.mcp_tool_use` that no `agent.mcp_tool_result` answers is dialled, called, and answered. One item still does one job — a pass that finds a call outstanding answers calls and does not discover, since the turn is stopped on that call while a listing is only ever wanted by a turn that has not started. A tool that ran and *failed* is an ordinary result with `is_error` rather than a work-item fault: MCP asks servers to report a failing tool that way so the model can read the error and self-correct, and faulting would reclaim-loop the item against a tool that fails the same way every time. A call that never reached its server produces *both* a result and a `session.error` — the result so the turn can continue and every later replay stays valid, the error, typed `mcp_connection_failed_error` and naming the server, so an operator sees a connection to heal; its endpoint is cut to `scheme://host` exactly as a catalog reason is, because an `mcp_servers` entry is customer-supplied and may carry a credential. Its `retry_status` follows what the platform will actually do next: `retrying` for an ordinary failure, since every turn re-attempts a failed server, and `terminal` for an egress refusal, since no later turn changes the policy that refused the dial. Only the refusal is marked terminal — the line is at what the code can know, not what it might guess, and a connection error is a server restarting as readily as a host that will never resolve. MCP hands back five content types and the wire admits four, so three of those mappings are decisions rather than translations — an embedded resource becomes a titled `document` (a media type the plain-text source cannot carry, since its enum holds one value, is kept in the block's `context` rather than lost), a resource link becomes text naming it rather than a url source the model's own side would fetch unvetted, and audio is described rather than silently dropped — and all three are recorded in docs/DIVERGENCES.md. An answer is held to the same 100 KiB budget a built-in tool's output gets, because a tool result is on the append-only log forever and rides every later replay — blocks charged in the order the server sent them and kept or dropped whole, with a trailing block naming what went, since a silently short answer reads as the tool's whole output. One block is exempt and only one, a leading *text* block, which is capped on its own where it is built: that is what makes the ordinary over-long answer truncated rather than dropped. A leading image or base64 document gets no exemption — it is bounded by nothing but the transport's megabytes and has no truncation to fall back on, and a result saying the image was too large is something a model can act on where half a base64 payload is not. Production calls go through a client whose request cap is the whole call's two-minute budget, which answers the question the timeout constant's own comment had left open: a call through the thirty-second dial client would have failed every tool slower than a handshake, whatever that constant said. Settlement is four-way now, and an outstanding MCP call comes first at every one of the four sites — the confirmation resume, the sandbox driver, the web driver, and the MCP driver itself. That ordering is correctness rather than preference: only this platform's driver answers an `agent.mcp_tool_use` (a client may post neither the call nor its result, and a BYOC worker's contract has no MCP surface at all), so the `tool_exec` that would otherwise come next is the one kind a customer-hosted worker claims and cannot finish. The MCP driver chains by handing its own item back rather than enqueuing a second one, since `Enqueue` is keyed `(session_id, kind)` over the live states and would be dropped on conflict with the item still running — silently, since a conflict is not an error. The scheduling side ships ahead of the emission on purpose: the brain and the control plane are separate deployments, so a rollout runs a new brain against an old control plane, and a brain that emitted an MCP call while a control-plane replica still lacked its resume arm would strand the call — the session left running rather than idle, which is the worse of the two, since a running session also refuses archive and delete and only a `user.interrupt` gets out of it. Nothing emits an MCP call yet, so all of this is inert until the brain does.
