- **Agent toolset configuration is echoed resolved, and an `mcp_toolset` is now validated like its built-in twin — plan 29 slice 1 (#45)** — Three wire rungs an MCP-configured agent needs before any MCP client exists. **Resolved config echo:** every read of an agent — create, get, a pinned version, the list — every resolved-agent snapshot on a session, and the `agent` a `session.updated` event carries now render both toolset kinds with `configs` and `default_config` present and each omitted `enabled` / `permission_policy` filled with the value it resolves to, which is what the reference's response types require of `agent_toolset_20260401` and `mcp_toolset` alike; a bare `{"type":"mcp_toolset","mcp_server_name":"docs"}` comes back carrying `configs: []` and a `default_config` of `{"enabled":true,"permission_policy":{"type":"always_ask"}}`, the built-in kind resolving to `always_allow` instead. Only an entry that configures a tool the toolset actually has is resolved: one naming a tool that does not exist, one carrying no name (which the built-in toolset has always accepted), and an element that is not an object at all are echoed exactly as supplied, in place, because filling them in would state configuration the brain never applies and dropping them would shrink the list a client hands back after a round-trip. Resolution happens at render, so the agent and session resources still hold the client's own bytes, agents written before this change echo resolved without a backfill, and an update still merges against what was actually sent; the one copy that is written down is the `agent` inside a `session.updated` event, which records what the API answered when the event was appended. **Dangling toolsets are rejected:** an `mcp_toolset` naming a server absent from `mcp_servers` is a 400 on every surface that resolves a whole spec — agent create, agent update's merged result, a session's `agent_with_overrides`, and a session-update `agent.tools` patch. Only the mirror-image rung (a declared server no toolset references) was enforced; the reference's public MCP-connector guide states both directions, so the earlier reading — recorded as deliberate under #66 on the strength of the SDK's param docs alone — is corrected rather than retired quietly, and docs/DIVERGENCES.md says which way it moved. Two consequences follow from the rung binding whole specs rather than requests, and both are deliberate. The pair now moves together in both directions: clearing `mcp_servers` on a session override or patch while the `mcp_toolset` that referenced them stays is a 400, the mirror of the refusal that clearing `tools` already produced, so a client turning MCP off for one session replaces both sides or neither. And an agent stored before this change with a dangling toolset — which the old validator accepted — fails at session create rather than starting a session whose toolset names a server that does not exist; the same is true of a stored `mcp_toolset` carrying a misspelled nested key, which is now re-checked on every resolve exactly as the built-in toolset always has been. Both are the treatment #66's caps already give a stored spec. **`mcp_toolset` shape validation:** an unknown key anywhere in the `default_config` / `configs[]` / `permission_policy` nest, a `permission_policy.type` outside the two-value enum, or a leaf of the wrong JSON type is now a 400 naming the field's path — `mcp_toolset: configs must be an array`, not the dump of a Go struct definition a typed decoder produces. One rejection names no path, because it cannot: an object carrying the same member twice reads as its last occurrence alone, so a bad value hidden behind a good duplicate is caught by a typed decode kept as a backstop, which can say only that a repeated field carries conflicting values. `parseTools` had checked only that `mcp_server_name` was non-empty, so a misspelled `permission_polciy` was dropped by `encoding/json` and the tool silently resolved to the toolset default — the fail-open that #26 closed for the built-in toolset, still open on the one kind whose default is to stop and ask a human. A Messages-API-only key such as `defer_loading` is refused here too: the two MCP schemas are deliberately different and must not be conflated. Three further refusals close the ways an entry could be accepted and then echoed in a shape the response schema rejects, or resolve to a policy its author did not write: a `configs[]` entry that is not an object or carries no non-empty `name` (the field is required on the response type, and an unnamed entry configures nothing), and an explicit `null` for `enabled` or `permission_policy` — the wire's unions have no null arm, and a decoded null is indistinguishable from an omission, so `"permission_policy": null` under an `always_allow` default would have silently inherited it. **Along the way, one long-standing inference is retired:** the built-in toolset's `always_allow` default was recorded as unconfirmed (#59) because the SDK's wire types carry no resolved default; the public permission-policies guide states it outright, twice, so docs/DIVERGENCES.md now records both toolset defaults as documented rather than inferred.
