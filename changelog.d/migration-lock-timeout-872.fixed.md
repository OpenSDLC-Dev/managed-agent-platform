- **Every migration now waits at most 2 seconds for each lock it asks for** ([#872](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/872)) — Migrations 0041, 0042 and 0044 set no `lock_timeout`, so an upgrade from v0.4.0 could wait indefinitely for their locks on `session_threads`, `deployment_runs`, `sessions` and `memory_stores` behind a long transaction, while every later read and write of those tables queued behind the request. Migrate now starts each migration with a 2-second `lock_timeout`; one that sets its own keeps it. A give-up rolls the run back and is retried, as the later migrations' already were, so a conflict that outlasts all five attempts fails the start instead of stalling it, and the next start tries again: after about 115 seconds of table-lock waits and backoff, plus up to 2 seconds an attempt for each row 0041's or 0044's update finds held, plus the migrations' own work, which each attempt repeats (the bound is on waiting for each lock, not on a migration's run). The bound overrides any `lock_timeout` the database, role or DSN sets, for migrations only: it ends with the migration transaction, and a binary waiting for another's migration run still waits as long as that run takes. A database at v0.5.0 or later has applied these migrations already.
