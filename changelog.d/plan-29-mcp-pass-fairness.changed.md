- **A slow MCP server no longer keeps the ones behind it out of the catalog, and one that cannot be reached is said out loud — plan 29 slice 6b (#45)** — The discovery pass dialled a session's declared MCP servers one after another, so position decided reach: a server that accepted a connection and never answered spent the whole pass budget, and the servers declared after it were recorded unreached for the life of the session — the model was never offered their tools. The dials now run concurrently, bounded at the same 20 entries the wire caps `mcp_servers` at, with the rows staying in declaration order however the dials interleave. Resolving credentials stays serial ahead of them, because it may run an OAuth refresh and an issuer that detects refresh-token reuse answers two simultaneous exchanges of one token by revoking the family. The same change bounds what a tarpit server holds: the executor's work goroutine is tied up for one server's dial-and-list rather than the sum of every declared server's, still capped by `EXECUTOR_MCP_PASS_TIMEOUT`. A discovery failure now also reaches the session log — `mcp_connection_failed_error`, or `mcp_authentication_failed_error` when the server refused the credential rather than failing to answer — naming the server, appended in the settlement's own transaction so the catalog row and the line about it commit together. It is said on the cadence the server is re-dialled at: once per work cycle, not once per turn, because a new work cycle already drops a session's failed rows and the row is what the dedupe reads. A server the pass simply ran out of time on says nothing, since there is no connection behind it for an operator to heal — and that row never silences the server's first real verdict.
