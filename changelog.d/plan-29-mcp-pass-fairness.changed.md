- **A slow MCP server no longer keeps the ones behind it out of the catalog, and one that cannot be reached is said out loud — plan 29 slice 6b (#45)** — The discovery pass dialled a session's declared MCP servers one after another, so position decided reach: a server that accepted a connection and never answered spent the whole pass budget, and the servers declared after it were recorded unreached for the life of the session — the model was never offered their tools. The dials now run concurrently, with the rows staying in declaration order however they interleave. Credentials are still resolved one at a time — an issuer that detects refresh-token reuse answers two simultaneous exchanges of one token by revoking the family — but each dial starts as soon as its own credential is resolved, since a refreshed token's remaining life may be only the leeway that triggered the refresh. The number of dials in flight is capped by what a pass can hold in memory, each connection carrying its own 8 MiB response budget. The same change bounds what a tarpit server holds: the executor's work goroutine is tied up for one server's dial-and-list rather than the sum of every declared server's, still capped by `EXECUTOR_MCP_PASS_TIMEOUT`. A discovery failure now also reaches the session log — `mcp_connection_failed_error`, or `mcp_authentication_failed_error` when the credential was the problem (refused by the server, or one the platform could not produce at all) — naming the server, appended in the settlement's own transaction so the catalog row and the line about it commit together. It is said on the cadence the server is re-dialled at: once per work cycle, not once per turn, because a new work cycle already drops a session's failed rows and the row is what the dedupe reads. A server the pass simply ran out of time on says nothing, since there is no connection behind it for an operator to heal — and that row never silences the server's first real verdict.
