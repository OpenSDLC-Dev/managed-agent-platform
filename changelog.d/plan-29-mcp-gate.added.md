- **An MCP tool call can stop and ask a human, and a refused one is answered in its own shape — plan 29 slice 3 (#45)** — The permission gate had been scoped to the platform's built-in tools since it was built, and the reason was in its own comment: a denial was answered with an `agent.tool_result` keyed by `tool_use_id`, which is not the answer a client watching an MCP tool waits for. Both halves move together here. `agent.mcp_tool_use` joins the confirmable set, so an MCP tool whose resolved policy is `always_ask` now suspends the session on `requires_action` and appears in the `session.status_idle` stop reason's `event_ids` exactly as a built-in does — and the human approves it by sending the same `user.tool_confirmation` keyed by `tool_use_id`, which is not an inference: the reference documents that field as "The id of the `agent.tool_use` or `agent.mcp_tool_use` event this result corresponds to", and documents the MCP tool use's `session_thread_id` as the value to echo back on the confirmation. A gate that admitted only built-ins would have run an MCP call the agent's own policy said to stop for. Denial synthesis now reads the family of the call it is refusing and answers in it — `agent.mcp_tool_result` keyed by `mcp_tool_use_id`, with `is_error` and the `deny_message` as content — and one batch refusing a built-in and an MCP call together produces one of each. That correction is invisible from the database, which is what made it worth testing directly: the answered-ness check coalesces all three reference keys, so a wrong-family answer marks the call answered, releases the gate and replays cleanly, and is wrong only where a client is looking. The synthesis moved out of the control plane into the events package to sit beside the interrupt's, since both encode the same knowledge — which result answers which call, under which key — from one table that a white-box test now holds consistent with the gate's own membership. Two consequences are deliberate and worth naming. A session parked on an ask-gated MCP call is excluded from idle-TTL sandbox reaping like any other pending approval, though the MCP call needs no sandbox itself: the session is mid-turn and its built-in tools resume into the workspace a reap would have destroyed. And the approval-latency metric now includes waits on MCP approvals, which is what it measures. Nothing stamps a permission on an MCP call yet — the brain offers no MCP tools to a model until the catalog is assembled into its request — so on a live log this slice is machinery waiting for its first caller; the confirmation resume still schedules work for built-ins alone, and the arm that runs an approved MCP call arrives with the settlement that first emits one.
