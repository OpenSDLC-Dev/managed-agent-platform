- **Plan 47 approved — a cancelled sandbox command leaves itself running** ([docs/plan/47_cancelled-exec-kills-nothing.md](docs/plan/47_cancelled-exec-kills-nothing.md), [#598](https://github.com/OpenSDLC-Dev/managed-agent-platform/issues/598)) — the design for the reclaim race the plan 40 review found, one layer below where the issue put it: `Sandbox.Exec` promises nothing about the command when the caller's context is cancelled, and both backends return `ctx.Err()` having signalled nothing, so a stall or a lost lease leaves it running while the session advisory lock releases and a reclaiming executor adopts the same sandbox. Reading the code corrected the issue three times: only the package install is inside that lock, a crash is not required, and every pass but `packages` sends a zero `Timeout` whose only bound is that cancellation. Key decisions: `Exec` terminates the command's process group before returning, best effort, on a detached `WithoutCancel` context with a short budget whose expiry is not an error — a cancellation must never become a hang; docker's exec wrapper gains a pid file, the daemon being unable to signal an exec and the pid it holds being host-namespace, where k8s already writes one; `TimedOut` stays false; and no new per-call timeouts, the outer contexts already bounding these calls. Two slices, because the issue's two remedies are not alternatives — a *crashed* holder runs no code — so the in-sandbox stale-owner lock stays slice 2.
